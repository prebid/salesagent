4. What the two open classes actually look like

Class 1 — the effect named in the Examples column that nothing reads

tests/bdd/steps/domain/uc026_package_media_buy.py:2003 binds the outcome should be {outcome}. Its success branch delegates to then_operation_succeeds (:1968), whose entire contract is: no error in ctx, a payload actually arrived, and the status is not a failure value. The outcome cell says "success with keyword added"; nothing reads a keyword.

READING The reason is upstream of the test. keyword_targets_add and keyword_targets_remove appear zero times under src/, and AdCPPackageUpdate (src/core/schemas/_base.py:3045) does not declare them, so there is no handler and no declared field. src/core/tools/media_buy_update.py appends an AffectedPackage on five branches only (budget, creative_ids, creatives, creative_assignments, targeting_overlay). AdCP 3.2.1 update-media-buy-response.json#/oneOf/0/properties/affected_packages defines the field as full Package objects showing complete post-update state, so a keyword op that modified a package would have to report one — and does not, because nothing implements it.

The 70f74f781 mock fix does not reach these rows. It made the mock report the package for the two actions that change one (pause / resume); the keyword actions still fall through to the empty return, because there is no production handler for the mock to be called from.

Class 2 — a row whose expected value coincides with production's only possible answer

EXECUTION This is the sharpest finding of the audit, and it refines what the in-tree ledger records.

tests/bdd/conftest.py:1943 notes that over e2e_rest, the [scheduled] row of @T-UC-004-webhook-notification-type cannot fail, because src/services/delivery_webhook_scheduler.py:332 assigns NotificationType.scheduled unconditionally. True — and the same row is equally unfalsifiable on all three in-process transports, for a different reason: there the payload is built by src/services/webhook_delivery_service.py:347-353, which does select the type, but "scheduled" is its else branch. A row asking for the default value cannot distinguish a working selector from a constant.

Pinning that selector to the in-spec constant "scheduled" (mutation M1b) turned the final and adjusted rows RED on all three transports (6/6) and left all three scheduled rows GREEN. Measured, per nodeid:

The class-5 candidate that looked worst and is dead

tests/harness/_mixins.py:1261 (WebhookMixin.call_deliver, payload authored at :1299-1312) writes the response payload itself, including notification_type and next_expected_at, and its own docstring says it "mirrors the payload shape that WebhookDeliveryService produces so that BDD Then steps can assert on payload fields without requiring the full service stack." A scenario asserting notification_type == "<type>" against that payload would be reading back the Examples column it was handed.

EXECUTION It is not reached. The BDD route table sends @webhook to "circuit-breaker" (scripts/audit/storyboard_spec.py:831) and therefore to CircuitBreakerEnv, whose CircuitBreakerMixin (tests/harness/_mixins.py:1335) extends LocalOriginMixin and not WebhookMixin — so its own call_deliver (:1728), which translates to production's is_final / is_adjusted flags and calls send_delivery_webhook, is the one that runs. That is why M1 and M1b reddened real rows at all. Enumerating every env the route table can build (11 by dotted string, 7 by callable) finds no WebhookEnv; it is live only in tests/integration/test_delivery_webhook_behavioral.py.

Three places in the repo say otherwise and are stale: tests/bdd/conftest.py:6, tests/bdd/conftest.py:6831 ("UC-004 @webhook → WebhookEnv (unit variant, no DB needed)") and tests/CLAUDE.md:144. Mutation beat reading here: those docstrings are what led this audit to the wrong hypothesis first, and only the mutation corrected it.

5. The machinery that already closes classes 3, 5 and 6

  • Class 3 — tests/unit/test_architecture_bdd_assertion_strength.py bans four weak-assertion shapes (hasattr, getattr-existence, len(x) > 0, early-return on a ctx flag) with all four allowlists empty. Plus 32 further test_architecture_bdd_*.py guards.
  • Class 5 — tests/unit/test_architecture_bdd_breaker_scenarios_graded_live.py is the standing check that the two UC-004 breaker scenarios stop grading a dict in the test process (#2060). It is unusually honest about its own limit: it grades the structural criteria and says plainly that the behavioural half can only be graded by a bdd-in-network run.
  • Dormancy — tests/bdd/dormant_scenarios.txt, 150 keyed entries, shrink-only, enforced per-test rather than by a count so it fires on a subset run.
  • Vacuous rows — _UC010_PARKED_ROWS (tests/bdd/conftest.py:1467) parks an individual Examples row that would pass vacuously, with run=False so it does not execute and cannot report XPASS. Its comment states the principle exactly: "a test that cannot fail is not coverage."
That last mechanism is the right one and it exists for UC-010 only — one table, one entry. There is no general equivalent, which is why the UC-004 [scheduled] row and the 54 UC-026 effect rows have nowhere to be recorded.

Not sampled. Stated plainly, because each is a real limit on the verdicts above:

  • The e2e_rest transport. No live Docker stack was brought up, so every mutation result is in-process only (a2a / mcp / rest). The class-2 finding is stronger for it — the in-process half was previously unexamined — but any claim about tests/bdd/e2e_rest_known_failures.txt (8 live entries) needs a bdd-in-network run.
  • UC-006, UC-010, UC-011, UC-019 by execution. These carry the largest step modules (7220, 3138, 4919, 3399 lines) and were read, not mutated. UC-010's extensive park tables suggest prior lanes covered it; UC-006 and UC-019 are the largest unmeasured surfaces in this audit.
  • The 18 unwired features. ~1150 scenarios that never collect. Out of scope here (they do not pass), but they are the biggest single block of ungraded obligation in the tree.
  • The payload-capture artifact. tests/bdd/payload_capture.py:12 records that 5421 of 8182 measured nodeids dispatch nothing. That is a strong class-1/class-5 prospecting signal and was not mined — it needs a full-suite run to populate.
