One class per schema branch: request generation in the adcp SDK

Solution design · adcp-client-python at 9.0.0b2 · bundle schemas/cache/3.2 (1,509 non-bundled files) · measured in a fresh clone at 00720022b (branch fix/anyof-branch-conditions; upstream main 0c7e8b86d) · supersedes the constraint-compiler design (codegen-solution-design.html), whose census this reuses and re-derives. Terminology: a schema’s anyOf/oneOf members are called branches throughout.

The generator renders a response root’s branches as one class each and a union (CreateMediaBuyResponse = CreateMediaBuyResponse1 | 2 | 3), but flattens a request root into one class — CreateMediaBuyRequest: 31 fields, every branch-discriminating field optional — and then bolts on a validator that reads only each branch’s required key and discards the rest. The flattening is what creates the validator’s job. This design deletes the job: every flat-root combinator schema is emitted as one class per branch plus a union alias, so the branch content stops being a rule and becomes a type. Measured over the whole affected population: all 247 branch-level keyword occurrences dissolve into types; zero survive as runtime checks. What survives as checks is the root conjuncts beside the combinator (41 occurrences), and those keep the constraint compiler — shrunk to that jurisdiction, with the closure rule unchanged: compiled, classified by a named rule, or UnexpressibleKeywordError. No skip lane, no ledger. The size of the change is not an input to any choice in this document: the shape that is correct against the schema wins, and consumer-facing consequences are documented (§5) so adopters can migrate, never weighed as counter-arguments.

The branch-class design therefore does not delete the constraint compiler of the superseded design — it shrinks its jurisdiction from “everything, including the combinator” to “root conjuncts only,” and relocates its output onto the branch classes. The combinator content — where the chased defect lived, and where all five red parity cases sit — is types.

2.2 · The extra='allow' caveat, stated plainly

The generated models are extra='allow' (the schemas say additionalProperties: true; forward compatibility is the SDK’s deliberate choice, and this design does not change it). Under extra='allow', merely omitting a field from a branch class does not refuse a wire document that carries it — pydantic would file proposal_id under extras and accept. So the 19 absence occurrences (plus the 7 distributed outright bans) are enforced in two layers, and the claim for each layer is different:

  • At construction, absence is a type. The branch class does not declare the field; the pydantic mypy plugin and every IDE refuse the keyword argument. There is no spelling of CommittedProposalExecution(packages=…) that typechecks.
  • At wire validation, absence is one shared check. Each branch class carries a node-derived frozen set (_absent) and the base class carries one mode='before' hook, written once in src/adcp/types/base.py, that refuses a listed key present in the raw document — present with any value, explicit null included, which is exactly JSON Schema’s not:{required} semantics. This is a check wearing the census’s “absence” label, and the count above says so rather than hiding it: it is the one place the type system alone cannot carry the branch content, because the type system does not see raw documents. It is one primitive, not per-site logic, and the alternative — extra='forbid' on branch classes — would refuse spec-permitted unknown fields, a different behavior change this design does not smuggle in.

3 · Names: every branch, from its node — a folded-in prerequisite

The naming rule exists, designed and measured under #1409 (scripts/union_arm_names.py, branch claude/issue-1409-union-arm-naming; measured 557 root-level branches bundle-wide: 169 by title, 82 by discriminator const, 27 by required set, 278 creating no class, 1 refused). Two amendments, both forced by this design and both mechanical:

  1. Step zero inverts for flat-root combinator schemas. The rule’s step zero says a branch introducing no new property is a validation branch and must mint no class — correct when a flat root class exists for it to refine. Under this design the flat root class no longer exists: the branch is the request shape (the merged root properties plus the branch’s modifications), and the class names exactly what a buyer sends. On a flat-root combinator schema, every branch mints a class.
  2. One new rung, still node-derived. Naming rungs stay title → discriminator const → full sorted required set, each prefixed with the parent model name (the title rung too: response-branch titles already carry their stem — CreateMediaBuySuccess — but request-branch titles are prose, and a bare CommittedProposalExecution on the flat surface does not say what it is; parent + PascalCase(title) is as mechanical as parent + const). Rung 3b: a branch whose only content is a nested required overlay is named parent + property + its sorted nested required set. One branch in the population needs it.

4 · Discriminated union or plain union, per schema

Measured: a pydantic discriminated union needs one field required in every branch with a distinct const per branch. Three schemas of 43 have one:

SchemaTagValues
brand/verify-brand-claim-request.jsonclaim_typesubsidiary / parent / property / trademark
account/list-account-changes-response.jsonstatuscompleted / failed
media-buy/get-reporting-status-response.jsonstatuscompleted / failed

Those three get Annotated[Union[…], Field(discriminator='…')]: single-pass dispatch and a one-line no-match error naming the tag. create-media-buy is not one of them — branches 0 and 1 differ by a const nested inside an optional object (budget_allocation.mode), branch 2 by the presence of proposal_id; there is no shared top-level tag, and inventing one would invent a spec field. (A pydantic Discriminator with a callable could synthesize dispatch, but the callable’s logic is hand-authored semantics per schema — the thing this design exists to stop. Refused.)

Everything else is a plain union in left-to-right mode (union_mode='left_to_right'), not smart mode, for one reason: determinism of the returned class. The anyOf schemas of the at-least-one-of idiom (§9) have overlapping branches — a control_media_buy document carrying both paused and total_budget satisfies two branches — and smart mode’s match choice is a scoring heuristic. Left-to-right is the schema’s own order, stable under regeneration of the same bundle, and JSON Schema anyOf semantics exactly: accepted iff at least one branch accepts. Disjointness was measured, not assumed: a first-order prover over the census (shared required consts with distinct values, or one branch requiring a field another bans) proves 12 of the 43 schemas (27 branches) pairwise disjoint; three more — create-media-buy (the two mode consts clash once branch 1’s required budget_allocation is present), buy-products and request-proposals (the negated-nested-shape conjunct separates the brand and account branches) — are disjoint by reasoning the emitter can also perform from the Arm records. For oneOf roots, exactly-one must also hold: every oneOf in the population is in the first-order-provable set, so at-least-one equals exactly-one and the union is the full semantics. The emitter proves that disjointness from the Arm records when it renders a oneOf as a union; a oneOf it cannot prove disjoint refuses generation (UndisjointOneOfError(file, pointer) in the same family as UnexpressibleKeywordError) rather than shipping anyOf-weaker semantics. Zero refusals fire at the pin for this population. The 22 existing response-union modules keep their current contract (cross-branch exclusivity carried by wire validation) until they pass through the same emitter in the landing series.

4.1 · The no-match error: the consumer’s whole diagnostic

When no branch matches, pydantic raises one ValidationError with a sub-error group per branch, keyed by the branch class name. For the document that supplies no required group at all (the ninth parity case), the three groups read, in schema order:

  Field required [type=missing, ...]

  Field required [type=missing, ...]      (and .total_budget, .budget_allocation)

Schema-derived text — the class names are the branch titles — and strictly more informative than the flat validator’s one sentence (“requires at least one of these field groups: …”), which named the groups but not what was wrong inside the nearest one. The two tests that match the old wording (tests/test_codegen_contract_compatibility.py:297 and :322, both match="at least one of these field groups") are asserting the message of a validator this design deletes; they are rewritten against the union error in the commit that deletes it (§7, commit 4), inside the 9.0 breaking window. A cross-branch mixture (e.g. packages + proposal_id) reports, per branch, the field that branch refuses — the absence hook names the offending key: proposal_id is not accepted by this request shape with the pointer, under the branch’s group.

5 · Consumer-facing consequences, documented for migration

Nothing in this section is a counterweight. These are the consequences an adopter migrating to 9.0 needs written down — what breaks, what the migration looks like, what the error reads like — and the governing distinction is: parsing accepts what the wire may carry; construction must only permit what the schema permits. A TypeAdapter over the union is parsing — reading a document the schema already governs. Any mechanism that keeps the flat shape constructible is construction of the illegal — so there is no permissive constructor accepting arbitrary kwargs, no __new__ that inspects arguments and routes to a branch, and no alias keeping CreateMediaBuyRequest(…) callable. Each of those is a place where the wrong combination can be spelled again, which is precisely what is being removed; if the common path becomes less convenient, that is the correct outcome, because the convenience was the defect.

What breaks. adcp.types.CreateMediaBuyRequest (and 42 peers) stops being a class and becomes a TypeAlias union — the exact shape responses already have. Consequences, each loud, none silent:

  • CreateMediaBuyRequest(…) raises TypeError (a union is not callable). The migration table maps each flat name to its branch classes; the fix at a construction site is to name the branch being constructed — which is information the caller already had, since the flat constructor’s argument combination was the branch choice, implicitly and uncheckably.
  • CreateMediaBuyRequest.model_validate(raw) becomes TypeAdapter(CreateMediaBuyRequest).validate_python(raw). The SDK exports one cached adapter per union alias next to the alias (node-derived name: CreateMediaBuyRequestAdapter), so dict-shaped callers change one spelling. No factory function with 31 optional keywords is provided: that is the flat class again, reintroduced at runtime, and it makes nothing impossible.
  • isinstance(x, CreateMediaBuyRequest) keeps working (a union is a valid second argument), and issubclass-style registry checks need the member tuple.
  • Surface count: 43 flat names become 43 aliases + 124 branch classes (+ ~15 module-internal variant models with no public binding). The flat surface grows by the branch classes; every new name is schema-derived; the rename table for the response ordinals rides the same MIGRATION_v8_to_v9.md table, and aliases.py re-points as it did under PR #1374’s renumbering. 9.0.0 is in beta; this is the window.

What it does to our seller. Measured against prebid-salesagent at 4eedcb1de (pins adcp==6.6.0, so this arrives with the 9.x bump, not as a hotfix):

  • src/core/schemas/_base.py:2209 — class CreateMediaBuyRequest(BuyerRequest, LibraryCreateMediaBuyRequest) subclasses the flat class and narrows fields (packages → local PackageRequest, push_notification_config, brand). A union cannot be subclassed; the seller subclasses each branch class and declares a local union — the shape it already uses for responses (CreateMediaBuySuccess/CreateMediaBuyError extending the library branch classes, CreateMediaBuyResponse = CreateMediaBuySuccess | CreateMediaBuyError, same file). The narrowings land only on the branches that carry the field, which is itself a correction: today the proposal branch carries a dead packages narrowing.
  • src/core/tools/registry.py:129 — ToolSpec.dto: type[Req] and its issubclass(self.dto, BaseModel) check assume a class. The row type widens to accept a union alias; the registry builds one cached TypeAdapter per row at import; the AccountIdentity derivation (“the DTO requires account”) quantifies over the union’s members (all-of for required-ness, since every branch of these tools requires account at the root).
  • src/core/tools/_boundary.py:228 — TOOLS[tool_name].dto.model_validate(raw) becomes the row’s adapter: one line. serve()-style dispatch is otherwise untouched: the _impl annotation req: CreateMediaBuyRequest is still one name, and the body replaces optional-field sniffing (if req.proposal_id:…) with isinstance/match over branch classes — which mypy can check for exhaustiveness, a dispatch the flat class could not offer.
  • Inherited blast radius, measured previously and inherited unchanged: 31 SDK-side test failures, 28 of them fixtures encoding requests the bundled schema also refuses, concentrated in two shared factories (≈5 edits); and tests/test_decisioning_webhook_emit.py:497 carries a comment stating the incomplete validator’s contract as fact — those edits are corrections of fixtures that the defect itself taught, not accommodation of the new design.

8 · Verifying the flaw class is eliminated, not just these instances

This class of defect has twice been believed fixed and then found again in the same kind. So the design states how the class is confirmed gone, and the statement rests on a distinction: a validation defect is tested by sending a bad document and checking the refusal; an impossibility is tested by trying to spell the bad thing and failing before anything runs. Verification has four layers, from instance to class.

8.1 · Spelling failures: negative type-check fixtures

The SDK already grades adopter-visible typing with fixture files under two checkers: make test-type-checks (mypy --strict, zero type: ignore allowed) and scripts/run_pyright_type_checks.py over tests/type_checks/ (72 fixtures today, all positive — code that must check clean). This design adds the inverted lane the impossibility claims need: tests/type_checks_negative/, graded by the same runner with the expectation reversed — each fixture spells exactly one forbidden construction and carries a marker comment naming the expected diagnostic code and line; the runner asserts the checker reports that diagnostic there, and a negative fixture that type-checks clean fails the suite (the impossibility has regressed to a possibility). The zero-ignore contract on the positive lane is untouched. The concrete fixtures, one per defect of §2.1:

  • CreateMediaBuyRequestCommittedProposalExecution(packages=…, proposal_id=…, …) — expected: unknown keyword argument (call-arg / reportCallIssue). Both names together are a type error, not a validation error, on every branch class.
  • a fixed-allocation branch package without budget — expected: missing required argument on the branch’s own item model, at construction, with no validator involved.
  • mode="seller_optimized" on the fixed-allocation branch’s budget_allocation — expected: Literal incompatibility naming the field mode, not a composition keyword.

8.2 · Construction failures: the error comes from the branch class itself

The same three spellings exercised at runtime assert the provenance of the refusal, not just its existence: a pydantic ValidationError whose loc names the field (packages.0.budget, type=missing; budget_allocation.mode, type=literal_error) raised by the branch class’s own constructor — asserted by error type and location, never by message text. A refusal that instead arrives from a root-level model validator would mean the shape regressed to flat-plus-check, so the assertions pin where the refusal originates.

8.3 · The differential witness: the parity corpus, population derived

The parity suite (4ad62cdaf/00720022b) remains the independent witness that model verdicts equal bundled-schema verdicts on real documents, with both of that work’s rules kept: population membership is derived (every generated union alias and every flat-root module — read off the generated tree, not an id list kept in the test), the suite asserts the population is non-empty, and it reads no ledger — there is no file to append a divergence to, because validation-model-divergences.json is deleted in commit 5 and the divergence set is asserted equal to the empty set with no allowlist parameter left to grow.

8.4 · The class-level guarantee: what a future schema would have to contain

The actual test of the class is the generalisation: what would a future schema branch have to contain for the generator to produce a model that permits something the schema forbids? After this design there are exactly two channels, and they are different in kind:

  • A keyword kind the grammar does not know. This cannot produce a weaker model, because it cannot produce a model: the reader is key-consuming, and an unaccounted key raises UnexpressibleKeywordError(file, pointer, keyword), aborting generation before install (generate_types.py’s staging-and-rollback keeps the checkout clean). The refusal-at-generation step is the class-level guarantee, and it is exercised, not assumed: a fixture schema carrying a deliberately unknown constraint keyword runs through the generator in a test that asserts the abort and its named file/pointer/keyword (the build fails; no test has to catch a shipped model, because no model ships); and the break-it-on-purpose probe — comment out one compiler case, regeneration goes red at the closure test — is run once per landing commit, red only counting at this design’s own assertion. The bundle-wide emit-closure test (commit 5) re-derives the full accounting — every parsed constraint is a type, a named-rule classification, or a compiled check — on every run, so the census of §2 is a guard, not a snapshot.
  • A semantic slip inside a kind the grammar does know — suppliedness of an explicit null, vacuous descent through an absent parent, the extra='allow' interplay of §2.2. This is the honest residual channel, and it is detection, not impossibility: it is bounded to the ~10 hand-written vocabulary primitives (each pinned by its own convention test) plus the emitter’s composition of them, and the differential corpus of §8.3 is the instrument that catches a composition slip first, on real documents against the canonical validator. Claiming this channel closed by construction would be the overclaim this document refuses to make.

“We fixed the instances we found” is what has happened twice. The statement this section makes instead: a model that under-enforces its schema’s combinator content cannot be generated — the attempt fails at generation, and the run that proves the attempt fails is in the suite — and the one channel that remains (primitive semantics) is named, bounded, and witnessed differentially.

9 · The strongest argument against this design

It reifies a partition the schema does not define. anyOf is a satisfaction condition over documents, not a taxonomy; this design turns each branch into a nominal type, and a parsed document comes back as exactly one of them. Measured with the disjointness prover of §4: only 15 of the 43 schemas (34 branches) have a partition the schema itself defines; the other 28 schemas — 90 of the 124 branches — are the overlapping at-least-one-of idiom (package-control 15, control-media-buy-request 12, frequency-cap-constraints 6, user-match 5, and 24 more), where a document carrying both paused and total_budget satisfies two branches. The SDK must still return one class, and left-to-right makes the pick deterministic but schema-arbitrary: two bundles identical in meaning that differ only in branch order (a null edit under anyOf semantics) generate SDKs that hand the same document different class identities. A consumer’s isinstance dispatch on that identity looks type-safe and is actually coupled to branch order — the type system presenting noise as signal. The flat class, whatever else was wrong with it, had no such channel.

The answer, in three parts, all about what is and is not schema information. First, for the 15 schema-defined partitions — titles, discriminator consts, provable mutual absence — the class identity of a parsed document is schema information the flat shape destroyed; recovering it is the point, and that set contains every schema whose branches carry distinct shapes (every oneOf, every const-discriminated schema, create-media-buy itself). Second, for the overlapping 28 the design does not pretend otherwise — and the census closes the exposure: in every one of those 28 schemas the branch content is requiredness only, so the branch classes are generated with identical field sets and an order-coupled isinstance can read nothing that differs between the candidates. The channel exists and carries zero bits. What cannot be removed is a consumer writing code that branches on it; what the design guarantees is that such code cannot observe different data by doing so, and the union alias — not the member — is the documented contract for parsed documents. Third, the residual correctness exposure that actually matters is not this one but §8.4’s second channel — a primitive whose semantics slip from JSON Schema’s on nulls or absent parents — and that is where the verification instruments point. If a stronger argument against the design exists, it is there, not in the number of classes or the size of the migration: those are consequences, documented in §5, and they were given no weight in any choice this document makes.

Amendment: the emit rule is a partition test, not a branch count

This supersedes the design’s uniform “emit branch classes for all 43 schemas”. The design’s own objection against itself was correct — for 90 of the 124 branches it reifies a partition the schema does not define — and the answer is not to argue the channel carries no information. It is to stop minting classes where there is no partition.

What forced the change: asking what happens to branches that overlap and carry no required at all. Measured over the bundle, 798 root-combinator branches across 250 schemas, 134 carry no required. Most are value unions rather than object shapes — core/start-timing.json is {const} vs {format} (that is Literal["asap"] | datetime), core/geo-place-type.json is enum-vs-pattern, and 108 branches are a bare {$ref}. Those already map to A | B at the field level and need nothing. Filtering to genuinely object-shaped branches with no required leaves 15, in five schemas:

media-buy/buy-products-request.json          2 branches
  0: {required: ["brand"]}
  1: {properties: {account: {required: ["brand","operator"]}}}

core/postal-country-system.json             10 branches
  0: {properties: {country: {const:"US"}, system: {enum:["zip","zip_plus_four"]}}}
  1: {properties: {country: {const:"GB"}, system: {enum:["outward","full"]}}}
  2: {properties: {country: {const:"CA"}, system: {enum:["fsa","full"]}}}

Without required, a branch is vacuously satisfiable, because properties grades only members that are present. A document carrying no country satisfies all ten postal branches, so left-to-right returns the US class for a document that never mentioned a country. And neither case is a shape: the postal schema is a lookup table (an if/then written as an anyOf), and buy-products-request is one requirement with two locations — brand at the top level or reachable through account.

The rule, replacing the two-way split: emit branch classes only where the branches partition by requiredness into distinct, mutually exclusive field sets. Everywhere else the anyOf is a constraint, not a type — compile it.

GroupCountModel
Distinct required sets, provably disjoint34 branches / 15 schemasbranch classes
Requiredness-only, overlapping90 branches / 28 schemasone class + compiled check
No required, vacuously overlapping15 branches / 5 schemasone class + compiled check

This subsumes the awkward case rather than special-casing it: “no required” fails the partition test for the same reason “overlapping required” does. There is no partition to model.

Consequences for the commit series. Commit 4 narrows from 43 schemas to the 15 that pass the partition test; the other 28 keep one class and gain a compiled check, so the condition compiler’s jurisdiction grows from 41 root conjuncts to 41 plus those 105 branch sets — still bounded, still the same vocabulary, and no new machinery. The partition test itself is the first-order disjointness prover the design already built, so it is a reuse rather than an addition. The order-coupled dispatch channel the design conceded is removed rather than argued down: where no partition exists there is no class identity to dispatch on, which is the property the flat class had and the uniform version gave up.

Also unenforced today, and worth stating. Because the current extractor reads only required, it finds none on those 15 branches and skips the schema outright — measured for buy-products-request, whose root anyOf no generated model enforces at all. The country→system rule and the brand-location rule are enforced by nothing in the Python SDK today.

Whether the postal lookup table should exist in a protocol schema at all is a separate question, under survey; it does not change this rule, which handles the shape whatever the spec decides about the subject.
