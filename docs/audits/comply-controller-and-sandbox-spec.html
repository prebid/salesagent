1. Verdict and the decision this spec supports

Build it, in stages, and do not treat it as one deliverable.

The controller is buildable here and most of it is cheap, because the pin's contract turns out to be far more accommodating than the repo's standing note assumed. Three facts carry that:

  1. The SDK already ships the request type, all eight response arms, the 30-name scenario list, and an abstract store contract with a working dispatcher (adcp/server/test_controller.py, 1569 lines). EXECUTION
  2. list_scenarios makes support incremental and self-declaring. A seller advertises only the scenarios it implements, and the conformance runner degrades the rest to not_applicable rather than failing them.
  3. The sandbox gate is already satisfiable from data the resolver loads today. identity.account.sandbox is the persisted column, so the verification the spec demands needs no new storage and no new read path.

But two things in the brief's framing do not survive contact with the code.

  • The three reporting-core scenarios are not a time-advancement problem. They are a missing-subsystem problem. There is no reporting-obligation entity in this codebase at all — no table, no row, no persisted expected_at, no recovery deadline. git grep -n "expected_at" -- alembic/ src/core/database/ returns zero hits EXECUTION. The SDK defines ReportingObligation with ~30 fields (adcp/types/domains/core/reporting_obligation.py:46), and this seller implements none of it. So reporting_core_lifecycle_probe is not stage one; it is a separate programme behind its own decision.
  • Sandbox accounts are not merely "declared but not first-class" — the isolation is absent, and that is a live exposure today, before any controller exists. A buyer referencing a sandbox account on a GAM-configured tenant reaches real GAM. See §11.1. This is the spec's first MUST NOT and it is unenforced right now.

On the MUST NOT expose in production clause, stated up front because it is a design constraint and not a footnote.

Nothing in this spec gates on adcp_testing, anywhere. The gate's only input is accounts.sandbox — a persisted database column a deployment sets through sync_accounts or the admin UI, read off identity.account.sandbox which the resolver already hydrates from the row (§6.4). No production path branches on a test flag, so critical pattern #11 is satisfied by construction rather than by discipline. The pin independently forbids the alternative: "Sellers MUST NOT alter behavior based on these headers. Sandbox mode is determined solely by the account reference." And the clause itself is satisfied by the gate rather than by hiding the tool — the same schema says "real production endpoints accept sandbox-flagged traffic … no separate test-mode endpoint required", and the storyboard grading env runs ENVIRONMENT=production deliberately, so hiding it would hide it from the only run that grades it (§6.4).

3. What the pin requires

3.1 compliance/comply-test-controller-request.json

READING Quoted from the pinned file.

"Request payload for the comply_test_controller tool. Triggers seller-side state transitions for compliance testing. Sandbox only — sellers MUST NOT expose this tool in production. Naturally idempotent: each known scenario is either a lookup (list_scenarios) or a state-forcing operation whose target state is carried in the payload (force_*_status, simulate_*), so replays converge to the same observable state without needing an idempotency_key. The compliance harness drives this tool deterministically and does not rely on the seller's at-most-once replay cache."

  • required: ["scenario", "account"]; additionalProperties: true; x-mutates-state: true.
  • scenario is a plain string, deliberately not an enum: "'list_scenarios' discovers supported scenarios … Runners and sellers MUST accept unknown scenario strings — new scenarios may be added in additive releases."
  • params: "Scenario-specific parameters. Required for all scenarios except list_scenarios." 56 declared properties; per-scenario if/then branches in allOf impose the required subset (29 such branches).

The account field is the gate, and its description is the whole sandbox contract:

"Sandbox account assertion. The runner MUST set sandbox: true on every comply_test_controller request. The seller MUST refuse the request (returning a structured error) if the targeted account is not a sandbox account in the seller's persisted records. This field is a caller-side declaration of intent — it does not grant sandbox status; sellers verify against their own account state. The (Sandbox) verification tier is defined by this gate: real production endpoints accept sandbox-flagged traffic and process it without real-world side effects, no separate test-mode endpoint required. See spec issue #3755 and the (Sandbox) framing in #4379."

— account.sandbox, const: true: "MUST be true. The seller MUST verify the targeted account is sandbox by looking up the persisted account record, not by trusting this field. A request asserting sandbox: false schema-rejects before reaching the seller — defense-in-depth on top of the per-request gate."

That last sentence settles the production-exposure question in the spec's own words. "No separate test-mode endpoint required" means the tool ships on the normal endpoint and the gate — not the deployment — confines it. §6.4 relies on this.

3.4 docs/media-buy/advanced-topics/sandbox.mdx — the seller's duties

READING Fetched via gh api; quoted from § "Seller implementation".

"When a request references a sandbox account (either via sandbox: true in the natural key or via a sandbox account_id), agents MUST NOT persist production state or cause real-world side effects:

  • MUST NOT make real ad platform API calls (no real orders, line items, etc.)
  • MUST NOT charge real money or create real billing records
  • MUST validate inputs the same way as production (reject invalid budgets, bad dates, etc.)
  • MUST return realistic response shapes with simulated data
  • SHOULD include sandbox: true in success responses

Sandbox errors are real validation errors. If a buyer sends an invalid budget using a sandbox account, return a real error — don't simulate fake errors."

And two structural rules that bear directly on the design:

"Sandbox is account-level, not per-request. Once a request references a sandbox account, the entire request is treated as sandbox. This eliminates the risk of accidentally mixing real and test traffic in a multi-step flow."

"The X-Dry-Run, X-Test-Session-ID, and X-Mock-Time HTTP headers are deprecated … Sellers MUST NOT alter behavior based on these headers. Sandbox mode is determined solely by the account reference."

That second quote independently forbids the shape critical pattern #11 also forbids: no out-of-band test signal may steer behaviour. The account reference is the only admissible input. The spec and the repo's own rule agree, which is a convenient place to be.

5. Sandbox-account design

The half that makes the controller legal. Three pieces, in dependency order.

5.1 The gate's input — no new storage

The spec requires verification "by looking up the persisted account record, not by trusting this field". That record is already resolved onto the identity before any _impl runs: ResolvedIdentity.account (src/core/resolved_identity.py:139) is built by account_from_row (src/core/database/repositories/account_serialization.py:155, sandbox=row.sandbox at :179) from Account.sandbox (src/core/database/models.py:1166).

So the gate is one predicate over data the boundary already loaded. No new column, no new repository method, no new read. Two details that will bite:

  • NULL and false are the same key (src/core/database/models.py:1213-1216). The gate must read bool(identity.account.sandbox), never is True.
  • On the natural-key arm, ref.sandbox is used as a query filter (src/core/database/repositories/account_lookup.py:85), so a runner asserting sandbox: true by natural key selects a sandbox row rather than being verified against one. That is still spec-conformant — the row it selects is a persisted sandbox row — but the verification semantics only exist on the by-id arm. The gate must therefore read identity.account.sandbox after resolution, which is correct for both arms, rather than comparing the request field.

5.2 The isolation that does not exist — and must

This is the single largest correctness item in the whole spec, and it is independent of the controller.

READING get_adapter(identity) (src/core/helpers/adapter_helpers.py:302) decides the adapter from (AdapterConfig.adapter_type for tenant_id) or tenant.ad_server or "mock" (resolve_tenant_adapter_type, :180-206). The account is not an input — grep -n "account\|sandbox" over that file returns zero matches EXECUTION. src/adapters/google_ad_manager.py:354-700 create_media_buy has no sandbox branch and calls orders_manager.create_order(...) at :624 → order_service.createOrders([order]) (src/adapters/gam/managers/orders.py:111-113). A sandbox account on a GAM-configured tenant books a real GAM order.

The fix: the account becomes an input to adapter resolution

resolve_tenant_adapter_type is the one place the choice is made, and every production caller reaches it through get_adapter(identity), which already holds the account. The change is to resolve "mock" when bool(identity.account.sandbox), before the AdapterConfig lookup.

Why this is the right shape rather than a flag check sprinkled at call sites:

  • One owner. Eight call sites reach get_adapter (media_buy_create.py:587,1314,1366,1527,2688; media_buy_delivery.py:179; media_buy_list.py:219; media_buy_update.py:577). None of them should know about sandbox; the resolver should. This is the CLAUDE.md root-cause rule — one guard in the shared function, not one per caller.
  • Critical pattern #11 is satisfied by construction. The input is accounts.sandbox, a database column a deployment sets through sync_accounts or the admin UI. It is not adcp_testing, not an env var, not a header. A test seeds it the way it seeds any other state.
  • The spec mandates exactly this. "Sandbox mode is determined solely by the account reference."

Honest limit on the "unconstructable" ambition: routing through one resolver makes the wrong state unreachable by any current caller, which is as far as this codebase's shape allows without a larger retype (e.g. a distinct SandboxAdapter type that the live adapters cannot satisfy). It is not a type-level impossibility. I am recording that honestly rather than claiming more; a stronger version is possible later and is not needed to close the exposure.

What the mock adapter already gives you for free

src/adapters/mock_ad_server.py supports all AdCP pricing models and currencies with simulated metrics, and it already reads a per-row response override: DeliverySimulationConfig (src/core/database/models.py:2730-2770, migration 64f0fff7d954) keyed (tenant_id, media_buy_id), holding the exact wire payload, read first with in-memory fallback (src/adapters/mock_ad_server.py:1164-1185 via src/core/database/repositories/delivery_simulation.py:42-48). It deliberately has no FK to media_buys so a row can be seeded before the buy exists. This is the existing precedent for a production-code, DB-backed, per-row behaviour override seeded by a harness, and §6.5 and §7 both build on it.

6.1 The DTO

The generated Python model says account: Account | None = None (comply_test_controller_request.py:513-518), and the hand-written MCP stub also declares "required": ["scenario"] (adcp/server/mcp_tools.py:1286). Per CLAUDE.md the written spec is the authority and the SDK is a cross-check, so the DTO narrows to required. Inheriting as-is would ship a tool accepting a request the pinned schema rejects.

This narrowing needs no allowlist row, which matters because the brief forbids growing one. READING tests/unit/test_architecture_schema_inheritance.py: the NOT-WEAKER test fires on is_nullable(child) and not is_nullable(parent) (:196) and on parent.is_required() and not child.is_required() (:198). Going Account | None = None → required non-null trips neither — it strengthens on both axes — and the SHAPE test is satisfied because the child's class subclasses the parent's non-None class (:145-146). Verify by running the guard before relying on it; this is a reading of the predicate, not a measurement of the guard on the real class.

Two things the DTO must NOT do

  • Do not narrow scenario to an enum or Literal. The pin says "Runners and sellers MUST accept unknown scenario strings". The MCP stub's 31-value enum is advertisement, not validation. An unknown scenario is answered with arm 7 UNKNOWN_SCENARIO, which the corpus grades (sample_request.scenario: nonexistent_scenario, 1 step / 4 checks EXECUTION).
  • Do not retype params to a free-form dict to dodge the accepted-shape strip. See the next card — this is the one genuinely awkward interaction and it should be resolved deliberately.

params versus critical pattern #7.

EXECUTION deep_strip_to_schema (src/core/schemas/_accepted_shape.py:158-175) keeps an object's contents verbatim only when the schema declares zero properties (allows_additional and not props) — the carve-out for ext and context. The SDK's Params def declares 56 properties, so the carve-out does not apply: any params key outside those 56 is stripped, and in dev raises INVALID_REQUEST naming pointer /params/<key> (src/core/schemas/_base.py:1080-1083).

Recommendation: inherit the SDK's Params unchanged and accept the 56-key ceiling. It is the pin's own accepted shape, every parameter the 3.2.1 corpus actually sends is inside it, and a new scenario's parameter arriving with a future pin is supposed to be loud in dev — that is the mechanism working, not failing. Retyping to a bare dict[str, Any] would hit the free-form branch and pass everything through, but it deletes the dev-strictness guarantee for this tool's entire payload and should not be chosen for convenience. One scenario, reliable_reporting_managed_delivery_probe, appears to send operations (advance_within_retention, revoke_access) that may be outside the pinned Operation enum NOT ESTABLISHED — check before scoping that scenario (§12.3).

The dispatch, and why list_scenarios is derived

# src/core/tools/compliance_service.py
_HANDLERS: Mapping[str, ScenarioHandler] = {
    "simulate_delivery":      _simulate_delivery,
    "force_creative_status":  _force_creative_status,
    # ... one entry per IMPLEMENTED scenario, and no others

    return sorted(_HANDLERS)        # derived, never declared

The advertised set is the handler table's keys. It cannot drift, because there is no second list to keep in step — the same reasoning the SDK's MRO walk uses, with less machinery. A declaration would go stale silently; a derivation cannot. (The one hazard with derivations is a population that silently becomes empty — here that is harmless, because an empty table advertises nothing and every storyboard degrades to not_applicable, which is the honest answer.)

Unknown scenario → arm 7 UNKNOWN_SCENARIO. Missing required params → arm 7 INVALID_PARAMS. Entity absent → NOT_FOUND. Terminal-state transition → INVALID_TRANSITION. All in-band, no exception raised, no AdCPSalesAgentError involved.

6.4 The sandbox gate, and how pattern #11 is satisfied

def _sandbox_gate(identity: ResolvedIdentity) -> ComplyErrorResponse | None:
    """The pin: verify the PERSISTED record, never the caller's declaration."""
    account = identity.account
    if account is None or not bool(account.sandbox):   # NULL and false are one key
        return ComplyErrorResponse(
            success=False,
            error=ComplyError.FORBIDDEN,
            error_detail="Targeted account is not a sandbox account in the seller's persisted records.",
        )
    return None

Four properties, each mapping onto a stated requirement:

  • Fail-closed. No account resolved → refuse. The SDK's own gate takes the same posture ("a raising resolver DENIES", adcp/server/test_controller.py:840-863), including for a caller who omits the declaration entirely — which is scenario @T-UC-032-ext-a-prod-rejected-no-account-declaration.
  • The caller's field is never consulted. account.sandbox on the wire is Literal[True], so it carries no information — a false assertion schema-rejects before the seller sees it. The gate reads identity.account.sandbox, the DB column.
  • Critical pattern #11 is satisfied because the gate's input is a database column. Not adcp_testing, not is_production, not a header. A deployment turns sandbox accounts on with tenants.account_sandbox and creates them through sync_accounts; a test seeds the same column with a factory. There is no fork on "a suite is running", so the behaviour a scenario grades is the behaviour a deployment runs.
  • No new error subclass. Arm 7 is a response, not a raise (§3.2).

The tool ships in production, and that is the correct reading

The schema says "Sellers MUST NOT expose this tool in production", and the same schema says "real production endpoints accept sandbox-flagged traffic and process it without real-world side effects, no separate test-mode endpoint required". The second sentence defines what the first one means: exposure is the ability to affect production state, and the gate removes it. Three further facts make conditional registration the wrong answer here:

  • The storyboard grading env runs ENVIRONMENT=production deliberately — the adcp-server-storyboard service, because "a conformance storyboard grades a DEPLOYED seller, and a deployed seller runs the production boundary" (tox.ini, [testenv:storyboard]) READING. Hiding the tool in production would hide it from the only run that grades it.
  • No mechanism exists. _TOOLS is frozen into a MappingProxyType at import — "nothing may add, drop or repoint a row at runtime" (src/core/tools/registry.py:278-288) — and git grep -n "is_production" -- src/core/tools/ src/core/main.py src/a2a_server/ returns nothing EXECUTION. Conditional registration would be the first environment-varying thing in the registry.
  • An environment fork is the shape pattern #11 exists to prevent, one level up: it makes the served seller depend on which deployment served it.

7. The time-advancement seam

7.1 Where the clock lives today: nowhere coherent

EXECUTION Measured over the eleven files on the reporting path:

  • No reporting-obligation entity exists. No table, no row, no persisted expected_at, no recovery deadline. git grep -n "expected_at" -- alembic/ src/core/database/ → zero hits.
  • expected_at exists only as the computed, never-persisted wire field next_expected_at, derived from wall-clock now at emission by three mutually-unaware sites: src/services/delivery_webhook_scheduler.py:326-328 (tomorrow, hardcoded daily); src/core/tools/media_buy_delivery.py:568-572 (now + 24h, a literal unrelated to the registration's cadence); src/services/webhook_delivery_service.py:355-358 (caller-supplied interval).
  • now is read ad hoc at 16 call sites — 12 wall-clock reads plus 4 elapsed-duration reads — plus 3 independent Postgres func.now() server defaults. There is no clock abstraction, no injected now, no Clock class: git grep -n "clock\|Clock" -- src/ yields 16 hits, all text in comments, zero identifiers. freezegun appears nowhere under src/.
  • The scheduler is a bare asyncio loop (src/services/delivery_webhook_scheduler.py:79-94) with no due-date comparison at all: "due" means "no successful send logged in the last 24 wall-clock hours" (:276-294). It computes no health states — partial_data = False and unavailable_count = 0 are hardcoded with TODOs (:334-335).
  • There is no delayed, action_required, late or missed reporting-health state. The one adjacent thing, reporting_delayed (src/core/tools/media_buy_delivery.py:307-308), is driven by an in-process circuit-breaker dict (src/services/webhook_delivery_service.py:293) keyed f"{tenant_id}:{config.url}" — process-local, tenant-scoped, lost on restart, not per-obligation.

So the brief's question — "can 'now' be moved for ONE obligation without moving it globally?" — has no answer in the current code, because there is no obligation to move it for. The favourable half is that everything buyer-visible is derived on read from timestamps, with no stored health column to keep in step. The unfavourable half is that there is no row to derive from.

7.2 The seam, once an obligation row exists

The right design inverts the brief's framing, and the pinned storyboard already specifies it that way. Do not move the clock. Move the obligation's timestamps.

ReportingObligation (adcp/types/domains/core/reporting_obligation.py:46) carries expected_at as a required AwareDatetime (:82), and ReportingSchedule.delivery_sla gives the normative derivation — "expected_at equals the resolved period end plus this duration" (adcp/types/domains/core/reporting_schedule.py:51). health (:103) and production_status (:104, a local StrEnum: not_due, pending, published, failed) are fields on the same row.

Therefore:

  • operation: prepare → INSERT an obligation row with expected_at in the future, and return its identity plus its timestamps in simulated.* (the step's six context_outputs).
  • operation: advance_time, target_health: delayed → UPDATE that one row's expected_at to a past instant such that the read-time derivation yields delayed.
  • operation: advance_past_escalation → same UPDATE, further back, past the escalation window.

Why this is the correct seam rather than a clock override:

  1. It is inherently per-obligation. One row's columns change. No global state, no process-wide monkeypatching, no effect on any other caller's obligations.
  2. It needs no clock abstraction and no refactor of the 16 now sites. Those keep reading real wall-clock time; only the row's timestamps move.
  3. Pattern #11 is satisfied the same way as §6.4 — the probe's effect is rows in a table, written through a repository by a tool whose gate is a database column. No production path branches on anything.
  4. It is what the storyboard asks for. The step's context_outputs read simulated.expected_at and simulated.recovery_deadline — the runner wants the obligation's timestamps back, which only makes sense if they are the obligation's own data. A clock override would have nothing to return here.
  5. The precedent exists. DeliverySimulationConfig (§5.2) is already a production, DB-backed, per-row behaviour override seeded by the harness. This is the same shape applied to a different row.

Scope honesty: the obligation row, its repository, its migration, the expected_at derivation from delivery_sla, and the read-time health derivation are the reporting subsystem, not controller work. The controller's share of reporting_core_lifecycle_probe is nine thin handlers over a repository that does not exist yet. That ordering is why it is stage 6 (§9) and why §10 prices it separately. recovery_deadline has no SDK type at all — the nearest declared things are automated_recovery_window_seconds (adcp/types/domains/core/reporting_delivery_capabilities.py:106) and consumer_mismatch_escalation_seconds (:120) — so the deadline is derived, not stored, and stale_received_grace_deadline must be invented NOT ESTABLISHED.

8.1 What list_scenarios must advertise, and what it may decline

This is the question that makes the work incremental, and the answer is precise:

  • To stop a check skipping as missing_test_controller, the tool must exist on the wire. That gate reads only the transport's tool listing (runner.js:1135-1142) — one registry row clears it for all 221 steps at once.
  • To stop a check skipping as fixture_seed_unsupported, the specific seed_*/force_* scenario a storyboard needs must appear in the list_scenarios array. findUnsupportedSeedScenario (seeding.js:1007-1023) checks membership; a miss degrades the storyboard to not_applicable (seeding.js:1046) — still ungraded, but under a different label and, crucially, not a failure.
  • A seller may legitimately decline any scenario by omitting it. The pin's own framing: list_scenarios "discovers supported scenarios", and the query_upstream_traffic opt-in/opt-out pair is written into BR-UC-032 as two scenarios (@upstream-traffic-opt-in, @upstream-traffic-opt-out) asserting that non-advertisement produces not_applicable grading rather than failure.

That is the safety property the whole staged plan rests on: advertising only implemented scenarios converts every unimplemented one into not_applicable instead of a failure. Without it, landing stage 1 would un-skip 221 steps into red. §11.2 treats the inverse as the main delivery risk.

Stages 0–3 are the recommendation. Seventeen to twenty-nine days closes a live production-exposure bug, puts the tool on the wire, and addresses the two highest-yield scenarios (148 of the 551 corpus checks, 27%, concentrated in 25 storyboards) using machinery that already exists. Stage 4 is good value and can follow immediately. Stage 5 should be re-estimated after 4.

Stage 6 is the one to decline, on this evidence: 20–40 days for 46 checks, where ~90% of the cost is a reporting subsystem that nothing else currently asks for. If reporting obligations become a product requirement, the probe is a cheap addition to that work — but buying the subsystem to buy the probe is the wrong way round.

What this does not buy, and the brief should hear it plainly: none of these stages gets the measured passed count from ~30 to the floor's 102 on its own. The 341 controller skips are the largest single cause, but 128 not_applicable and the 19 capability_profile_mismatch signing-posture losses are separate diseases, and the floor's provenance is itself unresolved (§2.1). Stages 0–4 should be justified as conformance and correctness work with a large check yield — not as the thing that restores the floor.

11. Risks

11.1 What a sandbox account can expose today (live, pre-existing)

The brief asks what a sandbox account could expose "if isolation is wrong". It is wrong now, and the exposure is concrete: a buyer referencing a sandbox account on a GAM-configured tenant creates a real GAM order and real line items (src/adapters/gam/managers/orders.py:111-113, reached unconditionally from src/adapters/google_ad_manager.py:624,667), and the adapter calls approval at :690. The account is not an input to adapter selection at any point (§5.2). Consequences, in order of severity:

  1. Real inventory booked under a test flow. The spec's warning — "Omitting the selector from a natural key defaults to production and can book real inventory" — is about the buyer's mistake; here the seller books real inventory even when the buyer does everything right.
  2. Indirect real money. There is no billing path in this system (EXECUTION: no invoice/charge/payment/ledger table among the 41 __tablename__ values; src/core/billing_policy.py is 58 lines deciding only who pays), so the seller charges nothing. But a real GAM order is something a publisher bills on outside this system. The "MUST NOT charge real money" obligation is discharged by absence; "MUST NOT make real ad platform API calls" is not.
  3. Adding the controller multiplies it. A controller that forces states and simulates delivery against an account whose requests reach a live ad server is strictly worse than no controller. This is why stage 0 precedes stage 1 and is not optional.

Conversely, the gate's own failure mode is mild: if the gate wrongly refuses a genuine sandbox account, the controller returns FORBIDDEN and storyboards skip — visible, inert, no state touched. Fail-closed is the right default and costs little when wrong.

11.2 Landing stage 1 could redden CI (manageable, by design)

A missing_test_controller skip is ungraded and unledgerable — runner skips are never known_failures.txt entries (tests/storyboard/conftest.py:10). Un-skip a check that then fails and it becomes a real failing item with no ledger entry, which reddens CI. Stage 1 un-skips 221 steps at once.

The mitigation is the design, not a process promise: list_scenarios derived from the handler table (§6.3) means an unimplemented scenario is never advertised, so the seeding gate degrades the storyboard to not_applicable (seeding.js:1046) rather than attempting and failing it. The residual hazard is a step with requires_tool: comply_test_controller but no controller_seeding prerequisite and not marked stateful: true — such a step is attempted anyway and will fail (runner.js:2409 only cascades stateful steps). NOT ESTABLISHED — I did not count how many of the 114 requires_tool steps fall in that category. Stage 1 should begin by measuring it, and the honest fallback if the number is large is to ledger those nodeids in the same change with a reason naming the stage that will clear them.

11.3 Other risks

  • The tool becomes publicly discoverable. One registry row puts it on MCP tools/list, the A2A card, and (if rest is non-None) a REST route. That is intended (§6.4) and the gate is the control — but it means every buyer sees a comply_test_controller skill. Mitigation: rest=None, and rely on the gate. Anyone uncomfortable with the discoverability should reopen §6.4 rather than weaken the gate.
  • x-mutates-state: true with no idempotency key. The pin says the tool is "naturally idempotent … replays converge to the same observable state without needing an idempotency_key", and reads/state-forcing operations take no key (consistent with critical pattern #7's rule that reads take no idempotency key). Handlers must therefore be written as assignments ("set status to X"), never as increments. cumulative on simulate_delivery is the exception the pin itself names, and @T-UC-032-idempotent-replay grades the property.
  • Seed scenarios write real rows. seed_* creates products, creatives and accounts. Under stage 0 those live on sandbox accounts and the mock adapter, but they are rows in the real database. Mitigation: they are confined by the gate to sandbox accounts, which is exactly the pin's model — "Sandbox is account-level".
  • Pin drift. The DTO inherits the SDK's 56-property Params. An SDK bump that reshapes it changes this tool's accepted shape silently. tests/unit/test_adcp_spec_version.py catches pin drift; the per-scenario if/then requirements are not guarded locally and would be caught by the storyboard run.
  • Two sandbox semantics in one field name. On the controller's request, account.sandbox is a one-field assertion type with Literal[True]. Everywhere else in this codebase account is a reference with a natural key. Conflating them in the resolver is the most likely implementation mistake; §6.3 is where it would surface.

  1. Does ToolSpec.requires_account() key on the account field's presence/required-ness alone, or on its type? (§6.3) The controller's account is a sandbox assertion, not a resolvable reference.
