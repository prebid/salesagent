The premise (settled; not re-litigated here). format_kind is THE canonical identifier. format_id cannot be derived from format_kind — the mapping does not run that way. The seller therefore ACCEPTS BOTH and RECORDS BOTH, and OPERATES ON format_kind everywhere else: acceptance and recording are the only places format_id survives as an input; every internal comparison, lookup, filter and persistence decision keys on format_kind.

One reading note the analysis depends on, because the spec text uses "derive" in the other direction too: the migration doc's compatibility projection ("An implementation serving older 3.x peers may derive named formats from canonical declarations. Keep the projection one-way", canonical-formats-migration.mdx § Compatibility projection) is a lookup of asserted v1_format_ref[] entries riding inside an authored declaration — never a synthesis from the kind string. EXEC: at our pin, adcp.canonical_formats.project_declaration_to_v1 on a declaration carrying v1_format_ref returns exactly those references; on a canonical_formats_only: true declaration it returns []. So the premise and the spec agree: a format_id only ever exists because somebody asserted it (a buyer on a creative, a seller inside a declaration), and the seller records assertions and operates on kinds.

0. Summary — where this seller already is

The surprising finding first: the creative identity subsystem is already designed on exactly this premise, at the type and persistence layers — and no business logic consumes it yet.

  • READ CreativeFormatIdentity (src/core/schemas/_base.py:604) documents kind as "THE identity — what logic keys on and what is compared"; the Creative ORM model (src/core/database/models.py:959-983) documents format_kind as "the identity every layer shares" and the deprecated format_id as "a RETAINED BUYER ASSERTION: stored verbatim, echoed to a legacy peer, never what business logic keys on". Four columns (format_kind, format_option_ref, legacy_format_id, legacy_format_key) already record both arms, written by one mapping (src/core/database/repositories/creative.py:62-67) and read by one reader (from_row, _base.py:665-688).
  • EXEC But zero comparisons key on the kind today: git grep for comparisons on identity.kind / .kind == across src/ finds the persistence write (repositories/creative.py:62), the vocabulary membership check (_base.py:811-816), and the wire-arm chooser (wire_format_kind, _base.py:700) — and nothing else. Every comparison, filter, and gate in the seller keys on FormatKey (the canonicalized legacy (agent_url, id) pair) or on bare id strings. The documented design and the operating reality have not met.
  • READ The product side is still inverted (the audit's F4): products.format_ids is the authored, NOT NULL catalog (models.py:385) and format_options is an opaque nullable document nothing authors or derives (models.py:395, product_conversion.py:417-427). A canonical-only product cannot be served (product_conversion.py:408-414 raises on empty effective_format_ids).
  • EXEC The pin already ships the machinery this stream needs, verified by execution in this worktree's venv: adcp.canonical_formats carries validate_format_kind_in_options / FormatKindNotInClosedSetError (the per-product closed set), project_declaration_to_v1 / project_product_to_v1 (the compat projection with advisories), and project_v1_format_to_declaration / project_v1_catalog_to_v2 (the normative v1→v2 order). adcp.types.ProductFormatDeclaration is a class at this pin. The local seam for the projection already exists too: canonical_kind_for (src/core/format_resolver.py:110-172) runs the two implementable normative steps and fails closed.
  • EXEC The buyer-side canonical inputs are all accepted and echoed, never operated on: PackageRequest inherits format_ids, format_option_refs, format_kind; Package.echoing carries format_kind and format_option_refs onto the response (probed end to end through the local models); ProductFilters inherits format_kinds and format_option_refs; CreativeFilters inherits format_kinds. A git grep for readers of format_option_refs, \.format_kind on packages, formats_to_provide, formats_pending, or format_kinds across src/ returns zero operating sites.

So the work is not "introduce format_kind" — it is (a) finish the one entity where the identity exists but is unread, (b) invert the product catalog so declarations exist to key against, and (c) replace every FormatKey-keyed gate and filter with kind/declaration-keyed ones, keeping FormatKey only inside the accept/record seams. Section 2 enumerates every site; section 7 orders the work.

The critical-pattern-#4 implication of "record both"

READ CLAUDE.md pattern #4: Field(exclude=True) strips a field from the wire, from persistence AND from the idempotency hash alike — "a field that is off the wire but must persist has no spelling on a wire model" and belongs on a repository-owned carrier. The creative subsystem already answers this correctly, and the product work must copy the answer, not invent one:

  • The verbatim assertion and its comparison key are ORM columns written by the repository (legacy_format_id, legacy_format_key), never fields on a wire model. The wire model chooses its single arm via wire_format_kind.
  • So "record both" on products means: the authored declarations are the column; the derived legacy projection is either computed at the conversion edge (A3) or a repository-stamped column — in neither case a wire-model field with exclusion tricks. During the 3.x window the projection IS on the wire, so nothing needs hiding at all; the only thing that must not exist is a second authored source.
  • Idempotency: the request hash is over the buyer's document, so accepting-and-recording both arms changes no hash; a replayed create_media_buy response stored before C7 will lack formats_to_provide — a known replay-shape seam to note in C7's change, not a blocker.

5.1 Products / get_products

core/product.json, root anyOf: a "Named-format product" branch (deprecated: true, required: ["format_ids"]) XOR-ish a "Canonical-format product" branch (required: ["format_options"]). format_ids description: "Deprecated in AdCP 3.2; removed in AdCP 4.0. … Products MUST carry format_ids, format_options, or both during the 3.x migration window. New products MUST author canonical format_options[]; sellers MAY additionally project those declarations to format_ids for legacy buyers. When both fields are present they MUST describe the same underlying formats, and buyers MUST prefer format_options. Do not author a new product from format_ids alone."

This single description is the whole Group A obligation: authored canonical, derived legacy, same-formats when dual, never author legacy-first. Our state violates the last sentence for every product.

5.2 Product filters

core/product-filters.json declares format_kinds ("Filter to products accepting any of these canonical format kinds", items $ref canonical-format-kind.json, x-canonicalization: set) and format_option_refs ("Filter to products accepting any of these exact publisher- or product-scoped canonical format options", items $ref format-option-ref.json); format_ids items $ref core/format-id.json, whose agent_url description carries the canonicalize-before-compare MUST and which is "deprecated": true at 3.2.

5.3 Packages / create_media_buy & update_media_buy

core/package.json: format_kind — "Direct canonical selector supplied for this package on create_media_buy. Sellers SHOULD echo…"; format_option_refs — "Structured 3.1+ format option references… Sellers SHOULD echo…"; format_ids — deprecated, "Sellers SHOULD echo this field whenever the request included it, including dual-emission cases where format_option_refs was the winning selector"; formats_to_provide — "Immutable canonical creative contracts established for this package. We echo correctly, operate on none of the selectors, and emit only the deprecated projection (C3/C7).

5.4 Creatives / sync_creatives & list_creatives

core/creative-asset.json: root oneOf — format_id XOR format_kind, the legacy arm deprecated: true. core/format-option-ref.json: discriminator: {propertyName: "scope"}, scope required in both arms, the product arm declares "publisher_domain": false. core/creative-filters.json (list_creatives): format_ids — "Deprecated in AdCP 3.2; removed in AdCP 4.0. Filter legacy named-format creatives. Use format_kinds for canonical libraries."; format_kinds — "Filter by canonical format kinds. Returns creatives matching any supplied kind."

And the matching rules that make the bare kind insufficient as a full identity (formats.mdx § Matching and satisfaction, fetched verbatim):

"Canonical compatibility is directional. A creative capability or manifest satisfies a target only when it meets every target constraint: Exact dimensions and durations must match. A requested range must be contained within the accepted range; overlap is insufficient. Required slots must be present with compatible asset types. An exact publisher claim must match both publisher_domain and format_option_id. Equal format_kind values alone do not prove compatibility. For a product with multiple included placements, the selected format set must cover every placement. A seller must reject or refine a package with an uncovered placement; it must not silently remove inventory."

5.5 The authoring direction and the one-way projection

canonical-formats-migration.mdx: "The deprecated fields and task remain parseable during the 3.x compatibility window. They are not an alternative authoring model in 3.2: if exposed, they should be projections derived from canonical data." § Compatibility projection: "Keep the projection one-way: canonical … → deprecated named-format response. Never merge independently authored legacy constraints back into the canonical catalog. That creates two sources of truth and makes compatibility decisions ambiguous." § Completion checklist: "Preview, sync, library, and delivery paths preserve format_kind and format_option_ref."

What must NOT be attempted in one change

  • The whole inversion as a flag day — stages 1, 3, 4, 5 each change behavior a buyer can see; landing them together makes the first regression unattributable and un-revertable.
