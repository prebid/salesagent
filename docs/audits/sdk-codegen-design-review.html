Adversarial review: “Where the generator loses the schema, and where to stop it”

Review of docs/audits/sdk-codegen-design.html at 610219f44 (branch docs/sdk-codegen-design), read in full before any measurement. Every measurement below was taken in a fresh clone of adcontextprotocol/adcp-client-python at 0c7e8b86d (origin/main head at review time; 9.0.0b2, bundle schemas/cache/3.2, 1,625 schema files), in a sibling directory sa-sdk-review-clone, in an isolated virtualenv (pydantic 2.13.5, jsonschema 4.26.0, CPython 3.12.9), 2026-10-10.
EXECUTION means I ran it in that tree and the output is quoted. READING means I read source, issue text or git history and did not run it. Nothing below is inferred from the design document's own figures, and nothing is relayed from a sibling lane without independent measurement — where a lane reported a number, I re-derived it and say so.

Verdict

FAIL. The design's recommendation defers the structural fix. Its own text names the permanent mechanism, argues it is legal, and then schedules it as a fallback contingent on a signal that I measured cannot fire. That is the pattern it exists to stop.

The diagnosis is sound and better-grounded than most of what it reviews. The recommendation is not, and the reasons are measurements rather than preferences:

  • Option A's structural part covers only shapes that are not in its residue set. The twelve models that are broken today stay broken by permission.
  • Its behavioral guarantee does not execute. An existing predicate in the conformance suite classifies the entire #1414 divergence class as already-declared, so the suite stays green. It is green right now, over 41,667 documents, with the defect live.
  • Three of the four objections it raises against the permanent mechanism are refuted by code already shipped in this repository.
  • The deferral's trigger — “if the residue set grows across the next two spec bumps” — is unobservable for the same reason as the second point.
  • One of the supports for deferring does not exist: the containment the triage lane reported (revalidate_instances="subclass-instances") is absent from main, was added and then removed on branches that never merged, and the pass-through it was said to close is live.

An unconstructible design does exist. It is one change with two parts, specified in §1, and it dissolves all four issues plus the two defects the sibling lanes found, because all six are consequences of one arrangement.

Amended after writing (§1.3): the dropped arm conditions turn out to be cheaply expressible in ordinary pydantic logic, so #1414 can be closed without schema delegation. That narrows Part A from “the only possible fix” to “the only fix that makes the class unconstructible,” and it strengthens the FAIL — the residue set's justification was that these conditions are hard, and they are not.

1. Is there a design that makes this class of defect unconstructible?

Yes. Finding it requires asking what is common to the six observed defects rather than what fixes each, so this section starts there.

1.1 The arrangement that produces all six

The SDK holds three artifacts in a specific relationship:

  1. the bundled JSON Schema, which docs/validation-contract.md declares the authority;
  2. a generated pydantic tree, produced by a pinned generator plus a 7,522-line post-processor that writes behavior into generated Python source (EXECUTION wc -l scripts/post_generate_fixes.py → 7522);
  3. a 1,173-line hand-written canonical layer that inherits from (2) in order to receive what the post-processor wrote.

READING CanonicalBoundaryModel's docstring (canonical_creative.py:491) states the dependency in the first sentence:

“Every canonical model is a real subclass of the generated wire model it refines, so each one inherits the generated model's fields, its injected model_validators, and its envelope ancestry.”

Every one of the six defects follows from “behavior is delivered as source injected into a generated class.” Delivering a rule as source means expressing it in Python; what cannot be expressed is dropped. Receiving a rule means inheriting, which means subtyping.

1.2 The design

Part A — Rules are evaluated from the schema, never transcribed into source. A model that corresponds to a schema node carries that node's identity as a class constant (tool + direction, or bundle + pointer). One @model_validator(mode="after"), written once in src/adcp/types/base.py, evaluates the node's composition keywords against the document through adcp.validation.schema_loader. The post-processor's job for composition rules becomes writing one constant — a copy, not a derivation.

Part B — The canonical layer is generated from the same schema minus a declared omission set, not hand-written as a subclass of the wire model. It declares the same schema identity and its own fields. It receives the same rules by naming the same schema, not by inheriting a method.

They are one change with an order: B is only possible once A holds, because inheritance is currently the only delivery route for the injected rules.

What becomes unconstructible, and what does not

Defect classAfter A+BBy what
An emitted rule weaker than its schema keyword UNCONSTRUCTIBLE There is no emitted rule. The keyword is evaluated where it is written. Nothing transcribes, so nothing can transcribe partially — and there is no remainder, so no residue set and no third hand-maintained allowlist.
A tolerant model that isinstance-passes as a strict one UNCONSTRUCTIBLE The lattice stops claiming it. Enforced by the type system, not by a pydantic config that has to be remembered — which is #1397's “honest lattice” direction, and the cost that direction had ("the inheritance that currently carries every injected validator would need another route") is paid by Part A, which IS the other route.
A redeclaration silently dropping an inherited constraint UNCONSTRUCTIBLE No inheritance from the wire model, so no inherited constraint exists to drop. The five sites stop being redeclarations and become first declarations, generated.
A positional name whose meaning can move UNCONSTRUCTIBLE Independent of A+B: the design's Option D is already structurally correct as written. union_arm_names.py derives the name from title, discriminator const, or required set, and raises UnnameableArmError otherwise. Derived-or-refused cannot be positional. It only needs wiring.
A canonical field declared weaker than its schema at the field level DETECTED, not prevented — unless B generates the fields This is the honest limit. If the canonical layer stays hand-written, A catches a field-level narrowing loss at validate time but does not prevent it. Generating the layer from the schema with a declared omission set is what closes it, and is why B says "generated", not "hand-written but careful".

The one-line test of whether this is structural or corrective: after A, ask “what would a future spec version have to contain for the projection to drop it silently?” There is no answer, because there is no projection. After Option A as the design recommends it, the answer is “any arm condition whose shape is not not.required or a sibling const” — and a human decides whether it goes in the residue or fails the build.

Precedent: Part A is already shipped in this repository

READING src/adcp/types/versioned.py:353, _VersionedExtensionModel._validate_schema_document — on a field-based pydantic model built by create_model: 

def _protocol_payload(self) -> dict[str, Any]:

@model_validator(mode="after")
def _validate_schema_document(self) -> _VersionedExtensionModel:
    validator = get_validator(self.schema_tool_name, self.schema_direction,
                              version=self.schema_version)
    ...
    issues = sorted(validator.iter_errors(self._protocol_payload()),
                    key=lambda error: list(error.path))

The class carries its schema identity as ClassVars (schema_tool_name, schema_direction, schema_version, schema_document); one validator evaluates it; the jsonschema error is rendered as path: message and raised as a ValueError that pydantic wraps into an ordinary field-level ValidationError. Part A is this mechanism, applied to the pinned tree instead of the negotiated-version tree.

The honest limit on the precedent: VersionedSchemaModel's docstring scopes it — “intended for boundary validation and schema generation, not as a base class for adopter-defined models.” So it does not authorize Part A by itself. It does remove three of the four objections the design gave for ruling it out (§4).

1.3 Amendment: the dropped conditions are expressible, which narrows Part A's premise

Added after the sections above were written, on a measurement reported by a sibling lane and not re-derived by me — marked accordingly.

A subsequent experiment hand-patched CreateMediaBuyRequest with every dropped arm condition written out as ordinary pydantic boolean logic. Reported result: nine parity cases green, and the cost within noise of the baseline (+0.9µs / −0.7µs against my 64µs figure for schema evaluation). I did not re-run it.

If that holds, my reasoning above overstated one thing. I wrote that not, const and nested allOf “have no cheap transcription” and that “transcription is lossy by construction.” That is wrong as stated for this schema: the conditions were transcribable, cheaply. The accurate claim is narrower and still holds — nothing forces a transcription to be complete. The extractor reads one key per arm because that is what it was written to read; the loss is a choice, not a ceiling.

What this changes, and what it does not:

  • Part A is no longer needed to fix this bug. If the twelve models' conditions can be expressed at no cost, express them. The defect closes without schema delegation, and the cost objection in §2 stops applying to the fix at all.
  • Part A remains the only thing that makes the class unconstructible. A hand-expressed boolean is complete today and silently incomplete the next time a spec version adds a keyword shape nobody transcribes — which is the same failure, one bump later, and the reason §6.1 matters regardless. So Part A becomes a question about the class rather than about this bug, and the user may reasonably decide the class is worth less than the cost.
  • The FAIL verdict stands, and gets stronger. The design's recommendation was a residue set re-admitting the twelve present defects. If those conditions are expressible at negligible cost, a ledger that tolerates them has no remaining justification — the argument for the residue rested on the conditions being hard, and they are not.
  • Part B and the ordering constraint are untouched. They rest on the canonical layer's inheritance being the delivery route for injected validators (§3), which this measurement does not bear on. The ordering constraint survives in a modified form: Part B still needs some route other than inheritance, and a hand-expressed boolean on the generated class is still delivered by inheritance. So Part B still cannot precede a change to how rules reach the canonical layer.

Honest note on how this correction arose: it was found by someone trying the cheap thing I had argued past. My claim about expressibility was an inference from the extractor's docstring (“those narrow an arm further”) and the design's framing, not a measurement — and it is the one load in this review I asserted without running anything.

Four readings, because they do not all point the same way:

  • The expensive half is the dump, not the check. Keyword construction is 168 + 64 = 232µs; model_validate-from-document is 64µs because the document already exists.
  • It does not justify the deferral. A deferral trades a known defect for a measured cost; it needs the cost to be unacceptable, and 64µs against a 548µs per-call baseline that the same document mandates is not an argument the design made — it used an adjective.

Unexplored lever, stated as unmeasured: a compiled validator (fastjsonschema-style codegen) over the arms-only subschema would plausibly cut the 64µs substantially. Not installed in this tree, so I did not measure it, and it is a new dependency.

3. Why does a hand-written canonical layer subclass generated models at all?

Because validator injection has no other delivery mechanism. That is the whole reason, it is stated in the code, and it is the same root cause as #1414.

3.1 The stated reason, and what it costs

READING The arrangement is class Canonical(GeneratedWireModel, CanonicalBoundaryModel), with CanonicalBoundaryModel listed last so its model_config wins. Its docstring gives the purpose: inherit “the generated model's fields, its injected model_validators, and its envelope ancestry,” and notes that two concerns “used to be re-attached per class by create_model” and are now inherited instead. The repo's refusals section confirms the history from the other side: “When an injected validator failed to reach the public canonical models, the fix was to delete the runtime copies so inheritance carries it.”

So the subclassing is not an independent modelling decision anyone made about creatives. It is the delivery mechanism for post-processor output. The layer wants the rules and is obliged to take the type relationship to get them.

And it does not want that relationship. READING _DeliveryCreativeManifest's own docstring says it is “deliberately not a subtype of the strict input” while being exactly that subtype. Then __pydantic_init_subclass__ deletes the unwanted inherited fields from model_fields and binds each name as a class attribute holding None — necessary, per its own docstring, because an inherited injected validator (_validate_format_reference_xor) reads the removed field and raised AttributeError when it was merely deleted. A hack that exists to repair an inheritance taken to receive a rule, which is three mechanisms deep into working around the first one.

3.4 So: is the arrangement right?

No, and the reason is not aesthetic. The layer takes a type relationship it documents as unwanted, in order to obtain rules, and then spends three mechanisms undoing the relationship's side effects — field deletion, attribute rebinding, and (on the unmerged branches) a revalidate_instances config. Each of those is a place a future defect lands. Part B removes the reason to take the relationship, which removes all three mechanisms rather than hardening them.

One sub-question I am explicitly not re-opening, per the instruction and because I independently confirm the finding: deriving the canonical/legacy split from the schema's deprecated markers fails in both directions, so is_legacy_creative_identity_key (canonical_creative.py:317, over the three-key regex at :253) stays the single hand-owned selector. READING the repository's own design text already makes it the one predicate shared by the input validator, the schema sanitizer, the serializer and the field removal — so the selector is already single-owner; it is simply not keyed on deprecation, and should not be. Part B does not change it: an omission set is what that predicate already computes.

6. Two measurements the design's recommendation rests on

6.1 The behavioral guarantee does not execute

EXECUTION:

create_media_buy graded? True

Divergence(tool='create_media_buy', pointer='/packages/0/budget', mutation='<removed>',
           direction='the model accepts a document the bundled schema refuses',
           keyword='anyOf', message='anyOf composition failed', schema_path='#/anyOf',

DECLARED["union_arm_absorbs_a_type_error"] is lambda d: d.direction == MODEL_ACCEPTS and d.keyword in ("oneOf", "anyOf"), and the jsonschema keyword that refuses a branch-membership failure is anyOf. So the predicate covers every root-composition divergence regardless of cause. Three consequences, and all three survive under any option:

  • Adding the field-removal mutations does not surface #1414. The suite stays green.
  • No residue set is ever graded behaviorally while that predicate stands.
  • The stale-entry test will never retire it, because it keeps matching the real type-absorption divergences it was written for — a correct entry that is also too coarse.

The suite's present state is the plainest form of the point. EXECUTION, driving its own grading machinery over every graded tool on 0c7e8b86d: 41,667 documents compared, 1,744 divergences, zero undeclared — the suite is green — while CreateMediaBuyRequest accepts a document its own bundled schema refuses. union_arm_absorbs_a_type_error matched 73 of the 1,744.

This is a finding about the instrument and it is independent of the verdict: narrowing that predicate is worth doing on its own merits, before and regardless of any design decision, because until it discriminates, the parity suite's green is not evidence about root composition.

A three-field document. The projection, its docstring, its PR text and its test all agree with each other and all disagree with the schema. Nothing was missing that a check could have supplied; the check, its author and its test shared one reading of what the keyword meant. Widening 3 will be written and tested by whoever holds that same reading of the next keyword — which is the argument against scheduling the structural fix behind it, independent of how good widening 3 is.

Stated fairly against myself: 110 commits have landed since v8.0.0 and at least seven carry ! on codegen or types. These maintainers do land structural rewrites. “Patches never hold here” is too strong as a general claim about this repository; it is established for this one mechanism, where the evidence is six days old.

8. Recommendation

Reject the recommendation. Delete the projection rather than widen it, and remove the canonical layer's reason to subclass. Both are specified in §1.2. The design's Option D for #1409 stands as written and needs no change beyond the corrected count.

Landing order, with the reason each step precedes the next:

  1. Narrow DECLARED["union_arm_absorbs_a_type_error"] and fire-probe it red. First, because it is the measurement instrument and it currently returns the wrong answer for the defect under discussion. Worth doing whatever is decided about the rest.
  2. Add field-removal mutations to the parity corpus. With step 1 done this makes the whole class visible; without step 1 it changes nothing.
  3. Part A. enforce_root_required_groups stops deriving anything: it writes the model's schema identity as a ClassVar, and one @model_validator(mode="after") in base.py evaluates the root composition through schema_loader. Delete the extractor, the emitter's tuple rendering, and the plan for a residue set. versioned.py is the shape to copy.
  4. Part B. The canonical layer declares its own fields and the same schema identity instead of inheriting the wire model. The 12 field-dropping subtypes stop being subtypes; __pydantic_init_subclass__'s deletion-and-rebinding is deleted; the five dropped constraints become first declarations generated from the schema; revalidate_instances is not needed in any branch.
  5. Option D, wiring the existing naming rule, with 39 renames behind the deprecation shim that adcp.types.__getattr__ already implements for one name.

Steps 1–2 are independent and small. Step 3 is the fix. Step 4 is the larger piece and is the one a maintainer may reasonably stage — but staging step 4 after step 3 is not deferring a structural fix, because step 3 is what makes step 4 possible and step 3 alone closes #1414.

The strongest argument against this recommendation.

Part B undoes an inheritance that landed six days ago. #1392 deleted the derived .pyi and made canonical models real subclasses precisely so injected validators would reach them, and that fixed a live defect. Proposing to remove the inheritance immediately afterwards asks the maintainers to reverse a recent, deliberate, correctness-motivated decision — and the repo's own refusals section warns against exactly this shape of churn (“this entry exists so it is not proposed a third time”).

My answer, and I think it holds: Part A removes the need for #1392's fix rather than reversing it. #1392 solved “injected validators do not reach the canonical models”; under Part A there are no injected validators to reach. But this is a sequencing argument, and if Part A is not taken, Part B is a regression and should not be done on its own.

The cost objection also stands on its own: 64–69µs does not amortize, is a 7.6× slowdown on small-document validation, and cannot be turned off with ValidationHookConfig because it lives inside the model. The maintainer who put defer_build=True on AdCPBaseModel to control model cost manages that dimension actively. A sharper form: carrying the arms means carrying their $ref graph, so Part A resolves to “read the bundled schema at validation time” — which makes model correctness depend on the shipped bundle's layout, where the projection did not.

If the cost objection is taken, the fallback is not the design as written. It is steps 1–2 plus a refusal with no residue: generation fails on any arm condition the projection cannot express, and the twelve affected schemas are fixed upstream or the build stays red. That is detection plus a hard stop, which is weaker than Part A and honest about being weaker. The design's version — a residue set that re-admits the twelve, graded by a suite that cannot see them — is the one shape I would not accept.
