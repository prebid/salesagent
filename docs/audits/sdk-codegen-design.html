Where the generator loses the schema, and where to stop it: a design analysis of adcp type generation

Measured against adcontextprotocol/adcp-client-python at 0c7e8b86d (v9.0.0-beta.2, spec bundle 3.2), fresh clone, editable install, 2026-10-10. Issues read in full with comments: #1409, #1414, #1362, #1359, #1366 (closed). This is a design document; it proposes no code.

1. The state of play moved before this analysis started

The four issues were filed against 8.0.0/9.0.0. Between filing and now, three pull requests merged (Oct 4–6) that resolve or reframe most of the ground:

2. The root-cause hypothesis, tested

The hypothesis: generation is lossy at the schema node and the loss is silent; all four issues are that one defect. Tested mechanism by mechanism:

IssueVerdictThe mechanism, located
#1409HOLDS Identity loss, silent. The response-variant renderer names arms f"{base}{index}"; the node's title/const/required are never consulted for the name. The repo carries three compensations that each prove the fragility: a patched rglob (run_datamodel_codegen.py) so filesystem order cannot renumber classes; the hardcoded BuildCreativeResponse permutation so an upstream insertion did not move two public names; and restore_format_asset_numbered_aliases, which re-points the stale positional name Assets94 by locating the class through its discriminator const — node identity used to prop up positional identity.
#1414HOLDS Constraint loss, silent, in two cooperating passes. Pre-generation, flatten_root_object_validation_union (hand-listed 8 schemas) deletes the root anyOf so one subclassable model is generated. Post-generation, enforce_root_required_groups re-reads the original schema — and its extractor _root_required_groups keeps only each arm's top-level required, discarding not, const and nested allOf by documented choice (its docstring: "those narrow an arm further and are not part of its group"). The emitted validator is more permissive than the schema, and nothing records the difference.
#1362HOLDS, DIFFERENT MECHANISM Not discard but invention: a pointer into a structural position has no name, so the generator minted one and wrapped the selected type. The fix that merged (#1371) is instructive because it is neither a validator nor a guard: it classifies the pointer and eliminates the wrapper before generation, so the wrong type is never constructed. The loss-shape is "origin discarded", cousin to #1409's "identity discarded".
#1359BREAKS An aggregate observable, not a mechanism — and its largest measured component runs the opposite direction. Of 5,995 divergences, 4,604 were schema-accepts-model-refuses, dominated by the bundled runtime validator silently skipping format: uri (8,580 occurrences in the bundle; a bare FormatChecker() enforces none) while the generated models enforce it as AnyUrl. There generation was faithful and the schema-side runtime was the lossy artifact. The coercion class ("yes" → True) is not a dropped keyword either: the keyword was expressed, into a carrier type whose semantics are wider. Only the optional-vs-nullable conflation and the conditional-subschema class are generation loss.
Verdict: the hypothesis holds for two of the four and names a real family, but the four issues are not one defect. The accurate grouping: #1409 and #1414 are the same defect (a schema-node keyword that cannot be expressed is silently projected away — identity to a position, a branch condition to a presence check); #1362 was the sibling defect (a nameless position silently given an invented type), already fixed by elimination; #1359 is a symptom aggregate with at least four causes, two of which are not generation defects at all. "Express the keyword or refuse" is the right invariant for the first family. It would have done nothing for the bundled validator's missing format checkers, which is a caution against treating it as the one principle the SDK needs.

2.1 One more measurement: why the parity suite did not catch #1414

#1375's conformance suite is exactly the "derived on both sides" test the hypothesis asks for — it enumerates the bundle, synthesizes, mutates, and requires every divergence to fall into a declared cause class. But its MUTATIONS tuple replaces one leaf value at a time with a value of a different JSON type. It never removes a field. Branch membership in an anyOf is decided by which fields are present, so the entire #1414 class of divergence — a document that satisfies no branch because of what it omits — is structurally outside the corpus. The suite's six UNREACHABLE tools (whose required sets live inside composition branches) are the same blindness seen from the synthesis side. Any fix for #1414 that does not also close this corpus hole is a fix the suite cannot defend.

3. Constraints the repository has already settled

These are documented in docs/design/type-generation.md ("What this architecture refuses") and in merged decisions; a design that ignores them will be rejected upstream:

  • The generator is pinned forever. datamodel-code-generator 0.64.0; 0.72.0+ cannot generate the tree (measured: multi-arm allOf ref resolution), 0.71.0 drops 44 const defaults and three discriminators (measured). Every mechanism must be a schema transform, a post-generation pass, or hand-written source inheriting generated output.
  • #1102 settled the two-artifact boundary: pydantic models are structural application types; the bundled schema run at the wire is the conformance authority. AdCPBaseModel's docstring states it. Full model–schema parity was explicitly declined.
  • No hand-maintained allowlists that can grow; derived or shrink-only sets only. The repo already practices this: the effect manifest (every post-fix records whether it changed the tree, no-ops must say why), DECLARED divergence classes, UNREACHABLE/UNMODELLED shrink-only sets.
  • No positional name on the public surface (stated refusal), while renaming 1,127 module-internal numbered classes as a gate is also refused as beautification.
  • Refusal is an accepted tool here. _has_bare_ref_root_arm raises; transforms carry explicit refusal ceilings; a fix that cannot find its target must raise. The "express or refuse" posture is not foreign — it is the house style, applied unevenly.

4. Design options

Option A — Widen the projection to the measured shapes, and refuse beyond them

For #1414. Three coordinated changes, all in the existing pipeline:

  1. _root_required_groups returns, per arm, the required group plus the arm's exclusions (not: {required: [...]} and not: {anyOf: [{required}...]} — the two shapes that occur in the 12 affected models) plus sibling const discriminators where present. enforce_root_required_groups emits them: an arm matches only if its group is present and none of its excluded fields are.
  2. The refusal: after extracting what step 1 can express, anything left over in an arm (a nested allOf item constraint like packages.items requiring budget; a cross-file conditional) must either appear in a shrink-only residue set naming schema + JSON pointer + keyword, or generation fails. Exactly the manifest pattern the repo already runs for fix effects, applied to arm conditions. A spec bump that introduces a new unexpressible condition shape goes red instead of silently narrowing the contract.
  3. Close the corpus hole: add field-removal mutations to the parity suite (delete one optional leaf at a time from the synthesized payload), so branch-membership divergence is graded over the whole bundle. This is what keeps the residue set honest from the behavioral side: an entry that stops being a real divergence shows up as removable; a divergence with no entry fails the suite.

What it makes impossible: a new dropped branch condition arriving silently (build fails or the residue names it); the suite going green over a model that accepts branch-violating documents. What it deliberately does not do: express nested allOf item constraints in the root validator. Those belong on the item's own model or in the residue — the triage reached the same line, for the same reason (expressing them means traversing $ref chains across generated files in a text-rewriting post-processor).

Cost: moderate. The extractor and emitter change together; ~12 models regenerate; the residue set is seeded with today's leftovers (on this bundle: the packages.items constraints and the budget_allocation.mode consts that step 1's const handling doesn't reach, if any); one enforce_root_required_groups early-return (already += 1) must become strip-and-reinject so existing incomplete validators update. How it lands: a 3–4 commit series, each leaving the tree coherent, along the exact scope the maintainer's triage already endorsed ("ready-to-implement", with the extension to not.required named). Lowest acceptance risk of any option.

Option B — Delegate root composition to the bundled schema at validation time

Instead of projecting keywords into pydantic, emit one model_validator that evaluates the original root anyOf/oneOf subschema — through the compiled-validator machinery the package already ships in adcp.validation — against the document under validation. Zero keyword loss for root compositions, by construction, forever.

What it makes impossible: every divergence class between the model and its root composition, including ones no one has thought of, with no per-keyword code and no residue set. Feasibility note that surprised me: layering does not forbid it — adcp.types already imports from adcp.validation in four modules (versioned.py, aliases.py, …), and the reverse direction is clean.

Cost, and why it loses: (1) it re-litigates #1102 — the settled decision is that models are structural and the schema is the conformance authority at the wire; moving schema evaluation into every model_validate call makes the model a second wire boundary, and the client already runs the schema hook on every call. (2) The validator needs a JSON document to grade, so the model must re-serialize itself (or retain the raw input) inside validation — construction cost on every instantiation, including server-internal ones that never touch a wire. (3) Failures surface as jsonschema pointer paths, not pydantic field errors, splitting the error vocabulary adopters see. (4) For construction (keyword arguments, not parsing), the document doesn't exist yet; the delegate would grade a round-trip of itself, which can mask author errors the projection would catch field-by-field. A permanent-fidelity mechanism that the architecture's own boundary decision argues against is not the right trade here.

Option C — Delete the root-group validator; the model carries structure only

The purist reading of #1102: a partial validator misleads, so emit none; conformance questions go to the bundled validator, which is the declared authority anyway.

What it makes impossible: a misleading partial check (nothing partial exists). Why it loses: it regresses live protection — the no-packages-no-budget-no-proposal document would then pass the model with no complaint, and the measured downstream failure (#1414's BUDGET_TOO_LOW for a budgetless request) returns for every adopter that parses with models and runs the schema in default warn mode. The maintainer already chose to have the validator. Stated for completeness because "express or refuse" taken literally endorses it; the right granularity for the invariant is the emitted check (it must say what it does and do what the arm says, with the remainder recorded), not the model.

Option D — Wire the union-arm naming rule (for #1409; composes with any of A–C)

The rule exists, is measured over all 557 root-level non-null arms of the pinned bundle (169 named by title, 82 by discriminator const, 27 by required set, 278 create no class, 1 refused), and fails closed with UnnameableArmError. Wiring it is the one-line swap at class_names plus the two decisions the issue names:

  • The one unnameable arm (get-content-standards-response.json oneOf[0], no title): take it off the flat surface and leave it reachable by domain path until adcontextprotocol/adcp#7913 lands a title. That is the repo's own "degraded honestly" pattern, and it avoids holding the wiring hostage to an upstream edit.
  • The 38 public numeric-suffixed names: breaking rename behind deprecation aliases (old name assigns to new class, warns on import/access — the Assets94 fix is the existing precedent, generalized and then deleted). The timing argument is now: the repo is inside a 9.0.0 beta window; a rename that ships in 9.0.0 final costs one migration table; the same rename after 9.0 settles costs a 10.0.

What it makes impossible: a schema insertion or reorder silently changing which node a public name means. The hardcoded BuildCreativeResponse permutation and the Assets94 re-pointing fix both become deletions — they exist only to compensate positional identity. Cost: the deprecation shim and migration table; a generated-tree test (the branch's test grades schemas, not output — the issue itself flags this). How it lands: after the residue decision, as its own PR; the maintainer's triage already sequenced it (blocked on #1392, which has merged).

Sub-question: should the canonical/legacy split derive from the schema's deprecated markers?

No for selection; yes for closure. Measured: deprecated: true does propagate (Product.format_ids carries deprecated and warns; 194 deprecated=True field occurrences in the domains tree) — but the bundle declares 363 deprecated top-level properties, and the effect manifest records that the metadata pass cannot reach 282 of them (hyphenated-directory module mapping). Two consequences: the marker is far wider than the legacy-creative-identity concept (deprecation marks many things that stay on canonical models), and its propagation is incomplete, so deriving the strip set from it would both over-select and under-select. The split's actual selector is a three-key regex (_LEGACY_IDENTITY_KEY = r"(^|_)(?:format_ids?|v1_format_ref)($|_)", canonical_creative.py:253). The improvement that fits the house rule ("derive, don't declare") is a closure test, not a derived selector: the set of bundle property names the regex matches must equal the set of properties whose subschema references the deprecated identity schemas (format-id.json and kin). The rule stays readable and hand-owned; a bump that adds a fourth legacy identity key or retires one goes red.

Sub-question: can a consumer that walks type annotations be made safe, rather than warned?

Python cannot forbid introspection, so "make it impossible" has to mean make the annotations stop lying, not fence the reader. The three lies are: an invented wrapper type (#1362 — eliminated at the source by #1371, 87 wrappers remaining with unwrap passes trending down), a positional name whose meaning can move (#1409 — Option D removes it from the public surface), and a validator annotation that implies a contract narrower than the model enforces (#1414 — Option A plus the residue makes the gap enumerable). What remains structurally inexpressible — conditionals, the open format_kind vocabulary — is invisible in annotations under any design, which is why the declared-divergence set and the wire-side schema hook are the correct home for it, exactly as #1102 decided. There is no fourth mechanism to invent here; there is finishing the three.

5. Recommendation

Option A for #1414, Option D for #1409, as two independent commit series, in that order of urgency. Concretely: extend the group extractor to exclusions and sibling consts; make everything an arm carries beyond that either a build failure or a pointer-named entry in a shrink-only residue; add field-removal mutations to the conformance corpus so the residue is graded behaviorally; then wire the existing naming rule with the unnameable arm demoted to its domain path and the 38 renames shipped behind deprecation aliases inside the 9.0 beta window.

This is a change of kind, not of volume: today the pipeline's posture is "express what fits a field declaration, drop the rest silently"; after it, the posture is "express what the measured shapes cover, and every drop is either impossible or has a name and a test that notices when it stops being true." That is the hypothesis's invariant, applied at the granularity where it is real — the emitted check and the emitted name — rather than at the slogan level, where it would also demand Option C's regression or Option B's re-litigation of a settled boundary.

The strongest argument against this recommendation: it is the third widening of the same projection (plain required groups → this PR's exclusions-and-consts → whatever the next spec version carries), and each widening re-opens "what is expressible" by hand, in a 7,500-line post-processor that is already the most fragile artifact in the repo. Option B ends the class permanently, needs no residue bookkeeping, and the layering it requires already exists. The honest reply is that B's cost lands on every model construction forever and contradicts a decision the maintainers made deliberately and recently (#1102) — but if the residue set grows across the next two spec bumps instead of shrinking, that is the signal the projection approach has lost, and B (scoped to model_validate-from-document paths only, not keyword construction) is the fallback this document would then argue for.
