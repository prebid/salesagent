The six that matter, in full

#1414 — our workaround has a hole, and #1359 is the hole

We restate the three create-media-buy-request.json anyOf branches by hand in _check_anyof_branch_conditions (src/core/schemas/_base.py:2818–2898), because the generated _require_schema_required_group tests only top-level field presence. The restatement uses model_fields_set as its requiredness test, and its docstring states the convention plainly: a supplied field counts even when explicitly null.

That convention is what reopens the defect. Measured on the pin:

packages[0] = {"product_id": "prod_1", "pricing_option_id": "cpm_usd_fixed", "budget": null}

our CreateMediaBuyRequest     -> ACCEPTED
get_total_budget()            -> 0
jsonschema Draft7 over
  _schemas/3.2/media-buy/create-media-buy-request.json
                              -> 2 errors ("None is not of type 'number'", plus the anyOf)

same document with the "budget" key removed entirely
our CreateMediaBuyRequest     -> refused: "matches no accepted shape"   (workaround live)

So the absent-key case is closed and the explicit-null case is open, on the same branch, through the same validator. Downstream the behaviour is exactly what #1414 describes: the budget floor receives 0 and answers BUDGET_TOO_LOW for a request that supplied no budget. The fix is one predicate — treat a field whose value is None as not-sent for a branch test wherever the schema's declared type excludes null.

Cross-cutting question 1 — is the codegen cluster one defect?

Four of the five are one defect. #1397 is not.

The shared root cause: generation is lossy at the schema node, and the loss is silent. The generator renders each node into what pydantic can carry on a field declaration and discards every keyword that does not fit, leaving no record that anything was dropped. Each of the four is one class of discarded keyword:

  • #1409 drops the node's identity — title, the discriminator const, the required set — and substitutes its ordinal.
  • #1362 drops the node's origin — a pointer selects a type, and the generator treats it as a position needing a name, minting a wrapper per referencing site.
  • #1414 drops the node's sibling conditions — nested required, allOf, not, const inside an anyOf branch — keeping only the branch's top-level required.
  • #1359's codegen half drops adjacent constraints: a pattern beside a format: uri, and the absent/null distinction that required plus the declared type together express.

The fix shape is also single, and #1409 is already written in it: express the keyword or refuse. union_arm_names.py raises UnnameableArmError rather than falling back to a number, which is exactly what #1414 asks for in its own words — "raise at import time or emit a documented gap, rather than silently narrow the contract". Asking upstream for one generator invariant ("no schema keyword is discarded without a recorded gap") reframes four issues as one, and gives a test that cannot go stale: enumerate the keywords in the bundle, subtract the keywords the generator can express, and require the remainder to be a declared, shrinking list.

#1397 is a different thing. It is about canonical_creative.py, which is hand-written, not generated: a deliberate API-design choice to make a tolerant boundary model subtype a strict wire model. No keyword is lost. Its second axis — the top-level export not being the annotated class — is a naming question that rhymes with #1409 without sharing its mechanism, and on our pin (above) it has already moved. Grouping it with the four would hand upstream a bundle it cannot act on as one.

The shape of dependence we should not be taking. All five issues are the generator losing structure; our exposure to them is a function of how deep into a generated annotation we read. That gradient is measurable, and it is sharper than "values are safe, annotations are exposed":

across the 1316 models reachable from src.core.schemas

field.annotation retaining a TOP-LEVEL Annotated        2      pydantic strips it into .metadata
field annotations carrying a NESTED Annotated        2867      pydantic does NOT strip these

So the top of field.annotation sits in a zone pydantic normalizes for us, and anything read inside it does not. That is the actual dividing line, and it explains both outcomes exactly: _known_asset_types() reads inside the annotation and was silently killed by a Discriminator the SDK added; the required-nullable rule at _base.py:878 reads only the top level and is correct. Reading a generated annotation is not the error — reading through it is. Stated as "walk no annotations", the rule would condemn a correct site and still permit a __pydantic_core_schema__ walk that is strictly more fragile.

Cross-cutting question 2 — what makes the empty-derivation failure mode unconstructible?

Not a check. A guard over _known_asset_types() would catch this instance of an empty derivation and nothing adjacent to it, because the set of ways to write a traversal wrong is not finite. The question is what authority already knows each answer, and whether asking it removes the derivation or only shrinks it.

First: the proposed answer does not work, and measuring why is what finds the real bug

The suggested fix is a TypeAdapter over the discriminated union, on the ground that "is this asset_type one the pin models?" is a validation question the model answers by accepting or raising. The union has a catch-all arm, so it never raises:

Format.model_validate({... "assets": [{"asset_type": "hologram", ...}]})   -> SUCCEEDS
  arm class: adcp.types.aliases.UnknownFormatAsset
  asset_type value: "hologram"

EXECUTION Accept-or-raise answers "accept" for every unmodelled asset type, so it cannot answer the question that was asked. The premise that pydantic already holds the mapping is nonetheless correct — it is reachable, and it is a trap:

Format.__pydantic_core_schema__ -> tagged-union, choices.keys() =
  ['_unknown','audio','brief','catalog','css','daast','html','image','javascript',
   'markdown','repeatable_group','text','url','vast','video','webhook']

EXECUTION That is the vocabulary the hand-walk is trying to rediscover, and reading it would be a deeper structure read — into a private dunder, still needing _unknown subtracted by hand. It is the route that looks like the fix and is the same class of dependence.

The form that works is narrower than either: ask the validated instance which arm it landed in.

isinstance(asset, UnknownFormatAsset)      asset_type=image  -> False
                                           asset_type=video  -> False
                                           asset_type=hologram -> True

EXECUTION UnknownFormatAsset is importable by name from adcp.types.aliases, so a rename is an ImportError at import, not a set that quietly empties. There is no derived vocabulary, nothing to traverse, and no Discriminator the SDK can add next release that changes the answer.

And the deletion is larger than the derived set, because the branch it feeds is already dead. _validate_formats_tolerant (src/core/creative_agent_registry.py:114–146) only consults the asset-type machinery inside except ValidationError. An unknown asset_type no longer raises, so that branch is unreachable for the thing it was written for. What it is still reachable by is any other validation failure — and there the empty set is actively harmful. Measured end to end:

format with ONE real defect: assets[0].requirements.codecs is a str, must be a list

Format.model_validate(doc)                    -> refused at assets.0.video.requirements.codecs
_KNOWN_ASSET_TYPES                            -> set()
_unknown_asset_types(doc)                     -> {'video'}          <- because the set is empty
_is_purely_additive_asset_type(doc, {'video'}) -> True              <- substituting "image" hides it
_validate_formats_tolerant([doc], log)        -> 0 formats returned

WARNING  Skipped 1 creative format(s) using unsupported additive asset_type(s) ['video']
         (not modeled by the pinned adcp schema); returning the 0 compatible format(s).

EXECUTION A format whose only defect is a mistyped video field is silently dropped, and the warning blames video — a first-class, fully modelled asset type. The function exists so that "any other ValidationError still fails LOUD so real contract breakage is not masked"; the empty set inverts it into a universal masker. The mechanism is that both asset arms carry extra="allow" and differ only in their requirements sub-model, so substituting "image" turns the 12 video-only fields into permitted extras and the defect disappears.

In the other direction the module's stated promise is inverted too. Its docstring says an unrecognized additive asset_type is "DROPPED (never mis-represented — we never model a creative we cannot fully understand)". Today it is kept, carrying an UnknownFormatAsset arm. Nothing of ours decided that; the SDK's union grew a catch-all arm and our drop path went dark.

Site 2 — a real tension worth naming

The enum is reachable two ways, and the obvious one is compromised by #1409. Its class name is Field1 — a positional codegen name, exactly the kind #1409 proposes to rename. Importing it by name trades a silent traversal for a loud ImportError, which is an improvement, but it couples us to a name upstream has already said will change. The announced-schema route takes neither dependence:

ListCreativesRequest.model_json_schema()  -> fields enum: 20 values
                                             ['creative_id','name','format_id','format_kind', ...]

EXECUTION That reads the model's own published contract rather than its Python type graph, so it is immune to arm naming, to pointer wrappers, and to Discriminator insertion — the #1409 / #1362 / #1414 family in one step. It costs a small $ref resolution. For this site that is the right trade, because the answer genuinely is a set and the set has to come from somewhere.

Site 4 — the honest case where asking the authority is worse

This is the site the question is most interesting about, and the answer is not the tidy one. The structural read is correct here, and both alternative authorities are worse.

Validation cannot answer it. TypeAdapter(ann).validate_python(None) over the same 1316 models produces 47 false positives, every one a bare typing.Any:

required + nullable, found by the current structural rule       6
the rule's apparent "misses" under validation                  48
  ... of which bare typing.Any                                 47
  ... of which a RootModel TypeVar                              1
  ... genuine misses                                            0

EXECUTION What the authority does not expose: pydantic's validator conflates "the schema declares this nullable" with "the type is unconstrained". TypeAdapter(Any).validate_python(None) succeeds, and no runtime API distinguishes the two, because at validation time there is nothing to distinguish — both accept None. The JSON Schema fact the wire serializer needs is a declaration, and a declaration is only legible in the declaration.

The announced schema can answer it, and gains nothing. It does draw the distinction ({"anyOf":[{"type":"string"},{"type":"null"}]} versus {}), and over the 1316 models it returns exactly the same six fields — CreateMediaBuyResponse1.confirmed_at, CreateMediaBuySuccess.confirmed_at, DiscriminatorItem.value, GetMediaBuysMediaBuy.confirmed_at, MediaBuy.confirmed_at, ReportingRevision.data_through — with no asymmetry in either direction. EXECUTION But reaching them needs a $ref/anyOf resolver, which is the "150 lines of $ref / allOf / JSON-pointer walking" the comment at _base.py:862–874 records as having been deleted in favour of this rule. Reintroducing it would restore a pointer walk to return an identical answer.

So the site stays as it is, for a reason that is now measured rather than asserted: it reads the top of field.annotation, which is the zone pydantic normalizes (2 of 1316 retain an Annotated there), so it is structurally outside the failure mode this question is about. The empty-derivation mode needs a traversal, and a single get_args at a normalized top level is not one.

Site 3 — out of scope, and why that is the right answer rather than a dodge

The model-rebuild closure walks annotations, so it looks like a fourth instance. Its failure mode is not silent: a model the closure misses raises 'MockValSer' object cannot be converted to 'SchemaSerializer' on its first dump. An empty worklist does not produce a wrong answer quietly — it produces a loud one at the first serialization. The authority that would replace the walk is __pydantic_complete__, and after import exactly one model in our namespace reports incomplete (BaseModel itself, re-exported and abstract). EXECUTION

Not measured, and stated rather than smoothed: whether iterating __pydantic_complete__ over our 257 declared models would reach everything the annotation walk reaches. The walk touches 1316 models, so the large majority are library leaves, and the comment's account of the bug is that those leaves are the ones needing the explicit rebuild. Isolating that would mean unwinding an import that has already run.

So: is anything only observable rather than structurally enforceable?

Yes, one thing, and it is not any of the four sites.

Site 1's architecture makes the empty-derivation mode unconstructible — there is no derived set, and isinstance against an imported arm class either resolves or fails at import. What it does not make unconstructible is the SDK silently changing what validation means. The _unknown arm turned a raising path into an accepting one, and no shape of ours could have refused that: our code was correct before and after, and the behaviour inverted underneath it. That is a property of the dependency, not of our code, and the only thing that surfaces it is reading the diff of what the union admits.

We are not reaching for a check there. The honest conclusion is that the tolerant-ingestion policy — "drop a format we cannot fully model" — cannot be implemented against a union that models everything. Either the policy changes to "keep it, and mark the unmodelled arms", which the SDK now implements for us and which the isinstance read expresses directly, or the policy is wrong and should be deleted along with the code. Both are design decisions, not detections, and that is the deliverable here: stop deriving the vocabulary, ask the arm, and decide which policy we actually want.

What could not be verified

  • #1397's concrete case. _DeliveryCreativeManifest and revalidate_instances appear nowhere in our tree, so we have no local observation of the manifest instance the issue is actually about — only of the ProductFilters instance we reported ourselves.
  • #1404's bundle-key risk. The _pinned_fields.py string slice and resolve_bundle_key agree on all four versions present in the bundle, so the divergence is possible and not current. Stated as latent rather than measured.
  • #1418's cold-start numbers. The 127–204 ms cold versus 0.001 ms warm figures are the reporter's; not reproduced here, and not reproducible from the seller side.
  • #1414's 42/14/12 blast radius. Taken from the issue. We verified only that our one exposed model is CreateMediaBuyRequest and that the workaround is live for the absent-key case; the other 11 models were not re-counted on our local-segment pin.
  • The .root deprecation horizon. The shim warns today. Whether it is removed in 9.0 GA or later is not stated in any open issue we read, so the 12 call sites have no dated deadline.
  • Whether __pydantic_complete__ alone would replace the rebuild closure. The walk touches 1316 models against our 257 declared ones, so most are library leaves, and the comment's account of the bug says those leaves are what need the explicit rebuild. Confirming it would mean unwinding an import that has already run. Stated as unmeasured rather than assumed either way.
  • When the _unknown arm was added. We measured that it absorbs unmodelled asset types on this pin, not which SDK release introduced it, so we cannot say how long our drop path has been dark. A delta needs two measurements and we took one.
  • Whether the false-drop has occurred in production. The path is reachable and reproduced locally. We did not search logs for the warning, so its real-world frequency is unknown.

Every measurement above was taken in a dedicated worktree against the pin named at the top. Numbers are evidence for that pin and that tree only; a different local segment of the SDK can move several of them, as #1397 and #1359 both demonstrate.
