5. Reasons found factually wrong

You asked me to check each stated reason against reality. Of the 8 live _XFAIL_TAGS/_SELECTIVE_XFAIL reasons in scope, 5 are wrong and 2 of the 10 entries are dead. Every verification below is against the pinned bundle in a tree carrying the identical wheel pin (adcp==9.0.0b2+prs1435.1415.1447.1456, confirmed byte-identical pyproject.toml line and adcp_pin.py in both trees).

1. T-UC-005-ext-b-disclosure-dupes — "the pinned schema declares no uniqueItems"
WRONG, and this one is a live flip. The pin declares "uniqueItems": true and "minItems": 1 on disclosure_positions and disclosure_persistence, on both role variants. The reason concludes "production is right to accept it… reconciling it upstream is the fix, not patching production to match" — the opposite of the truth. The real cause is that the SDK implements uniqueItems as a coercion (coerce_to_unique_enum_list) rather than a validation. EXECUTION — 9 items flipped to PASS under probe.
2. T-UC-005-ext-b — "suggestion field not implemented in error responses"
WRONG. suggestion is written onto the wire at src/core/schemas/_base.py:1315, derived from CODE_TABLE, and core/error.json declares it as an optional member. Proven by the suite itself: roughly ten sibling ext-b-* scenarios in the same feature (lines 490, 530, 544, 558, 573, 586, 599, 613, 626, 639) assert the identical sentence and all pass. The actual blocker is the undeclared type field (Rank 7). EXECUTION
3. T-UC-005-ext-a — "error code AUTH_REQUIRED instead of TENANT_REQUIRED"
WRONG on both sides, and stale. The scenario no longer mentions TENANT_REQUIRED — it was corrected to demand AUTH_MISSING, with the feature's own comment at line 464 explaining that TENANT_REQUIRED "was a minted code no raise site can emit". TENANT_REQUIRED is absent from the pin's 120-member enums/error-code.json. And production already raises AUTH_MISSING (src/core/exceptions.py:515, AdCPAuthRequiredError._code). Neither half of the reason describes anything current; the real blocker is Rank 8. EXECUTION
4. Five reasons citing "adcp 3.12: type filter removed from ListCreativeFormatsRequest"
WRONG as stated, right by accident. type was not removed at the pin: creative/list-creative-formats-request.json declares it with enum ["audio","video","display","dooh"] and no "deprecated" marker — unlike its siblings format_ids and include_pricing, which do carry one. The true statement is narrower and more useful: type exists only on the creative-agent variant, so it is not an obligation on a sales agent. The operational conclusion survives; the cited cause does not, and the phrasing has propagated into a step assertion (Trap T1). READING of the pinned schemas + upstream 3.2.1 prose.
5. T-UC-005-sandbox-happy — "sandbox mode not implemented in list_creative_formats response"
MISLEADING rather than wrong. The field is on the response model and on the pinned schema, and the code has a sandbox= argument with a comment claiming it is "determined from identity". The value is hardcoded None (creative_formats.py:515). A reader checking "does this tool support sandbox?" against this reason looks in the wrong place — the obstacle is in the resolver, not in the response (Rank 4). EXECUTION
6. Two dead _XFAIL_TAGS entries
T-UC-005-inv-049-1-holds and T-UC-005-inv-049-1-violated are registered in _XFAIL_TAGS and appear nowhere in the feature file (0 occurrences; the family runs inv-049-10-* and inv-049-11-*). They produced zero items in the run. A free shrink of the routing table with no behavioural risk. EXECUTION
7. e2e_rest_known_failures.txt:351 — already self-corrected
Not a finding against the author: the block at :330-351 states that its own recorded reason (adcp#7338) is stale and that the node now fails on a missing audio category. I measured the same failure independently. Noted because it is the one reason in the scope that documents its own staleness instead of carrying it silently.
