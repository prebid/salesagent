Reasons found factually wrong

R1. metro requires a system — the pin says the opposite, and always did

Three places encode the same wrong obligation:

  • tests/bdd/conftest.py:2828 — AdCP spec defines metro/postal_area system requirement only in field description; no validator. See docs/test-debt-bdd-strict-markers.md item C10.
  • tests/bdd/conftest.py:3511 — reporting_dimensions validation not implemented — production accepts invalid configs.
  • tests/bdd/e2e_rest_known_failures.txt:80 — the same row, one of only 8 active lines in that ledger.

EXEC The pinned 3.2 request schema does carry a formal constraint — #/properties/reporting_dimensions/properties/geo/allOf, three if/then branches — so the no validator half of the C10 reason is stale. But its metro branch reads:

"then": { "anyOf": [ {"not": {"required": ["system"]}},     {"properties": {"system": {"$ref": "#/$defs/MetroAreaSystem"}}, "required": ["system"]} ],   "not": {"required": ["country"]} }

The first anyOf arm permits system being absent outright, and the field's own description says Omit to request the level without selecting a specific system. Validated directly: {"geo": {"geo_level": "metro"}} is VALID against the pinned bundle under Draft202012Validator, while {"geo": {"limit": 10}} correctly fails on the required geo_level. EXEC

And this is not a 3.2 regression. The same document validates as VALID at the 3.1, 3.1.15 and 3.2 schema sets the SDK ships — three measurements, not one. EXEC The row has always demanded a refusal no version of the spec mandates. Production accepting it is correct; the scenario is the defect.

The misreading is traceable to one line of the feature itself. The invariant comment at feature:708 reads BR-RULE-091 INV-5: geo_level=metro/postal_area -> system field specifies classification — which is true of a system that is present. The two rows extrapolated specifies into is required. That comment is where a fixer should start. READ

Acting on R1 removes the only non-dormant reporting-dimensions routing in UC-004 and one of the eight remaining e2e_rest ledger lines. It is the single highest-value item in this report and needs no production change — but it is a scenario correction, so it belongs to whoever owns regrounding, not to a graduation pass.

R2. UC-022's format_id obligations are inverse to the 3.2 design

Rows 6 and 7 above. UC-022 treats format_id as the mandatory identity of a creative manifest and derives five or more refusals from that premise. The pin deprecates format_id in 3.2, makes it mutually exclusive with format_kind, and requires only assets. The feature is grounded in the 3.1 shape throughout. READ

Traps — call these out before anyone writes a scenario here

T1. The Given's dimension vocabulary admits 43 things that are not dimensions

_assert_wire_carries_dimension (tests/bdd/steps/domain/uc004_delivery.py:1091) derives the legal dimension names from PackageDelivery.model_fields by taking every by_* field and stripping the prefix — excluding only names ending _truncated. It does not exclude _sorted_by, _sort_direction, _pagination or _suppressed. EXEC The accepted set is 60 names, of which 17 are real dimensions; the other 43 are applied-sort echoes and pagination flags. the seller supports reporting dimension "creative_sorted_by" therefore passes, which I confirmed by running it: PASSED on all three transports.

The derivation's docstring is right about the principle — the wire surface should be the vocabulary — and wrong about the filter. A dimension is a by_* field whose type is a list; the echoes are scalars. One-line defect, reported not fixed. Note also that the positive and negative sentences still share a body, which the sibling comment at :1148 already flags as the shape to stop sharing.

then_packages_include_breakdown (tests/bdd/steps/domain/uc004_delivery.py:3077) is a strong assertion — it requires a non-empty list, impressions on every entry, a non-empty dimension identifier, and distinct identifiers across rows. Its identity column comes from dimension_key = field[3:].
