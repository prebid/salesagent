3. Xfail reasons that are factually wrong

Six. Five of them describe production behaviour that does not exist; the sixth cites a mechanism that does not exist.

3.1 "spec expects CREATIVE_REJECTED" — the scenario was corrected away from it years ago

tests/bdd/conftest.py:2453 and :2463: "creative error code mismatch: production uses NOT_FOUND/VALIDATION_ERROR/INVALID_CREATIVES, spec expects CREATIVE_REJECTED — spec-production gap". The feature file says the opposite in its own words at tests/bdd/features/BR-UC-002-create-media-buy.feature:1306: "Three conditions, three codes. They read CREATIVE_REJECTED for all three and passed for years because production emitted that one code for all three too — a test that encodes production's bug is not coverage." The rows now ask for CREATIVE_NOT_FOUND / VALIDATION_ERROR / VALIDATION_ERROR, and all five rows covered by these two entries measured XPASS(strict). EXEC

3.2 "max_creatives limit not enforced in production"

tests/bdd/conftest.py:2458 and :2468. It is enforced: the pin sets maxItems: 100 on packages[].creatives (media-buy/package-request.json:370), pydantic refuses 101 with too_long, and the boundary emits INVALID_REQUEST. Both rows measured XPASS(strict). EXEC

3.3 "INVALID_CREATIVES error lacks suggestion field" — neither half is true

tests/bdd/conftest.py:634 and :635, on T-UC-002-inv-026-2 / -026-4. Three errors:

  • INVALID_CREATIVES is not a code. CODE_TABLE holds 158 entries and that is not one of them. EXEC

  • Neither scenario names a code at all — each asks only for failure plus a suggestion (BR-UC-002-create-media-buy.feature:1006-1024). READ

The real cause is dormancy, and both obligations are implemented (media_buy_create.py:379, :3702).

3.4 "inline creative upload not persisted in create_media_buy"

4. The traps — scenarios that would pass while grading nothing

4.1 error with suggestion is satisfied by every code in the table

Both format-id-structure outlines write their five invalid outcomes as the bare string error with suggestion. _assert_error_outcome routes that to the suggestion-only branch at tests/bdd/steps/domain/uc002_create_media_buy.py:1267, which asserts one thing: a non-empty top-level suggestion on the wire envelope. Since every one of the 158 codes carries one, the assertion reduces to "some error happened". Three of the five rows (plain_string, missing_agent_url, missing_id) are refused by pydantic regardless of any creative logic; the two that name the actual subject (unregistered_agent, unknown_format) are refused by the product-subset gate at media_buy_create.py:3219-3243 because the step points them at a different agent or a nonexistent id, which also puts them outside the product's declared set. The step's own docstring (given_media_buy.py:3230-3236) states the gap: "unregistered agent and unknown format pass Pydantic validation and are only caught later (or not at all) by format compatibility checks." Flipping these two outlines buys 33 green items and zero coverage of agent registration or format existence. EXEC (that they pass) + READ (why).

4.2 success means "no error", so replacement semantics goes unread

All nine creative-replacement rows end in the result should be success. then_result_should_be at uc002_create_media_buy.py:787 answers that branch with two assertions: "error" not in ctx and a non-None payload. The scenario titles promise replacement semantics and the Givens construct the precondition for it (the package "pkg_001" has existing creative assignments [cr_old_1, cr_old_2]), but no Then reads the assignment set afterwards — so production's replacement behaviour (media_buy_update.py:1163-1173 deletes assignments absent from the request) is never observed. T-UC-003-partition-creative-replacement and T-UC-003-boundary-creative-replacement are additionally row-for-row duplicates: the same four modes, the same four outcomes, different column headings. EXEC + READ

4.3 A note on the response-compliance Then

Every outline in both files also carries the response is compliant with the <tool> spec (tests/bdd/steps/generic/then_schema.py:257), which grades the whole response oneOf. That is weaker than naming a branch but is not vacuous — the step's docstring records the measurement showing it rejects an empty object, a junk object, and success documents missing confirmed_at / revision. It does not rescue §4.1 or §4.2, because in both cases the response IS one of the legal shapes. READ

5. Separate findings — defects, not flip candidates

5.1 A per-creative REFERENCE_NOT_FOUND is reported as CREATIVE_REJECTED, carrying code-table text

src/core/helpers/creative_helpers.py:318-325 composes detail_msgs = [f"{r.creative_id}: {err.message}"] from the nested sync's per-creative errors and raises AdCPCreativeRejectedError(details=CreativeRejectionDetails(reasons=detail_msgs)). Measured consequence on the wire:

"code": "CREATIVE_REJECTED", "details": {"reasons": ["inline-cr-001: Generic fallback for a referenced identifier, grant, session, or other resource that does not exist or is not accessible by the caller. Use when no resource-specific not-found code applies …"]}

Two defects in one site. The code is wrong — CREATIVE_REJECTED reads "Creative failed content-policy, brand-safety, or accessibility review", which is the exact misreading BR-UC-002-create-media-buy.feature:1306 and media_buy_update.py:366-372 both already reject for this condition. And reasons carries derived buyer-facing text lifted from the code table, which ADR-010 puts off the wire; the field becomes unusable to a buyer. EXEC (the envelope) + READ (the site).

5.2 create skips the creative-format check that update refuses on

For a creative carrying only the canonical arm (format_kind, no legacy assertion), the two tools answer the same condition oppositely:

  • create skips it. src/core/tools/media_buy_create.py:459: "a creative identified by its canonical kind is unconstrained here until products carry format_options[]."
  • update refuses it. src/core/tools/media_buy_update.py:353: if creative_identity is None or creative_identity not in supported_formats: — a None identity lands in incompatible and the package is rejected with VALIDATION_ERROR.

This is the skip-vs-refuse divergence named as risk 4 in docs/audits/format-kind-canonical-analysis.html §8, confirmed live at this HEAD. No scenario in either feature file sends a canonical-only creative into either tool, so nothing grades it. READ

5.3 The immutable-package-field obligation holds only in dev

AdCPPackageUpdate (src/core/schemas/_base.py:3045) declares none of format_ids, product_id, pricing_option_id, so the pin's package-update root not constraint is enforced by extra="forbid" — which is the dev/CI setting. Under production's extra="ignore" the three keys are silently dropped instead of rejected. That is critical pattern #7 working as designed for forward compatibility, but it means the three outlines in row 6 will grade an obligation the deployed seller does not meet. Worth a decision before the step work, not a code change. EXEC (model fields) + READ (the split).

6. Deliberately not claimed

  • No 4-transport measurement. The probe graded a2a / mcp / rest. e2e_rest needs the full stack, and tests/bdd/e2e_rest_known_failures.txt was neither consulted per-row nor exercised. Any graduation touching that ledger needs a bdd-in-network run.
  • No claim that a passing row is correct beyond its own assertions. Rows 1, 2 and 3 are graded on named codes through the wire envelope; rows 4 and 5 pass and are called traps for exactly that reason.
  • The probe gave each catch-all its sibling's seed. A real wiring change might choose a different seed, which would move the UC-003 numbers. The seed choice is the one way this measurement could be optimistic.
  • Storyboard is out of scope per the brief, including the unwired upstream media_buy_seller/canonical_formats storyboard that would grade package selectors, CONFLICTING_SELECTORS and canonical satisfaction.
  • No canonical-selector scenario exists to flip. Grepping both feature files for format_kind / format_option_refs on a package returns nothing, which matches the format-kind analysis §6: package selectors are ungraded in BDD. The format-identity design therefore unblocks nothing in these two modules today — its payoff here is §5.2, which needs a new scenario rather than a graduation.
