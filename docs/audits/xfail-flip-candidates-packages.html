3.1 The format-selector refusal code: production is right, four scenarios are not

Four items demand INVALID_REQUEST where the pin gives VALIDATION_ERROR. READING, from the pinned enum and the written spec.

3.2.1 enums/error-code.json splits them explicitly:
INVALID_REQUEST — "Request is malformed, missing required fields, or violates schema constraints."
VALIDATION_ERROR — "Request contains invalid field values or violates business rules beyond schema validation."

A format_id the target product does not carry is a business rule beyond schema validation. And docs/media-buy/specification.mdx:1040 lists VALIDATION_ERROR ("Request format or parameter errors") in the media-buy protocol's own error set while never listing INVALID_REQUEST at all.

Production refuses correctly: src/core/tools/media_buy_create.py:3220–3245 computes requested_format_keys - product_format_keys and raises AdCPValidationError(field="packages[n].format_ids", details=ValidationDetails(product_id=…, rejected_value=…, accepted_values=…)). AdCPValidationError._code is ErrorCode.VALIDATION_ERROR (src/core/exceptions.py:449–452). The refusal is present, attributed to the right field, and carries the accepted set. The conftest reason "a format_id the product does not carry is accepted instead of refused" (conftest.py:4287) is factually wrong — it is refused, with a different code than the scenario names.

This is the same wrong premise the sibling pricing-option entries carry ("Production returns 'validation_error' instead of AdCP-spec 'INVALID_REQUEST'", conftest.py:4405–4409), which is out of this scope but shares the root cause: somewhere a reading took INVALID_REQUEST as the only legitimate refusal code for a bad parameter. The pin disagrees for anything past schema shape. The graduations that do rest on INVALID_REQUEST — ext-g-*, inv-197-4 — are all DTO/pydantic refusals, i.e. genuine schema-constraint violations, so the distinction holds cleanly.

3.2 format_ids defaulting: the pin forbids what two scenarios demand

3.2.1 core/package.json on format_ids: "Legacy named-format IDs supplied for this package on create_media_buy. Sellers SHOULD echo this field whenever the request included it … Omitted means the request did not carry legacy format_ids." READING

The field is a request echo. A seller that returns the product's formats for a package that supplied none is inventing a wire value the buyer never sent — the pin's own sentence rules it out. T-UC-026-inv-197-3 ("format_ids omitted defaults to all product formats", feature line 558) and the then_package_default_formats assertion inside T-UC-026-main-required-fields (tests/bdd/steps/domain/uc026_package_media_buy.py:1747–1770, which compares the response's format_ids set for equality against ctx["default_product"].format_ids) are both over-specified against 3.2.1. They were written against a pre-3.2 reading.

Note what production does do, which is the right thing and is invisible to these scenarios: media_buy_create.py:3299+ ("Fallback to product's formats if no request format_ids") defaults format_ids_to_use — the list handed to the adapter and persistence — while the response package is built by Package.echoing(package, …) from the request package (media_buy_create.py:3926–3933). Effective selection defaults; the wire echo does not. That is the pin's shape. READING

3.3 format_ids_to_provide: the one place the canonical design matters here

The second failing assertion in T-UC-026-main-required-fields is a real, grounded obligation and a real gap. Production sets format_ids_to_provide=package.format_ids (media_buy_create.py:3932) — the request echo again — so a package that omitted format_ids gets None, and then_package_formats_to_provide (uc026_package_media_buy.py:1780) fails on its first assertion. READING

Under 3.2.1 the fix is not "echo the effective list". formats_to_provide is the canonical field — "Immutable canonical creative contracts established for this package … each entry is a PackageFormatSnapshot", minItems: 1 — and format_ids_to_provide is explicitly "DEPRECATED in 3.2. Legacy named-format projection of formats_to_provide". So this is the one item in my scope that maps onto the format-kind staged plan: snapshot emission, with format_ids_to_provide as a derived projection (docs/audits/format-kind-canonical-analysis.html §7, the selectors/emission stage). READING

The format-kind design will not flip anything else in either module. EXECUTION: a regex scan of both feature files for format_kind, format_option, v1_format_ref, formats_to_provide, formats_pending returns hits only on format_ids_to_provide in UC-026 (lines 14, 58, 63, 76, 78) and nothing at all in UC-019. Neither module exercises the canonical arm, so the brief's category 1 — "blocked only because comparisons key on the legacy pair" — has exactly one member here, and it is this assertion.
