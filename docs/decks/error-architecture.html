The problem

Every raise site was writing a published document

adcp_error_for() returns any AdCPError unchanged. So the string you typed at the raise site was the wire. Not a log line — the document the buyer receives.

The last two rows together are the whole story: someone opened error-code.json, copied one of its three fields per class, left message and suggestion sitting in the same JSON object, and then wrote a 150-line guard to check the copy hadn't drifted from the file it came from.

From any single class, copying recovery is correct. From any single raise site, writing a message is correct. It is only wrong at 42 and at 315.

What the spec actually says

The code is an open label. The recovery is the closed contract.

From core/error.json, AdCP 3.1.1 — verbatim:

"The error-code vocabulary is open: error.code is wire-typed string
 (not a closed enum), the standard codes published in enums/error-code.json
 are documentary, and senders MAY emit codes outside that set.
 Receivers MUST decode unknown codes — read error.recovery for the
 recovery classification."

Two consequences we had backwards:

  • Our platform-specific codes were legal all along. ERROR_CODE_MAPPING (42 entries) and to_wire_error_code were collapsing them onto spec codes — discarding information the spec asks senders to keep.
  • recovery is the field receivers branch on, it is closed to three values, and the schema says implementations must not override it. It should never have been a per-class hand-copy.
The solution

One table. The class declares a code and nothing else.

src/core/errors/codes.py

Recovery      correctable | transient | terminal
AppErrorCode  our 8 platform codes
ErrorCodeT    = ErrorCode | AppErrorCode
CodeEntry     recovery, suggestion, message, status
CODE_TABLE    100 entries

The 92 spec entries are loaded from the installed wheel at import, not transcribed. A loaded table cannot drift, so there is nothing for a guard to verify. Only the 8 platform entries are hand-written, in the same fields. status is the exception: the pin fixes the 4xx/5xx band per code but not the number, so the numbers are authored here — keyed by code, never by class.

The exception

class AdCPValidationError(AdCPError):
    _code = ErrorCode.VALIDATION_ERROR

That is the entire subclass. message, suggestion, recovery and the HTTP status_code resolve from the table by code. The status was the last per-class knob, and it was removed once a subclass was found re-coding itself to INVALID_REQUEST while keeping its parent's 404. _code is a ClassVar, never a constructor parameter, so no instance can change its own code.

Vendor names left the wire

GAM_UPDATE_FAILED → AD_SERVER_UPDATE_FAILED. The buyer must not learn which ad server we run.

How you raise now

You cannot write the sentence. You supply the facts.

# before — the f-string IS the buyer-facing document
raise AdCPValidationError(
    f"Per AdCP spec, format_ids must be FormatId objects with {{agent_url, id}}. "
    f"Received {fmt_id!r} in {where}."
)

# after — code carries the sentence; you carry the data
raise AdCPValidationError(
    field=field,
    details={**where, "received": fmt_id, "expected": "FormatId object"},
)

Where a caught exception goes

raise AdCPValidationError(field=field, details=dict(where), internal_detail=e) from e
# internal_detail reaches the SERVER LOG only. It never reaches the buyer.
There is no message=, no suggestion=, no recovery= parameter. Not discouraged — absent. A raise site that wants to say something has field, details, and internal_detail.
How you raise — worked examples

Five shapes that cover almost everything

1 · The buyer sent something invalid

raise AdCPValidationError(field="packages[0].budget")
# field is the error.json pointer naming WHICH request field was rejected.
# message, suggestion and recovery all resolve from VALIDATION_ERROR's table entry.

2 · …and you want to say what you expected

raise AdCPValidationError(
    field=field,
    details={"received": fmt_id, "expected": "FormatId object"},
)

3 · A referenced entity does not exist — use a declared shape

raise AdCPReferenceNotFoundError(
    field="package_ids[2]",
    details=ProductRefDetails(missing_product_ids=["prod_9", "prod_11"]),
)
# ProductRefDetails extends EntityRefDetails, so account_id / media_buy_id /
# package_id / product_id are available on it too — you cannot invent a fifth key.

4 · A third party failed — the raw text goes to the log, never the buyer

except httpx.HTTPError as e:
    raise AdCPServiceUnavailableError(
        details=UpstreamCallDetails(agent_name=agent.name, status_code=resp.status_code),
        internal_detail=e,          # server log only
    ) from e
# Note what is absent: no f-string, no str(e), no hostname. The URL of a
# seller-configured agent is not the buyer's business.

5 · A batch where some items failed

raise AdCPBulkUpdateError(details=ProblemsDetails(problems=[
    ErrorProblem(code=ErrorCode.CREATIVE_NOT_FOUND,
                 subject_type="creative", subject_id="cr_7", field="creative_ids[0]"),
    ErrorProblem(code=AppErrorCode.AD_SERVER_CREATE_FAILED,
                 subject_type="package", subject_id="pkg_2"),
]))
# subject_type is a Literal, so "creatives" or "Creative" will not compile.
The class you raise decides the code. The code decides the message, the suggestion and the recovery. You decide the facts: field, details, internal_detail.
The part that has been a struggle

Where each thing you pass actually lands

Asserting from BDD is hard when you cannot see the mapping. Here is the whole chain for example 3 above.

// what reaches the wire
{
  "adcp_error": {                     // envelope layer
    "code": "REFERENCE_NOT_FOUND",    // from the CLASS's _code, verbatim

  },
  "errors": [ { ...the same object... } ],   // payload layer

Four things that used to bite

  • The error appears twice. adcp_error at envelope level and errors[0] at payload level. assert_wire_error reads the normalized envelope, so you never choose — and require_suggestion checks both layers.
  • to_dict() is a different shape. It emits error_code; the wire emits code. to_dict() is for audit logging, not the wire. If you are asserting against error_code, you are asserting the wrong artifact.
  • You do not pass recovery. It defaults to the pinned table value, so the assertion is non-vacuous without per-scenario duplication. Passing a wrong one fails — that is the point.
  • An unemittable code fails loudly. assert_wire_error checks CODE_TABLE first: "…is not an emittable error code, so no raise site can put it on the wire. Reconcile the feature to a code production can emit." A feature file demanding an invented code now says so, instead of silently xfailing.
Never hand-roll envelope parsing in a step. assert_wire_error is transport-independent — the same call holds on mcp, a2a, rest and e2e_rest, because the dispatcher normalizes the envelope per transport before you see it.
What happened to details

details is a declared class, not a dict

src/core/errors/details.py — the shapes are typed, and they compose:

ErrorDetails                 base
├── VersionUnsupportedDetails  supported_versions, supported_majors, build_version…
├── EntityRefDetails           account_id, media_buy_id, package_id, product_id
│   └── ProductRefDetails      + missing_product_ids
├── UpstreamCallDetails        agent_name, url, status, status_code
├── ProblemsDetails            problems: list[ErrorProblem]
└── AdapterFailureDetails      = EntityRef + UpstreamCall + Problems

ErrorProblem   code, subject_type: Literal["creative"|"product"|"package"|"account"],
               subject_id, field

A per-entity failure inside a batch is an ErrorProblem with a typed subject_type — not a free-form string a caller has to parse. Adapter failures compose three shapes rather than inventing a fourth dict.

How you assert — BDD

Assert the response the code returned. Never a reconstruction.

# one helper, on the result you already hold
result.assert_wire_error(
    "VALIDATION_ERROR",
    recovery="correctable",       # optional
    field="packages[0].budget",   # optional
    details={"expected": "FormatId object"},
    require_suggestion=True,
)

What we deleted, and why it matters to you

  • _CODE_TO_CLASS is gone. Tests no longer rebuild an exception from a wire payload and assert on the rebuild. The reconstruction was lossy — it could pass while the real envelope was wrong.
  • The IMPL pseudo-transport is gone. It had no wire, so any assertion routed through it was grading nothing. Every scenario now runs a real transport.
  • 406 "message should contain …" steps are gone. They asserted a copy of CODE_TABLE's own sentence — a test that can only fail if you edit the table. Assert the code and the field pointer; the sentence is derived.

Transports a scenario runs against: mcp, a2a, rest, e2e_rest.

Rule of thumb: if your assertion would still pass when the buyer received a different code, it is not grading the error.
DTOs — what follows

The same move, applied to the payload

Typed details is one instance of a larger change: shapes on the wire are declared, not assembled. Also landed:

  • Pricing-option models are owned locally so non-spec fields stay off the wire.
  • get_media_buys got the REST route 61 scenarios were waiting for.
  • An absent adcp_version now means the pinned version, not v2.
  • An invented error code is unaddable anywhere — not merely where tests happen to look.
Two things still moving — do not present this as finished.
  • salesagent-2cco1 (open, P1): we cannot control extra on SDK RootModels, so non-spec fields can still reach the wire through them.
  • salesagent-rys3u.2 (in progress): 48 of 156 details= arguments are declared classes; 104 are still dict literals. _details_to_wire() keeps a Mapping branch as scaffolding until the last one converts.

The rules

What to do differently on Monday

  1. Raise, then stop. raise AdCPValidationError(field=…, details=…). The transport boundary owns the envelope. Do not catch and re-raise to add prose.
  2. Third-party text goes to internal_detail=. Never into anything buyer-facing. It is logged server-side for you.
  3. Need a new error? Add a class. The class is how you raise it — that has not changed. What changed is what the class declares: a code, and nothing else. If the code is a spec code it is already in the table. A platform code additionally needs an AppErrorCode member and its CodeEntry — one cannot exist without the other.
  4. recovery lives in the table, keyed by the code your class declares — not on the class and not at the raise site. It is a read-only property. If a case needs a different recovery, it needs a different code; the vocabulary is open, so that is cheap.
  5. Assert the code and the field pointer. Not the sentence. A test that asserts derived prose can only fail when you edit the table.
  6. Grade on the wire, across transports. If it did not go through mcp, a2a, rest or e2e_rest, it is not graded.
  7. Reach for a declared details class before adding a dict key. The shapes compose.
