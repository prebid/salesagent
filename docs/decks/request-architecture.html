The problem

One tool had four independent opinions about its own request

Every AdCP tool is reachable three ways, and each transport had written down the request shape by hand. The SDK ships a request DTO for that tool. Nothing connected the four.

WhereHow the shape was decidedDrifts from the spec?
MCPthe Python signature of the wrapper — flat parameters, hand-typedfreely
A2Akeys plucked out of a skill payload by handfreely
RESTa hand-written *Body model listing fields againfreely
the SDKthe actual spec-derived DTOit is the spec

So the shape a buyer reads out of our published schema, and the shape a buyer reads out of the AdCP spec, were two different documents maintained by two different processes. One of those processes was “somebody remembers.”

The invariant all of this exists to protect is one sentence: a body-semantic field must be honored or refused — never silently dropped. Decided per transport, at each wrapper’s argument binder, a field one transport bound and another did not was accepted on the wire and discarded before the tool. The buyer was told it applied.

What that actually cost — three real ones.

get_adcp_capabilities advertised protocols: list[str] where the DTO declares a typed enum, and ext: dict where the DTO declares ExtensionObject. Two different contracts, and nothing failed — no test, no guard, no type error.

list_creative_formats refused pagination in its hand-written map while fully implementing cursor pagination. The refusal ran first. A working feature was turned off by a stale list.

update_media_buy published targeting_overlay and creatives to buyers. Neither is in the pinned 3.1.1 request schema, _impl honors only the per-package overlay, and no caller ever passed them. Advertised, accepted, read by nothing.

The second problem

We had built machinery to police the drift instead of removing it

Because the four shapes could disagree, we grew apparatus to detect when they did. A field the tool didn’t implement yet had to be listed as unsupported, so a buyer sending it got a refusal instead of silence. That list was hand-maintained, per tool.

# the shape of the old world
_UNSUPPORTED_GET_PRODUCTS_FIELDS = {...}          # × 10 tool modules, hand-written
refuse_unsupported_fields(req, tool=..., unsupported=...)  # called per tool, by hand
merge_spec_request(flat_kwargs, spec_model)        # reconcile two shapes at runtime
UNDISPOSED_LEDGER = {...}                         # fields nobody had decided about yet
tests/harness/spec_field_consumption.py           # a static analyzer to grade the above
test_architecture_spec_field_disposition.py       # + 2 sibling guards

Every one of those is a mechanism for noticing that two hand-written things disagree. None of them makes the disagreement impossible. A guard that lists violations records the disease; it does not cure it — and each new tool added a row to every list.

And the checkers were themselves checkable only by mutation. Two examples, each found by deliberately breaking the code to see whether the guard noticed:

  • A refusal map counted as present when the dict existed — so deleting the refuse_unsupported_fields call left 27 guards green. The map was decorative and the guard graded the decoration.
  • A parameter counted as handled when the signature declared it. Crediting the signature is exactly how targeting_overlay and creatives stayed invisible while being read by nothing.
This is the pattern worth naming, because it recurs everywhere: when two artifacts can drift, the instinct is to add a checker. But a checker is a third artifact that can also be wrong — and now nobody is checking it. The cure is to derive one from the other so there is only one artifact and the checker can be deleted.
The rule

Announced = the DTO’s fields ∩ the implementation’s arguments

One sentence, and everything else in this deck falls out of it. Both halves carry weight:

  • A DTO field the tool does not accept is not announced. We never advertise a parameter the implementation would ignore — and there is no hand-maintained list of “unimplemented” fields to fall out of date. Absence from the signature is the statement. To expose a new spec field you make the tool accept it, and the announcement follows.
  • A parameter the DTO declares takes the DTO’s type. This is the half that cannot drift: bump the SDK pin and every advertised type moves with it, on every transport, in one commit.

And the corollary that retires legacy names for free: a parameter the DTO does not declare is dropped from the announcement. FastMCP never passes what it does not advertise, so a flat legacy name like list_creatives(status=...) stops working without anyone maintaining a list of retired names.

# src/core/schema_helpers.py — the whole mechanism, twice
accepted_kwargs(impl)                 # what the implementation will take
select_request_fields(model, src, ok) # forward exactly that, nothing else

The request DTO is the vocabulary. There is no plumbing denylist: a key the DTO does not declare is simply not forwarded. No allowlist, no ledger, nothing to keep in sync.

The template

wrapper → builder → DTO → impl

Four steps, and every tool on every transport follows the same four. The builder is the new piece — the single seam each transport constructs the typed request through.

# src/core/tools/accounts.py
def build_list_accounts_request(
    *,
    account: LibraryAccountReference | None = None,
    status: AccountStatus | None = None,
    pagination: PaginationRequest | None = None,
    ...
) -> ListAccountsRequest:               # ← the return annotation IS the declaration
    """The single seam every transport constructs the typed request through,
    so a future request field lands here once instead of in wrapper lockstep."""

That return annotation is load-bearing. request_model_for reads it to find the DTO, which is how a tool’s advertised shape gets derived without anyone naming the model twice.

One hour lost, recorded so you don’t lose it too: a string forward-ref with the import inside the function resolves to nothing. The bytecode scan finds the builder fine — it is the annotation that fails to resolve, and from the outside the two failures look identical. Builder return types must be importable at module scope.
The enforcement

A tool that cannot name its request DTO cannot be registered

This is the difference between the old world and the new one. We did not add a guard that lists tools with an underived shape. We made the underived state unreachable.

def _register_tool(fn, dto=None):
    ...
    if not apply_dto_announced_shape(registered, fn, dto):
        raise RuntimeError(
            f"{tool_name} cannot be registered: no request DTO. Its advertised "
            f"shape is 'DTO fields INTERSECT the implementation's arguments', so "
            f"without a DTO there is nothing to derive from and the tool would "
            f"publish a hand-written shape that can drift from the spec. Give it "
            f"a build_*_request builder, or pass the model explicitly."
        )

It used to fall back silently: the derivation returned False and registration proceeded with the hand-written signature. Five tools quietly kept an underived shape and nothing said so.

The cost is real and it is the point: adding a tool now forces the DTO decision up front, at the moment you have the context to make it — instead of six months later, in a schema diff, in front of a buyer.
Three transports, one derivation

Announcement and acceptance cannot drift, because they are computed from the same two artifacts

What the buyer is told

What we actually take

# REST

The request body, derived from the same pair — and the pair itself is now read off the tool, so neither side names it.

Same intersection, computed twice from the same two inputs, so the answers are equal by construction rather than by inspection. There is no test asserting “the schema matches the body” because there is no way to author a difference.

    with BOTH read off the tool. REST and A2A used to write the pair out per call

The output half

Return the model. Never the dict.

The input story has a mirror on the way out, and it is shorter because it is already enforced. An _impl returns a typed model and never calls .model_dump() — serialization is the transport’s job, because only the transport knows what the wire looks like.

- return result.model_dump()          # impl decides the wire shape → four wire shapes
+ return GetProductsResult(...)       # impl decides the FACTS; transport renders them

The moment an _impl hands back a dict, three things become possible again: the transports serialize it differently, the type checker stops seeing the contract, and a field can be dropped without anything noticing. All three have happened here.

One wrinkle worth knowing: Pydantic serializes a nested child by its declared (library) type, so a parent whose children are local subclasses opts into NestedModelSerializerMixin, the one serializer seat, to re-dump them by instance. That is Pattern #4 in CLAUDE.md; no model overrides model_dump().
Errors, part one — which code

The spec already decided. We were answering three ways.

A malformed request has exactly one correct code, and enums/error-code.json is explicit about where the line falls:

CodeThe pin’s own wordsSo: raised when
INVALID_REQUEST“malformed, missing required fields, or violates schema constraints”a Pydantic ValidationError — by construction always this
VALIDATION_ERROR“invalid field values or violates business rules beyond schema validation”our own logic raising — an unknown format, an unsupported pricing model

REST already answered INVALID_REQUEST. MCP and A2A answered VALIDATION_ERROR for the identical failure. The same buyer sending the same bad field got a different classification depending on how they connected.

Why this took a while to land, and the general lesson. Two generated feature files graded an out-of-enum value with different codes, so any consistent mapping would break one of them. Checking the upstream source rather than the generated copies showed the contradiction is upstream, and broader: enum appears near INVALID_REQUEST in three storyboards and near VALIDATION_ERROR in two others.

“Match upstream” was therefore not an available answer — upstream disagrees with itself. The pinned error-code enum is the tiebreaker. When a generated artifact and the spec prose conflict, go read the prose.

Errors, part two — what the refusal carries

Facts in fields. Not four sentences in a string.

Five different key names — validation_errors, creative_errors, config_errors, adapter_errors, violations — all held list[str], and every string was built by interpolating structured facts into an f-string and throwing the structure away.

f"Adapter does not support '{pricing_model}' pricing. "
f"Supported pricing models: {sorted_supported}. "
f"The requested pricing model ('{pricing_model}') is not available. "
f"Please choose a product with compatible pricing."

Four authored sentences on the buyer’s wire. The last is a suggestion — the field we made a function of the code last quarter, so it was a second and divergent copy of what CODE_TABLE already says. The supported set was a string joined on ", " that a buyer had to split. And with three packages, nothing said which one was refused.

class ErrorProblem(BaseModel):
    code: ErrorCodeT | None                # the SAME vocabulary as the carrying error
    subject_type: Literal["creative", "product", "package", "account"] | None
    subject_id: str | None                 # WHICH package
    field: str | None                      # packages[0].pricing_option_id
    rejected_value: str | None             # the pin's canonical rejection keys
    accepted_values: list[str] | None      # an ARRAY, not a joined string
There is no free-text field, deliberately. A declared class stops field-name drift but not prose inside a declared field — a reason: str slot would just relocate the f-string one level down. And code classifies the problem with the same vocabulary as the error carrying it, rather than a parallel reason enum: one code table for one job, and the buyer renders each problem from CODE_TABLE exactly as they render the error itself.
How any of this is graded

Through the wire, on four transports, from one scenario

The rule that keeps this honest, and it is a hard stop:

If you find yourself writing a new internal guard or unit test to check something about how a tool uses an SDK class — stop. That is the disease this work exists to remove. Behavior is graded through BDD scenario execution only.

A scenario is written once and runs on mcp, a2a, rest and e2e_rest. The assertion is on the envelope the transport actually built, never on a reconstruction:

assert_envelope_shape(result.wire_error_envelope, "INVALID_REQUEST", recovery="correctable")
assert isinstance(exc, AdCPValidationError)   # a reconstruction — can pass vacuously

And the negative assertion that makes the prose deletion permanent — it scans the whole envelope, not one field, because the claim is not “this key is clean” but “the adapter layer has no way to put a sentence on the wire at all”:

rendered = str(result.wire_error_envelope)
for authored in ("Please choose a product with compatible pricing",
                 "Adapter does not support", "is not available"):
    assert authored not in rendered
The same disease, one level up

A tool nobody can find is a tool that does not exist

Deriving shapes from the DTO forced us to ask, for every tool, “which spec tool is this?” That question had never been asked out loud. Asking it found capabilities we had fully implemented and made undiscoverable by naming them ourselves.

A buyer finds a tool by its name. A name that appears in no version of the spec is, from outside, an absence.

We publishThe spec calls itStatusWhat it actually takes
get_tasktasks/get · get_task_statusin 3.1, both namespacesclose to a rename — same required task_id; we also gain three optional fields we already could serve
update_performance_indexprovide_performance_feedbackin 2.5, 3.0 and 3.1rename and reshape — the spec takes one scalar reading per call with a required measurement period; we take a list of per-product indices
list_authorized_propertieslist_property_lists · get_property_list2.5 name; the capability lives on in 3.1 under twoa rename onto real spec operations — one old tool maps to two new ones

The one worth stopping on. A shipped docstring on build_get_task_request states that get_task “appears in neither the pinned 3.1 schema tree nor ADCP_TOOL_DEFINITIONS — so a local DTO is its final shape, not a placeholder waiting for an SDK type.”

The 3.1 tree files it under tasks-get and get-task-status. The lookup that returned “absent” had searched for our name. A negative result became a written architectural conclusion — this shape is final — which closed off three optional spec fields the tool could already have served.

And the inverse: tools we published that the spec never defined

On A2A, tool == skill == RPC route — so a skill the pinned schema does not define has no business on the surface. Six had none anywhere in 3.1: approve_creative, assign_creative, create_creative, get_media_buy_status, optimize_media_buy, get_creatives. Deleted, with their 5 dispatch entries and 3 agent-card advertisements. The A2A surface is spec-only now.

Absence is not evidence when you searched for your own name. Every “the spec doesn’t have this” in a comment or a ticket is only as good as the string that was grepped — and our own vocabulary is the one string guaranteed not to appear in someone else’s document.
The payoff

Every body we derived surfaced a bug that was already shipping

This is the argument for doing it, and it is not theoretical. Deriving a shape does not just prevent future drift — it reveals the drift already there, because the derived shape and the hand-written one disagree out loud instead of silently.

A required field the buyer sent, discarded before anything looked at it

SyncCreativesBody carried idempotency_key, and sync-creatives-request.json lists it in /required — but the REST route omitted it from the call. MCP and A2A both forwarded it, which is exactly why no cross-transport test caught the difference. A malformed key was rejected on two transports and silently accepted on the third: the same request answered two ways depending only on how it arrived.

Two code paths for one concept, one of them fixed years ago

The error pointer carried FastAPI’s location prefix — /body/idempotency_key where the pin wants /idempotency_key. The field key had stripped that for years. issues[] never did. Same fact, two renderings, and only one of them had received the fix. Stripped once now, so both read the same document.

A test list that was a third copy of the roster

The A2A contract test hand-listed the skills, so deleting six from the dispatch map and the agent card left it stale — a copy does not know it is out of date. It reads the agent card now, which is the artifact a buyer actually sees. Deriving it paid on the first run: the hand-copied list had been missing list_accounts and sync_accounts entirely, so their auth contract had never been graded. Grading them showed the two legitimately differ — list_accounts permits an unauthenticated call and returns an empty list; sync_accounts writes, and rejects one.

A payload that outlived the field it names

A test still sent "budget": 15000.0 under the comment “Float per AdCP spec, not Budget object”. True of 2.x — which is precisely why it survived. 3.1.1 defines no top-level budget at all, so the request was refused before reaching the assertions and surfaced as a KeyError on an unrelated key.

Read the last one twice. The comment was not wrong when it was written, and that is what made it durable. A statement about the spec with no version attached becomes false silently, on someone else’s release schedule — and the code around it keeps passing until something forces the question.

Monday

What to do differently

  1. Adding a tool? Name the request DTO first. Write build_<tool>_request returning the SDK type, with the return annotation importable at module scope. Registration refuses anything else, so this is not advice — it is the only path.
  2. Never write a request shape twice. If you are typing field names into a REST Body or a signature, and the SDK ships a DTO for that tool, you are creating the drift this whole deck is about. derived_body_model_for(tool) on REST, select_request_fields_for(tool, bag) on A2A — name the TOOL, never its DTO and builder.
  3. Exposing a new spec field = making the impl accept it. There is no second place to update. No ledger, no unsupported map, no announcement to edit.
  4. Before writing “the spec doesn’t have this” — grep the spec’s vocabulary, not ours. Search the schema tree by capability (task, performance, propert), not by our tool name. A tool published under a name that is in no spec version is undiscoverable, and that is a compliance defect, not a cosmetic one.
  5. Never write a claim about “the spec” without a version. “Float per AdCP spec, not Budget object” was true when written and false by 3.1.1 — and nothing failed until a derivation forced the question. Cite the version, or do not write the comment.
  6. Schema violation is INVALID_REQUEST. Business rule is VALIDATION_ERROR. If a Pydantic model raised it, it is the first one. Always. On every transport.
  7. Put facts in ErrorProblem, never in a sentence. If you are reaching for an f-string to describe a rejection, the fields you are interpolating are the fields the buyer wanted. Ship those.
  8. Grade it with a BDD scenario on the wire envelope. Not a unit test about how a tool uses an SDK class. If the behavior is not observable through BDD, it is an integration test — and nothing else.
  9. When two artifacts can drift, do not add a checker. Derive one from the other and delete the checker. Three guards died that way this month; that is the shape of a real fix.
