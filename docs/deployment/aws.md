# AWS deployment (ECS Fargate, RDS, ALB)

This guide deploys a multi-tenant sales agent on AWS with Terraform: the application on ECS
Fargate, PostgreSQL on RDS, TLS on an Application Load Balancer, secrets in Secrets Manager,
and the reference creative agent as a second Fargate service. The Terraform lives in
[`deploy/aws/terraform/`](../../deploy/aws/terraform/).

The deployment below was run end to end on 2026-10-01 in `eu-central-1` against a real
account, verified over HTTPS, and then destroyed. The commands are the ones that run used,
with local image names generalized; Terraform ran as `docker run hashicorp/terraform:1.14`.
Where a step depends on a fix that is still an open pull request, the step says so.

## What you get

```
                 Route53: <domain>, *.<domain>, custom tenant hosts
                                    |
                    ALB :443 (ACM: <domain> + *.<domain>, one cert per custom domain)
                    |                                   |
  creative.<domain>/api/creative-agent*        every other host and path
                    |                                   |
     Fargate: reference creative agent        Fargate: sales agent (image nginx :8000
       (adcp at ADCP_PIN, :8080)                -> MCP, A2A, Admin on :8080)
                    \                                   /
                     RDS PostgreSQL 17 (not public): adcp_registry, salesagent
```

- **Network**: the default VPC's public subnets and no NAT gateway. Tasks get a public IP
  for outbound traffic; security groups admit traffic to a task only from the ALB, and to
  the database only from the tasks.
- **Hosts**: the apex serves signup and the Admin UI, `admin.<domain>` the Admin UI,
  `creative.<domain>` only the creative agent's API, and any other `<name>.<domain>` a
  subdomain tenant. A wildcard DNS record and a wildcard certificate mean a new subdomain
  tenant needs no DNS or certificate change.
- **Posture**: `ENVIRONMENT=production`, `ADCP_TESTING=false`. Formats come from the
  self-hosted creative agent through `CREATIVE_AGENT_URL`, over public HTTPS.
- **Secrets**: generated by Terraform (database passwords, `ENCRYPTION_KEY` as a Fernet
  key, `FLASK_SECRET_KEY`, the signing KEK, the creative agent's token secret), stored in
  three Secrets Manager secrets, and injected by ECS at task start.
- **Logs**: one CloudWatch log group per task family.
- Every resource carries the tag `Project=<project>`.

## Before you start

- An AWS account and credentials for the AWS CLI v2. The guide uses the default VPC of the
  region.
- A Route53 hosted zone that holds the deployment domain.
- Terraform 1.9 or later, Docker, `jq`.
- About 30 minutes, most of it the creative agent image build and RDS creation (about 7
  minutes).

## Step 1: Build the two images

Fargate runs `linux/amd64` by default; build on, or for, that platform.

```bash
git clone https://github.com/prebid/salesagent.git && cd salesagent
docker build -t salesagent/app:$(git rev-parse --short HEAD) .

# The reference creative agent, from the pin this repo tests against (about 10 minutes)
PIN=$(sed -n 's/^ADCP_PIN="\(.*\)"/\1/p' scripts/creative-agent-stack.sh)
mkdir -p /tmp/adcp-$PIN
curl -sLf https://github.com/adcontextprotocol/adcp/archive/$PIN.tar.gz | tar xz -C /tmp/adcp-$PIN --strip-components=1
docker build -t salesagent/creative-agent:$PIN /tmp/adcp-$PIN
```

## Step 2: Configure Terraform

```bash
cd deploy/aws/terraform
cp terraform.tfvars.example terraform.tfvars
```

Set at least `domain`, `route53_zone_id`, `app_image_tag` (the tag from Step 1),
`creative_agent_image_tag` (the pin) and `super_admin_emails`. The verified run used:

```hcl
project         = "salesagent-aws-guide"
region          = "eu-central-1"
domain          = "aws-sa.noetis.dev"
route53_zone_id = "Z0123456789EXAMPLE"
custom_domains = {
  "shop.awsglossary.noetis.dev" = { route53_zone_id = "Z0123456789EXAMPLE" }
}
app_image_tag            = "noetis-339d1d27"
creative_agent_image_tag = "76b031a85eb8"

# Throwaway deployment only: destroy must leave nothing behind.
db_deletion_protection      = false
db_skip_final_snapshot      = true
secret_recovery_window_days = 0
ecr_force_delete            = true
```

Leave the last four at their defaults for a deployment you keep. The state file holds every
generated secret in plain text; for anything shared, configure an S3 backend.

## Step 3: Create the registries and push

The services cannot start until their images exist, so create the two ECR repositories
first:

```bash
terraform init
terraform apply -target=aws_ecr_repository.this

REGISTRY=$(terraform output -json ecr_repositories | jq -r .app | cut -d/ -f1)
aws ecr get-login-password --region eu-central-1 | docker login --username AWS --password-stdin $REGISTRY
docker tag salesagent/app:<tag> $(terraform output -json ecr_repositories | jq -r .app):<tag>
docker push $(terraform output -json ecr_repositories | jq -r .app):<tag>
docker tag salesagent/creative-agent:$PIN $(terraform output -json ecr_repositories | jq -r '."creative-agent"'):$PIN
docker push $(terraform output -json ecr_repositories | jq -r '."creative-agent"'):$PIN
```

## Step 4: Apply

```bash
terraform apply
terraform output -json > outputs.json   # read by deploy/aws/run-task.sh
```

This creates about 70 resources. The certificates validate through Route53 records that
Terraform adds, so the apply finishes without manual steps. Both services start right away
and fail their first attempts until Step 5 creates their databases; ECS keeps retrying.

## Step 5: Create the databases

A one-off task (`postgres:17-alpine` from ECR Public) connects as the RDS master user,
creates the roles `salesagent` and `creative_agent` and a database owned by each, and
exits. It is safe to re-run.

```bash
../run-task.sh db-admin
# CREATE ROLE / CREATE ROLE / ALTER ROLE / ALTER ROLE / GRANT ROLE /
# CREATE DATABASE / CREATE DATABASE / REVOKE / databases ready / exit code: 0

for s in app creative-agent; do
  aws ecs update-service --region eu-central-1 --cluster $(jq -r .cluster.value outputs.json) \
    --service $s --force-new-deployment
done
```

The sales agent runs its migrations when the container starts. On an empty database they
took about 15 seconds; the log group shows `✅ Migrations complete` and, with no demo
flags, one blank `default` tenant at the apex.

```bash
aws logs tail /ecs/<project>/app --region eu-central-1 --since 10m | grep -E "Migrations complete|Database initialization"
```

## Tenants and publishers

A tenant is a seller: one sales agent, served at one URL. The URL's host is the tenant's
`virtual_host`.

A tenant is not a publisher. One tenant sells for many publisher sites, hundreds in
production. Each site authorizes the tenant by serving `/.well-known/adagents.json` on its
own domain, with an `authorized_agents` entry whose `url` is the tenant's URL. The tenant
holds the site as an authorized property (Admin UI, **Authorized Properties**) and verifies
it against that file.

The recommended tenant host is on the seller's own domain, for example `sales.acme.com`. A
subdomain of `<domain>`, such as `acme.<domain>`, also works.

`custom_domains` (Step 2) is the list of tenant hosts outside `<domain>`: one entry per
tenant on its own domain, each with its own ACM certificate on the listener. Publisher sites
never go in it.

- Adding a tenant on its own domain takes one `custom_domains` entry, the DNS record that
  points its host at the ALB (plus ACM's validation record, see
  [Tenant TLS](#tenant-tls-and-custom-domains)), and the tenant's `virtual_host`. A subdomain
  tenant takes only the `virtual_host`: the wildcard record and certificate cover it.
- Adding a publisher site to a tenant changes no DNS record, no certificate and no Terraform.

The app finds the tenant by matching the request's host against its `virtual_host`.

## Step 6: Create a tenant

`deploy/aws/run-task.sh app <command>` runs any command in the application image with the
service's environment and secrets. It uses a second task definition, `<project>-app-task`,
because the image's entrypoint starts the whole server and `run-task` can replace the
command but not the entrypoint.

```bash
# A subdomain tenant
../run-task.sh app python scripts/setup/setup_tenant.py "Tenant One" \
  --tenant-id t1 --virtual-host t1.aws-sa.noetis.dev --adapter mock

# A custom-domain tenant (its certificate is in custom_domains, see Tenant TLS below)
../run-task.sh app python scripts/setup/setup_tenant.py "AWS Glossary Shop" \
  --tenant-id awsglossary --virtual-host shop.awsglossary.noetis.dev --adapter mock
```

The script creates the tenant, its USD/EUR/GBP limits and a principal, and prints the
principal's token. **The token goes to the task's log, so it is stored in CloudWatch.**
Copy it, then delete that log stream, or create principals in the Admin UI instead, which
shows a token once and logs nothing.

A new tenant has no products, so `get_products` returns an empty list until you add some in
the Admin UI (**Products**). For the verified run, one product was seeded with the repo's
seeding helper to make the check meaningful:

```bash
../run-task.sh app python -c '
from decimal import Decimal
from scripts.setup.seed_products import seed_product
from src.core.database.database_session import get_db_session
from src.core.database.models import AuthorizedProperty, PropertyTag
T = "t1"
with get_db_session() as s:
    s.add(PropertyTag(tag_id="all_inventory", tenant_id=T, name="All inventory", description="Every property"))
    s.add(AuthorizedProperty(property_id="example_com", tenant_id=T, property_type="website", name="example.com",
        identifiers=[{"type": "domain", "value": "example.com"}], tags=["all_inventory"],
        publisher_domain="example.com", verification_status="verified"))
    seed_product(s, T, {"product_id": "t1_display_ros", "name": "Run of site display",
        "description": "Display on every page of example.com",
        "formats": [{"agent_url": "https://creative.adcontextprotocol.org", "id": "display_300x250_image"}],
        "targeting_template": {}, "delivery_type": "non_guaranteed",
        "pricing": {"model": "cpm", "rate": Decimal("5.00"), "is_fixed": True}})
    s.commit()
print("seeded")'
```

## Admin login

Production mode has no test login. Give the deployment an OIDC provider through
`app_environment` and `app_secrets` (see [environment variables](environment-variables.md)):

```hcl
app_environment = {
  OAUTH_DISCOVERY_URL       = "https://accounts.google.com/.well-known/openid-configuration"
  OAUTH_CLIENT_ID           = "....apps.googleusercontent.com"
  GOOGLE_OAUTH_REDIRECT_URI = "https://<domain>/admin/auth/google/callback"
}
app_secrets = {
  OAUTH_CLIENT_SECRET = "..."
}
```

`app_secrets` go into the app secret in Secrets Manager; any other secret variable
(`GEMINI_API_KEY`, `GAM_OAUTH_CLIENT_SECRET`, ...) goes there the same way. The verified run
configured no provider and checked only that the Admin UI redirects to its login page.

## Tenant TLS and custom domains

Subdomain tenants are covered by the `*.<domain>` certificate and DNS record. A tenant on
the seller's own domain (`sales.acme.com`) needs a certificate for that name. Three ways to
do it on AWS:

| | (a) ACM certificate per domain on the ALB | (b) CloudFront SaaS Manager | (c) Caddy on-demand TLS on Fargate |
|---|---|---|---|
| How | One ACM certificate per custom domain, added to the HTTPS listener (SNI) | A multi-tenant distribution in front of the ALB; each tenant is a distribution tenant with a CloudFront-managed certificate | Caddy behind an NLB (TCP passthrough) obtains a Let's Encrypt certificate on first connection, after asking the app's `/tls/ask` (#2313) |
| Tenant's DNS | Validation CNAME + CNAME to the ALB | CNAME to the CloudFront endpoint | A record to the NLB's Elastic IPs, or a CNAME |
| Apex domain (`acme.com`) | Only if the tenant's DNS supports ALIAS/flattening (the ALB has no fixed IP) | Same | Yes (Elastic IPs) |
| Per-domain operator step | Add the domain to `custom_domains` and apply | Create a distribution tenant (API call) | None: setting the tenant's `virtual_host` is enough |
| Limits | 25 certificates per ALB by default, raisable to 100 | Designed for large tenant counts | Let's Encrypt rate limits; certificate storage must persist (EFS or S3) or every task restart re-issues |
| Extra cost | None | 10 tenants free, then $20/month up to 200, then $0.10 per tenant; plus CloudFront traffic | NLB (about $20/month) + a Caddy task (about $10/month) + EFS |
| Extra parts | None | CloudFront in front of MCP's streaming responses (origin timeouts, caching rules) | NLB, Caddy, certificate storage, and a second TLS path beside the ALB |

**Recommendation: (a)**, and it is what this Terraform does and what the verified run
used. It adds nothing that runs or bills, keeps every certificate in ACM with automatic
renewal, and holds 25 tenants on their own domains by default (100 after a quota increase),
plus any number of subdomain tenants. Move to (c) when tenants must onboard a domain without
an operator, or need apex domains; move to (b) when tenants on their own domains number in
the hundreds.

The ALB and CloudFront options hold a certificate for each configured domain and never ask
the app about a host, so this Terraform leaves `TLS_ASK_ENABLED` unset and `/tls/ask`
answers 404. Option (c) needs it: set `TLS_ASK_ENABLED=true` in the app task's environment,
or Caddy's ask request gets 404 and Caddy refuses every certificate.

To add a custom domain:

1. Add it to `custom_domains`. If this account hosts its zone, give `route53_zone_id` and
   Terraform creates both records itself; skip to step 4.
2. Otherwise create the certificate on its own and hand the records to the domain owner:

   ```bash
   terraform apply -target='aws_acm_certificate.custom["sales.acme.com"]'
   terraform output -json custom_domain_dns
   ```

3. The owner publishes the validation CNAME and `sales.acme.com CNAME <alb_dns_name>`.
4. `terraform apply`. It waits (up to 2 hours) for ACM to issue the certificate, then adds
   it to the listener.
5. Set the tenant's `virtual_host` to the domain (`setup_tenant.py --virtual-host`, or the
   Admin UI).

In the verified run, `shop.awsglossary.noetis.dev` was served with its own certificate
(`CN=shop.awsglossary.noetis.dev`, issued by Amazon) next to the wildcard
(`aws-sa.noetis.dev, *.aws-sa.noetis.dev`) on the same listener.

## Operations

- **Upgrade**: build and push a new tag, set `app_image_tag`, `terraform apply`. The app
  service runs one task and replaces it stop-first (`deployment_minimum_healthy_percent =
  0`) so two containers never run migrations at once; expect a minute or two of 503s.
  Take an RDS snapshot first when a release carries migrations.
- **Creative agent**: rebuild only when `ADCP_PIN` in `scripts/creative-agent-stack.sh`
  moves, then set `creative_agent_image_tag`.
- **One-off commands**: `deploy/aws/run-task.sh app <command>`, for example
  `python scripts/ops/check_tenants.py`.
- **Logs**: `aws logs tail /ecs/<project>/app --follow`.
- **Backups**: RDS automated backups (`db_backup_retention_days`, 7 by default) and a final
  snapshot on destroy unless `db_skip_final_snapshot` is set.
- **Secrets**: never let Terraform replace `random_bytes.encryption_key` or
  `random_password.signing_kek` on a live deployment. Both decrypt stored data (OIDC
  secrets, adapter credentials, tenants' signing keys); a new value strands all of it.
- **Scaling out**: the app runs one task. Before raising `desired_count`, move migrations
  into a one-off task (`SKIP_MIGRATIONS=true` on the service) and check that the
  in-process schedulers tolerate several copies.

## Gotchas

Each of these came up in the verified run.

- **One-off tasks need their own entrypoint.** The image's `ENTRYPOINT` is
  `run_all_services.py`; `run-task --overrides` replaces only the command, so a tenant-setup
  "command" started a second full server that never exited. The `app-task` task definition
  sets `entryPoint = ["/usr/bin/env"]`.
- **RDS refuses unencrypted connections** (PostgreSQL 15+ sets `rds.force_ssl`). The app's
  `DATABASE_URL` ends in `?sslmode=require`; the creative agent's pg client ignores
  `sslmode` and reads `DATABASE_SSL=true` (plus `DATABASE_SSL_REJECT_UNAUTHORIZED=false`,
  because the RDS CA is not in Node's trust store; supply it with `NODE_EXTRA_CA_CERTS` to
  verify). The `db-admin` task sets `PGSSLMODE=require`.
- **PostgreSQL 16+ `CREATE DATABASE ... OWNER x`** needs the creating role to be a member
  of `x`. The RDS master user is not a superuser, so the init script grants itself both
  roles first.
- **The creative agent runs with `NODE_ENV=development`.** Since adcp v3.1.1 it refuses
  its `DEV_USER_*` auth bypass under `production`, and without the bypass it needs WorkOS.
  The ALB forwards only `/api/creative-agent*` on `creative.<domain>` and answers 404 for
  the rest.
- **The app reaches the creative agent over its public HTTPS name**, through the ALB.
  Outbound HTTP goes through the egress gateway, which refuses private addresses, so a
  service-discovery address inside the VPC would not work without
  `ADCP_OUTBOUND_ALLOW_PRIVATE`.
- **The first creative agent call waits about 5 seconds.** The client tries the base URL
  as MCP, gets a 403, and connects to `<url>/mcp` (#2315); later calls reuse the result.
- **Memory**: the app used about 1.25 GB of its 2 GB at idle; a 1 GB task is too small. The
  creative agent used about 600 MB of 1 GB.
- **MCP streaming** holds responses open; the ALB idle timeout is 300 seconds instead of 60.
- **The ALB's HTTP-to-HTTPS redirect** includes `:443` in the `Location` header. Harmless.
- **Wildcard DNS sends every name under the domain to the app.** A name that is no
  tenant's `virtual_host` gets an error response from the app, not a tenant.

## Cost

On-demand prices in `eu-central-1` (AWS Price List API, 2026-10-01), 730 hours a month, light
traffic:

| Item | Size | Per month |
|---|---|---|
| Fargate, sales agent | 1 vCPU, 2 GB | $41.45 |
| Fargate, creative agent | 0.5 vCPU, 1 GB | $20.72 |
| RDS PostgreSQL | db.t4g.micro, single-AZ | $13.87 |
| RDS storage | 20 GB gp3 | about $2.75 |
| ALB | hourly + about 1 LCU | $25.55 |
| Public IPv4 addresses | 2 tasks + 3 ALB nodes, $0.005/hour each | $18.25 |
| Secrets Manager | 3 secrets | $1.20 |
| CloudWatch Logs | about 2 GB ingested | about $1.30 |
| ECR | about 1.6 GB stored | $0.16 |
| **Total** | | **about $125** |

Ways to spend less: run the creative agent on Fargate Spot; build `linux/arm64` images and
run on Graviton (about 20% less for Fargate); place the ALB in two subnets instead of three
(one IPv4 address less). A Multi-AZ database roughly doubles the RDS lines. For comparison,
a single small EC2 instance running the Docker Compose stack costs $15 to $20 a month, with
the operations work that implies.

The verified run was up for about 40 minutes and cost well under a dollar.

## Teardown

```bash
terraform destroy
```

With `db_deletion_protection = false`, `db_skip_final_snapshot = true`,
`secret_recovery_window_days = 0` and `ecr_force_delete = true`, this removed all 70
resources in about 3 minutes: the database, the ECR repositories with their images, the
secrets (deleted without a recovery window), the log groups, the certificates and the
Route53 records. Check afterwards:

```bash
aws resourcegroupstaggingapi get-resources --region eu-central-1 --tag-filters Key=Project,Values=<project>
aws secretsmanager list-secrets --region eu-central-1 --include-planned-deletion --filters Key=name,Values=<project>
aws rds describe-db-snapshots --region eu-central-1 --query "DBSnapshots[?contains(DBSnapshotIdentifier, '<project>')]"
```

What stayed listed after the destroy, and how it resolved:

- The tagging API kept listing the deleted security group rules and the INACTIVE ECS
  cluster and services; `describe` calls on them confirm they are gone, and none of them
  bills.
- `terraform destroy` deregisters task definitions but leaves them INACTIVE. Delete them
  with `aws ecs delete-task-definitions --task-definitions <family>:<revision> ...`.
- The automated RDS snapshot (`rds:<project>-<date>`) stayed listed for about 30 minutes
  after the instance was deleted. It cannot be deleted by API (`automated snapshots cannot
  be deleted`); RDS removed it on its own.
