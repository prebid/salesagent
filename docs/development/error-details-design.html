How a buyer-facing error.details block is built, what AdCP 3.1.1 actually mandates, and the class structure that makes a wrong one unconstructible.

TodayHow details are sent now

An error's details is a free-form dict, assembled inline at the raise site. There is no declaration anywhere of what keys an error may carry, so the key name is the contract — and it drifts.

# src/core/tools/media_buy_create.py, before conversion
raise AdCPValidationError(details={"validation_errors": validation_errors})
raise AdCPValidationError(details={"config_errors": config_errors})
raise AdCPValidationError(details={"adapter_errors": pre_creation_errors})
raise AdCPCreativeRejectedError(details={"creative_errors": detail_msgs})
raise AdCPValidationError(details={"violations": violations})

Five key names, one concept: a list of problems. And every one of those lists is list[str], built by interpolating structured facts into an f-string and discarding the structure:

# src/core/helpers/creative_helpers.py:583
detail_msgs = [f"{r.creative_id}: {err.message}" for r in failed_results for err in (r.errors or [])]

# src/core/tools/media_buy_create.py:486
validation_errors.append(
    f"Creative {cid} has format '{creative_fmt}' which is not accepted by "
    f"product {package.product_id} (accepted formats: {sorted(accepted)})"
)

The measured drift. An AST survey of all 173 sites found AdCPValidationError alone carrying 30 distinct key sets across 34 sites. AdCPCapabilityNotSupportedError: 15 across 28. AdCPConfigurationError: 14 across 19. AdCPCreativeRejectedError: 10 across 16.

A buyer receiving {"creative_errors": ["cre_123: missing url"]} must apply a regular expression to learn which creative failed.

The second channel nobody closed

The epic locked message, suggestion, and recovery to CODE_TABLE so no raise site could author buyer-facing text. details is a second channel to the same buyer, and it was never covered:

# src/adapters/base.py:410 -- four authored sentences, the last one a SUGGESTION,
# which is the exact field the epic made a function of the code
errors.append(
    f"Adapter does not support '{pricing_model}' pricing. "
    f"Supported pricing models: {sorted_supported}. "
    f"The requested pricing model ('{pricing_model}') is not available. "
    f"Please choose a product with compatible pricing."

SpecWhat AdCP 3.1.1 actually mandates

Two places in the pin govern this, and they answer different questions.

1. core/error.json — the error object

PropertyRequiredWhat it is
codeyesOpen vocabulary; the discriminator a buyer switches on
messageyesHuman-readable. This repo derives it from CODE_TABLE
fieldnoJSONPath-lite pointer, e.g. packages[0].targeting
suggestionnoDerived from CODE_TABLE
retry_afternoSeconds; first-class, not a details key
issuesnoStructured list of validation failures. The canonical multi-field channel
detailsnotype: object, additionalProperties: true. Task-specific specifics
recoverynotransient / correctable / terminal. Derived from CODE_TABLE

The finding that changed the design. issues[] is the pin's canonical channel for multi-field rejection, and our first-pass catalog invented a parallel one. Quoting the schema:

“Structured list of validation failures. Primary use is VALIDATION_ERROR, where multi-field rejections are common and field (singular) cannot carry the full pointer map.”

Item schema: required: ["pointer", "message", "keyword"], additionalProperties: true. Plus optional schemaPath, schema_id, discriminator.

And a MUST on the seller: “When issues is present, sellers MUST also populate field from issues[0] … translating the RFC 6901 pointer format to the JSONPath-lite format field uses.”

What pointer is

RFC 6901 JSON Pointer is a string that addresses one value inside a JSON document: a sequence of tokens, each prefixed by /, where each token is an object member name or an array index.

/packages/0/targeting/geo_countries/2
 └─ root's "packages" member → element 0 → "targeting" → "geo_countries" → element 2

""            the whole document
/a~1b         a member literally named  a/b     ( / escapes to ~1 )
/m~0n         a member literally named  m~n     ( ~ escapes to ~0 )

The escaping is why the pin chose it over the JSONPath-lite form that field uses. packages[0].targeting becomes ambiguous the moment a key contains a dot or a bracket; /packages/0/targeting never does. The pin also notes it matches Ajv's instancePath, so a JSON Schema validator's output drops straight in.

Canonical rejection-set keys. core/error.json's details description names the shape for “enum mismatch, unsupported pricing option, invalid signal id”: rejected_value and accepted_values, explicitly “rather than seller-specific variants observed in the wild (available, allowed…)”. SHOULD-level, and we adopt it.

Caution. Do not import a pinned shape's key under a code the pin does not associate with it. A site emitting VALIDATION_ERROR may not borrow minimum_budget from budget-too-low.json.

TargetThe class structure

Five rules, in dependency order. Each removes a way to be wrong rather than adding a check that catches it.

Rule 1 — the exception owns the code; a shape owns nothing but fields

The exception class is the authority on which code it is. A detail shape names no code, which is exactly why one shape can serve several errors, and sharing is preferred over copying.

class AdCPError[DetailsT: ErrorDetails](Exception):
    _code: ClassVar[ErrorCodeT]
    def __init__(self, *, details: DetailsT | None = None, field=None,
                 retry_after=None, context=None, internal_detail=None) -> None: ...

class AdCPPackageNotFoundError(AdCPNotFoundError[EntityRefDetails]): ...   # PACKAGE_NOT_FOUND
class AdCPGamUpdateError(AdCPAdapterError): ...                            # AD_SERVER_UPDATE_FAILED

One __init__ on the base gives all 31 classes their own exact detail type. mypy rejects both a dict and a foreign shape at every raise site, and exc.details reads back typed. Parameterizing rather than overriding __init__ 31 times is what keeps this free of the copy-paste the DRY invariant forbids.

Why the code is not on the shape. An earlier draft had the shape name its code and the exception adopt it. That inverted the authority: {package_id, media_buy_id} legitimately serves both AdCPPackageNotFoundError and AdCPGamUpdateError, and {creative_id} already appears under three classes. A code on the shape forces one shape copy per error. It also required a runtime check that the two halves agreed — a check that existed only to catch a contradiction the duplication created.

Rule 2 — no authored prose, at any level

A declared class stops field-name drift. It does not stop prose inside a declared field: a reason: str slot is just a new home for the f-string. So no shape declares a free-text field, and classification uses code drawn from the existing 100-code vocabulary — never a parallel reason enum.

class ErrorProblem(BaseModel):
    code: ErrorCodeT | None = None
    subject_type: Literal["creative","product","package","account"] | None = None
    subject_id: str | None = None
    field: str | None = None
    rejected_value: str | None = None          # pin-canonical
    accepted_values: list[str] | None = None   # pin-canonical

Rule 3 — required prose is derived, never authored

Each issues[] item requires message, so it cannot be omitted. The pin requires the field to be present; it does not require a human to write it. That is the same situation as the top-level message, which this epic already made a function of the code.

class ErrorIssue(LibraryIssue):                 # extends adcp.types...core.error.Issue
    model_config = ConfigDict(extra=get_pydantic_extra_mode(), frozen=True)

    pointer: str                                # built by JsonPointer, never a literal
    keyword: JsonSchemaKeyword                  # Literal of the JSON Schema vocabulary
    code: ErrorCodeT                            # our classification -> derives message
    rejected_value: str | None = None           # legal extras, still typed
    accepted_values: list[str] | None = None
    # NO `message` parameter exists. A mode="before" validator resolves it from
    # (code, keyword) -- the mechanism Error._derive_graded_fields already uses.

One policy, not two. A buyer-facing sentence is derived from a table and never authored at a raise site — now at both the error level and the item level. The 11-agent design review rejected this routing on the grounds that rule 2 forbids a prose field; that reads rule 2 as “no prose field” when it means “no authored prose.”

additionalProperties: true on the item is what lets the typed fields sit alongside the pinned keys rather than being displaced. The property that matters survives: a caller cannot populate this except by instantiating a typed class.

Rule 4 — a pointer is a value type, not a string

The pin's MUST (populate field from issues[0].pointer, translated) must not be satisfied by hand at raise sites — that is the drift this migration removes. One value type owns both renderings:

JsonPointer.of("packages", 0, "targeting")
    .pointer   ->  "/packages/0/targeting"       # issues[].pointer  (RFC 6901)
    .field     ->  "packages[0].targeting"       # top-level field   (JSONPath-lite)

It owns the ~0/~1 escaping, so a member named a/b round-trips. field is then derived, never typed twice. Cross-check against the existing JSONPath-lite producer, first_validation_error_field().

Rule 5 — compose, never redeclare

Because a shape names no code, one shape serves every error whose details answer the same question. The AST survey found 11 key-sets already duplicated across unrelated classes — {account_id} under four, {media_buy_id} and {product_id} under three each.

class EntityRefDetails(ErrorDetails):        # WHICH entity: account_id, media_buy_id,
    ...                                      #   package_id, product_id, creative_id, ...
class UpstreamCallDetails(ErrorDetails):     # what the upstream did: status, status_code, url
class ProblemsDetails(ErrorDetails):         # problems: list[SerializeAsAny[ErrorProblem]]

class AdapterFailureDetails(EntityRefDetails, UpstreamCallDetails, ProblemsDetails):
    """All three axes, by composition. Zero fields redeclared."""

VerificationHow the BDD side checks it

Construction is typed; assertion is on the wire. Those are different layers and the asymmetry is deliberate — a test that asserted on a reconstructed Python object would be proving serializer self-consistency, not what the buyer received.

# tests/harness/transport.py -- the ONE way to assert an error
result.assert_wire_error(
    "SERVICE_UNAVAILABLE",
    recovery="transient",          # required keyword: pins buyer retry semantics
    field="packages[0].budget",
    details={"media_buy_id": "mb_1"},   # subset membership on the wire dict
    retry_after=30,
)

Every scenario runs across mcp / a2a / rest / e2e_rest. recovery is a required keyword, not a soft default. And a structural guard with no allowlist, test_architecture_one_wire_error_assertion.py, bans the older two-step spelling so there is exactly one way to assert an error.

Gap: the assertion layer cannot grade issues[] yet. A scan of both helpers finds details mentioned 16 and 19 times respectively, and issues zero times. Until assert_wire_error takes an issues= keyword, every issues[] scenario would pass vacuously. That is part of salesagent-rys3u.6, not a follow-up: an ungraded channel is indistinguishable from an absent one.

Prerequisites before any further conversion

  1. ProblemsDetails.problems must become list[SerializeAsAny[ErrorProblem]]. Without it a subclass passes to_wire() with its own fields silently dropped — a warning in CI, field loss in production.
  2. A to_wire() key-set test must land before editing the two committed shapes. Re-basing AdapterFailureDetails moves serialization order.

Known hole in what has already landed

EntityRefDetails is both a shared base and the type parameter of ~10 error classes, so ProductRefDetails and any future descendant is silently assignable at those raise sites. The narrowing is weaker than claimed for those specific classes. Each new family gets a zero-field leaf to stop the pattern spreading; repairing the committed ones is a follow-up.

Blocked on the spec-grounding gate

Five decisions are protocol behavior, not shape design: whether CONFIGURATION_ERROR may carry details at all (the pin defines no shape for it); UPDATE_ACTIONS intersecting the pinned media-buy-valid-action enum in zero members; whether below-minimum-budget sites should raise BUDGET_TOO_LOW rather than VALIDATION_ERROR; no pinned code for a cardinality refusal; absent-versus-malformed URL distinguishability.
