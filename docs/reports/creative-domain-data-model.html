The creative domain, and the data model it implies

Three layers — what the SDK gives, what the creative domain is, how this app should store it. Measured against v9.0.0-beta.1 + PRs #1435 and #1415, spec 3.2.1. Companion to Creative formats: the spec model, the measured gaps, the design, which this does not restate.

The question is how to represent creatives, formats, products and metrics now that the creative domain is canonical-first. The short answer: one identity, stored once, keyed on the canonical kind — and three of the four entities currently store something else.

1. What the SDK gives

Three surfaces, and knowing which to sit on is most of the design:

SurfaceShapeUse
adcp.types.domains.* (generated) both arms optional, XOR enforced the 3.x compatibility window — where this seller belongs
adcp.types.Legacy* (52 types) identical to generated on identity not a format_id-only surface; no reason to prefer it
adcp.types.canonical_creative format_id deleted, format_kind required the 4.0-ready surface; adopting it drops the legacy arm the 3.x window requires

The resolution layer already exists

This is the single most load-bearing measurement in this document, because the companion report's gap G2 reads "no resolution machinery exists at all" — and that is a gap in our wiring, not something to build:

adcp/_schemas/3.2/registries/v1-canonical-mapping.json   the normative v1↔v2 mapping
load_default_registry()                                  parses it
resolve_legacy_format_refs(declaration, resolver=...)     "without ever reverse-guessing"
LegacyFormatConverter · CanonicalFormatLegacyResolver     the projection seam
is_canonical_format_kind(value, vocabulary)               the vocabulary check

What the SDK deliberately does not do

format_kind is an open str on every model, in both directions, and the SDK never validates it. From the helper's own docstring:

“it is a PARAMETER, because the set that matters is the seller's, not this SDK's… refusing [a kind defined after the pin] would make this SDK's version a ceiling on what the protocol permits. ‘I accept the request and then tell you I cannot process this creative’ is a seller's answer, not a type error.”

So the vocabulary check is this seller's, and the seller's supported set is a real input — a tenant column or an adapter capability — not the pin's sixteen. Defaulting to the pin is a ceiling, and today that default is all we have.

2. The creative domain

One rule governs everything downstream, and it is not a preference:

v1 -> v2   RESOLVES, through a six-step normative order in v1-canonical-mapping.json
v2 -> v1   DOES NOT. "SDKs MUST NOT synthesize a v1 format_id from the registry by
           inverting structural matches" — the registry's slugs lack the agent_url half,
           and glob/structural entries have no single literal to invert to.

Because the projection runs one way only, the canonical kind is the only representation every layer can share. Which fixes the roles:

MemberRole
format_kindTHE identity. What business logic keys on, what is compared, what is stored as identity.
format_idA retained buyer assertion: stored verbatim, echoed on the legacy wire, never the thing logic keys on.
format_option_refNarrows the kind to a concrete option. REQUIRED when the kind alone is ambiguous in the enclosing product context.

The consequence worth stating plainly: the isinstance branch belongs at exactly one place — the edge where an inbound legacy identity is projected to a kind. Carrying two co-equal arms inward makes every consumer branch, which is the shape to remove.

A current implementation detail that contradicts this: creative_format_identity() returns a union of two frozen types and the repository branches on it. That was built to the "state mirrors input" reading, which the spec supports for the WIRE but not for internal representation. The accessor stays; what it returns should be a kind plus a retained assertion.

3. The data model this implies

Creatives

Today one identity is spread across three partial columns and reassembled on read:

agent_url          String(500)   the legacy arm's first half
format             String(100)   its second half
format_parameters  JSON          FormatId's OTHER FOUR declared fields, as a loose blob
format_kind        String(100)   added this session
format_option_ref  JSON          added this session

That is three representations of one value, and the reassembly is where pixel_ratio was being dropped — the blob did not know which fields the model needed. The faithful shape is the domain's:

format_kind        the identity          NOT NULL once backfilled
format_option_ref  JSON, nullable        the option that narrows it
legacy_format_id   JSON, nullable        the retained buyer assertion, ONE faithful value
                                         (agent_url + id + all declared parameters)

agent_url, format and format_parameters collapse into legacy_format_id. A FormatId goes in and comes back out; nothing is decomposed, so nothing can be dropped on reassembly. Request → persistence model → DB → logic → response flows with no scaffolding, which is the whole point.

Formats

A format is not a row this seller owns — it is a declaration fetched from a creative agent and cached. What matters for the data model is the one field we ignore: Format.reported_metrics: list[AvailableMetric].

Products

core/product.json                     "Products MUST carry format_ids, format_options, or BOTH"
                                      (root anyOf, plus canonical_formats_only)
core/product-format-declaration.json  format_kind + params REQUIRED
                                      format_option_id, v1_format_ref[], format_shape,
                                      format_schema, canonical_formats_only

format_options has zero references in src/, so this seller carries only the deprecated half of a MUST … or BOTH. And v1_format_ref[] is the field that makes the one-way rule workable: a canonical declaration states its legacy refs, so serving a legacy peer is a lookup, never a synthesis.

Metrics

The least examined and the simplest to state:

pin:  AvailableMetric — a CLOSED 49-member vocabulary
      (impressions, spend, clicks, ctr, views, completed_views, completion_rate,
       conversions, conversion_value, commissionable_value, roas, cost_per_acquisition, …)
      and Format.reported_metrics declares which of them a format reports

app:  AvailableMetric      0 references
      reported_metrics     0 references
      "impressions"       41 files

So the seller has no notion of the vocabulary at all: it hardcodes one metric name across forty-one files and never asks a format which metrics it reports. Metrics belong to the format declaration, and what a package can be reported on is derivable from the formats it carries — not from a name repeated in the code.

4. The flow, once the above holds

REQUEST    either arm accepted (3.x window)
   ↓       edge: project legacy -> kind via the SDK resolver; retain the assertion verbatim
DOMAIN     one identity: format_kind (+ option ref). No isinstance branching.
   ↓
DB         faithful: format_kind, format_option_ref, legacy_format_id
   ↓
RESPONSE   canonical by default; the retained assertion echoed to a legacy peer

5. Sequencing

  1. Wire the SDK's resolver at the edge. Nothing else is correct until a legacy identity can become a kind, and no new code is needed for it.
  2. Collapse the creative identity columns to the three faithful ones. Structure only; the backfill of format_kind for existing rows is separate and may be impossible where an agent publishes no canonical declaration — that case needs a decision, not a default.
  3. Make logic key on the kind and delete the branching the current union forces.
  4. Products: add format_options[], which is also what makes format_option_ref's ambiguity rule checkable.
  5. Metrics: adopt the vocabulary and read reported_metrics off the format instead of assuming impressions.
  6. Only then decide the SDK release question. A forked release is viable — a wheel built from the integrated tree carries the schema bundle (measured: 2,973 _schemas entries) where a pushed branch does not, because src/adcp/_schemas/ is gitignored and generated. But if steps 1–5 surface more SDK gaps, cutting a release first is premature.

Steps 2 and 3 invalidate part of what landed this session: the migration added format_kind beside the three partial legacy columns rather than collapsing them, and the identity accessor returns a two-arm union the design says to remove. The BDD work is correct to 3.2.1 and stays.
