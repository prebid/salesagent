Creative format identity: both arms, canonical preferred

What the spec says, what the SDK gives, what the app is missing. Companion to Targeting: input versus state — and a different answer. Branch adopt/sdk-9.0.0, adcp==9.0.0b1, spec 3.2.1.

The targeting gap turned out to be a missing conversion, because the request and state schemas there have opposite null semantics. The creative identity looks like the same problem and is not: here the spec puts the same duality on both sides, so nothing needs converting. What is missing is simpler and more embarrassing — the app only accepts the deprecated arm.

1. What the spec says

Both the request shape and the state shape carry both arms, mutually exclusive, with the legacy one deprecated:

SchemaMemberSpec text
core/creative-asset.json
the input		 format_id “DEPRECATED in 3.2. Legacy named-format path retained for older 3.x peers. New creative assets use format_kind and optional format_option_ref.”
format_kind “Canonical format name this creative targets (e.g. image, video_hosted). Mutually exclusive with deprecated format_id.”
format_option_ref “3.1+ format-option path, optional. Structured format option reference matching one of the target product’s format_options[] declarations.”
creative/list-creatives-response.json
the state		 format_id “DEPRECATED in 3.2. Legacy named-format path. New listed creatives use format_kind and optional format_option_ref.”
format_kind “Canonical 3.2 path. The canonical format kind this creative targets. Mutually exclusive with deprecated format_id.”
format_option_ref “Optional reference to the concrete canonical format option this creative targets. Required when format_kind alone is ambiguous in the enclosing product context.”

And the item schema enforces the exclusivity structurally, with named arms:

"oneOf": [
  {"title": "Listed creative (named-format reference)",
   "required": ["format_id"],   "not": {"required": ["format_kind"]}},
  {"title": "Listed creative (canonical format kind)",
   "required": ["format_kind"], "not": {"required": ["format_id"]}}
]

Two consequences follow, and both matter:

  • The state mirrors the input. A creative created with format_id is listed with format_id; one created with format_kind is listed with format_kind. No resolver is required.
  • Exactly one is always present. The identity can never be projected away — which is why a fields selection that omits it still gets it.

2. What the SDK gives

Three surfaces, and the two compatibility ones are identical on these members:

Surfaceformat_idformat_kind format_option_ref
core.creative_asset.CreativeAsset (generated) optionaloptionaloptional
LegacyCreativeAsset optionaloptionaloptional
canonical_creative.CreativeAsset ABSENTrequiredoptional

Legacy* is not a format_id-only surface — it is the same both-arms shape as the generated class. The canonical layer is the 4.0-ready one: it deletes legacy identity from model_fields and binds the name to None, so the generated XOR validator reduces to “format_kind must be set”.

So for a seller that must accept both arms during the 3.x window, the correct surface is the generated/Legacy one. That is where the app already sits. Repointing to canonical_creative would remove the legacy arm the spec says to retain — an earlier attempt here did exactly that and was reverted.

3. What the app has

It is on the right surface and uses one arm of it. Measured:

format_id          296 refs / 31 files
format_kind         15 refs /  4 files
format_option_ref    2 refs /  2 files

format_kind in src/core/tools/creatives/   0
format_kind in src/core/database/          0
creatives table identity columns:          agent_url, format     (no format_kind)

And the business logic refuses the canonical arm outright:

// src/core/tools/creatives/_validation.py:104
if not creative.format_id:
    raise AdCPValidationError(field="format_id")

The DTO accepts a canonical-only creative — measured: format_kind alone constructs fine, and both-or-neither is refused as oneOf. So a spec-conformant canonical creative clears the boundary and is then rejected by business logic, with VALIDATION_ERROR naming format_id: a field the spec tells new creatives not to send.

That is the worst available failure mode. Refusing at the boundary would at least be honest; refusing afterwards, by name, tells a correct buyer to add a deprecated field.

4. The gap

No conversion, no resolver, no new model. Four things, in order of how much they hurt:

GapToday
1Accept the canonical arm on input refused at _validation.py:104, naming the deprecated field
2Persist which arm and its value columns exist for the legacy pair only (agent_url, format)
3Read back the arm the creative was created with always emits format_id; a canonical creative could not round-trip
4format_option_ref when format_kind is ambiguous 2 references in src/; the conditional obligation is unimplemented

Items 1–3 are one feature: carry the identity the buyer gave, and give it back. Item 4 is a separate conditional rule and needs the product’s format_options[] to exist first — which is the canonical-products work (format_options: 0 references in src/).

What validation must keep doing

The legacy arm’s value is checked against the creative-agent registry today (fetch_format_spec(agent_url, format_id), which refuses a format no agent serves with REFERENCE_NOT_FOUND). The canonical arm needs the equivalent: a format_kind outside the pinned 16-member vocabulary is not a reference lookup, it is an enum violation, and the two should not be collapsed into one code.

5. Plan

  1. Stop requiring the deprecated arm. Replace the format_id presence check with an identity check that accepts either, and let the model’s own XOR be the authority on exclusivity — it already refuses both-or-neither.
  2. Give storage a canonical column and record which arm the creative carries. A migration adds structure only; a backfill of existing rows is separate work and may be impossible for creatives whose agent publishes no canonical declaration.
  3. Echo the stored arm on readback, so the state mirrors the input as the spec describes, and exactly one identity is always on the wire.
  4. Grade all of it in BDD: a creative synced by format_id lists by format_id; one synced by format_kind lists by format_kind; both-or-neither is refused oneOf; an unknown format_kind is refused as an enum violation, not a missing reference.
  5. Defer format_option_ref ambiguity until products carry format_options[].

6. Why this is not the targeting gap

TargetingCreative identity

What is missingthe conversion between them acceptance, storage and readback of one arm

The lesson they share is the one that cost three reverted patches: an error about a type mismatch is not evidence that a type annotation is wrong. Both cases needed the spec read first, and in both cases the app’s type declarations turned out to be right.
