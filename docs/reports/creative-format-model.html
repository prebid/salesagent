Creative formats: the spec model, the measured gaps, the design

Branch feature/spec-gaps-1210 · AdCP 3.1.1 (adcp==6.6.0) · 2026-09-10

This started as one question — can the legacy bare-string format_id compatibility be dropped — and the answer uncovered a subsystem built on inputs the pinned spec no longer defines that way. Every claim below carries the measurement or the schema citation that produced it. Nothing here is inferred from reading source alone.

The one-line summary. The pinned spec moved creative format identity from a name in a vendor's namespace to a canonical shape plus product-scoped parameters. This codebase implements the name, stores the name in three columns, resolves the name against a creative-agent registry, and admits the new shape at its boundary without implementing anything behind it.

1. How the spec says it works

Format identity is an object, never a string

core/format-id.json requires agent_url and id, with optional width, height, and duration_ms that pin a template format to a variant. The schema states the rule outright: "A JSON object — never a plain string ... Using a plain string here is a schema violation." Callers comparing two values MUST canonicalize agent_url first.

An upload carries one of two identities, and one of them is legacy

core/creative-asset.json is a root oneOf. Required across both branches: creative_id, name, assets.

BranchRequiresThe schema's own title
1format_idLegacy creative (named-format reference) — "remains supported through 4.x"
2format_kind3.1+ creative (canonical format kind) — introduced by RFC #3305

So format_id on an upload is the legacy branch of 3.1.1 itself, not a pre-3.1.1 artifact. Dropping it means refusing a spec-legal 3.1.1 request.

Why the change was made

The pin names the failure mode of the old model directly, in v1_format_ref's AAO-convention paragraph:

Without this convention, every publisher's 300x250 ships with a different v1_format_ref (theirs vs nytimes.example vs cnn.example vs …) and the v1 wire fragments into per-publisher namespaces — exactly what canonical-formats was designed to eliminate.

A format_id is a name someone owns, so the same IAB MREC had N identities and a buyer needed per-vendor catalog integration to learn they were the same thing. format_kind replaces a pointer with a description: a small closed set of shapes a buyer can reason about generically, plus open machine-readable parameters per product.

Identity did not disappear — it changed scope. format_option_id is still a stable identifier, namespaced to the product (or to a publisher catalog) rather than to a creative agent's global namespace. Shape is global and closed; identity is local and open. A creative keeps its creative_id because a creative is an instance; a format stopped being an instance-with-a-name and became a type.

The enum is closed for producers and open for consumers

core/canonical-format-kind.json lists 13 values: 12 canonicals plus custom. The asymmetry is normative:

Open-enum semantics (normative). … Consumer SDKs MUST treat this enum as open at parse time: an unknown format_kind value MUST be retained as-is on the in-memory object (not silently dropped or rewritten to "custom") and MUST NOT cause the surrounding payload to fail validation. … The producer-side enum stays closed (sellers MUST NOT mint ad-hoc format_kind values — use format_kind: "custom" with format_shape + format_schema for non-registered shapes)

So a new format is defined two ways: now, as custom plus format_shape (a recognized global pattern from core/format-shape-vocabulary.json) plus format_schema (a URI+digest reference to a fetchable schema); later, by promotion into the enum in a minor release (queue: adcp#3666), which the schema calls "non-breaking by design".

The payoff the spec claims for the fetchable schema: "Buyer agents fetch the schema, validate manifests structurally, and reason about manifests without per-seller integration code."

The three-part 3.1+ identity

FieldAnswersScope
format_kindWhich canonical shapeGlobal, closed (12 + custom)
format_option_refWhich of the product's concrete options realizes it{scope:"publisher", publisher_domain, format_option_id} or {scope:"product", format_option_id}
format_idWhich named format in an agent's namespaceLegacy; global name

Assets is a slot map, and that is deliberate

Both core/creative-asset.json and core/creative-manifest.json key assets by slot. Legacy path: each key matches an asset_id from the format's assets array (banner_image, vast_tag). 3.1+ path: each key matches an asset_group_id from the format's slots declaration, drawn from the canonical vocabulary registry (images_landscape, video, published_post, landing_page_url). A value is a single asset object or an array for slots with min/max > 1 (carousel cards, responsive headlines), and each asset carries an asset_type discriminator selecting its schema.

Resolution between the two identities is asymmetric by design

v1 to v2 resolves, through a six-step normative order in registries/v1-canonical-mapping.json: the seller's v1_format_ref → an explicit canonical field on the v1 file → registry glob → structural match → ambiguous-family → fail closed. Step 4 yields a family, which is what a format_kind is.

v2 to v1 does not resolve. The registry is "authoritative for v1 → v2 projection only", and:

SDKs MUST NOT synthesize a v1 format_id from the registry by inverting structural matches: the registry's id slugs lack the agent_url half of a FormatId, and registry entries with format_id_glob: '*' or pure-structural matches have no single literal to invert to.

At 3.1, all seven published registry entries are pure-structural, so nothing is invertible even best-effort. The only v2→v1 source is the seller asserting v1_format_ref[] on a product declaration, and canonical_formats_only: true is the explicit way to say there is none. Four canonicals carry v1_translatable: false and can never have a v1 form: image_carousel, sponsored_placement, responsive_creative, agent_placement — "the v1-unreachability is structural."

Consequence for the internal model: the unifying representation must be format_kind, because that is the direction that resolves. The codebase does the opposite.

core/creative-manifest.json is the spec's adapter-facing shape. Nothing in this codebase implements it.

Provenance

core/provenance.json is AI-provenance metadata (EU AI Act Article 50) attached to a creative: "Serves as the default provenance for all manifests and assets within this creative. A manifest or asset with its own provenance replaces this object entirely (no field-level merging)." provenance_required is a product policy field on core/creative-policy.json, and the seller "may independently verify claims via get_creative_features."

2. What the code does — thirteen measured gaps

Each row states how it was measured. These are candidate issues; the numbering is for reference in discussion, not priority.

G1 — The 3.1+ branch is admitted at the boundary and dies inside

CreativeAssetRequest._exactly_one_format_identifier correctly accepts the format_kind branch. Then tools/creatives/_validation.py:99 builds a Creative(**schema_data) whose format_id is None:

boundary ACCEPTS the format_kind branch: image | format_id: None
Creative(**schema_data) -> ValidationError
    format_id: Input should be a valid dictionary or instance of
               FormatReferenceStructuredObject [input_value=None]

A spec-legal upload clears validation and fails internally. This is the worst of the three possible states — worse than refusing it outright.

G2 — No resolution machinery exists at all

grep over src/: format_kind appears only inside the validator that admits it and in comments. v1_format_ref, format_options, canonical_formats_only, and format_option_ref appear nowhere (one comment mention in product.py). So neither direction of the spec's resolution order is implemented.

G3 — list_creatives cannot report a format_kind creative

Filed upstream as adcp#7402. sync_creatives accepts both branches (properties.creatives.items is $ref: ../core/creative-asset.json); list-creatives-response.json requires format_id unconditionally and the strings format_kind and format_option appear nowhere in the file. All three supply routes are closed (see §1). This one is an upstream defect, not our bug — but it blocks any internal design until it is answered.

G4 — The ORM has no column for the 3.1+ identity

LayerRepresentation
Wire / schemaone object: FormatId {agent_url, id, width, height, duration_ms}
DB / ORM (creatives)three columns: format: String(100), agent_url, format_parameters: JSONB

No column can hold format_kind or format_option_ref, so even a resolved value has nowhere to live. Any fix to G1/G2 needs a migration.

G5 — No creative manifest; three divergent adapter dicts stand in

The spec's adapter-facing shape is core/creative-manifest.json. The live path, media_buy_create._build_adapter_asset_from_creative:754, emits a hand-rolled dict:

{creative_id, package_assignments, width, height, url, click_url, asset_type, name}

G6 — Non-GAM adapters read a key the live builder never sets

kevel.py:366, triton_digital.py:277 and mock_ad_server.py:1207 index asset["format"]. The dict above has no format key, so those branches raise KeyError on contact. GAM — the mature adapter — reads only creative_id, package_assignments, snippet, snippet_type, and never touches format.

Decision taken: declare the non-GAM adapters unsupported as part of this work. Mock needs a carve-out — the whole test harness and every BDD scenario run on it.

G7 — The SDK closes the format_kind enum

Filed upstream as adcp-client-python#1140, together with a second finding: the SDK is strict where the spec mandates openness and permissive where the spec constrains producers.

CreativeAsset2.model_validate({..., "format_kind": "a_future_canonical_from_3_2"})
# ValidationError: [{'type': 'enum', ...}]     <- spec says MUST be retained

ProductFormatDeclaration.model_validate({"format_kind": "custom", "params": {}})
# ACCEPTED                                     <- spec says format_shape + format_schema REQUIRED
ProductFormatDeclaration.model_validate({"format_kind": "image", "params": {},
                                         "format_shape": "roadblock"})
# ACCEPTED                                     <- spec says MUST be absent

G8 — Creative extends the listing RESPONSE model and serves three roles

class Creative(LibraryCreative) where the parent is the SDK's list_creatives_response.Creative. It is used as a response type (GetCreativesResponse.creatives), as DB rehydration (listing.py:392), and as an internal validation vehicle (_validation.py:99). It adds principal_id (internal, exclude=True) and provenance (a local subclass, because the library Provenance is refused cross-hierarchy), and reshapes assets.

G9 — assets is retyped to dict[str, Any], discarding the SDK's slot map

The SDK parent types it correctly:

dict[Annotated[str, StringConstraints(pattern='^[a-z0-9_]+$')],
     AssetVariant | Assets] | None

The local override is dict[str, Any] | None, which throws away both the key constraint and the discriminated asset_type union. Every "coerce the blob" branch in creatives/listing.py is the bill for that.

G10 — The request DTO extends the legacy branch, and not on purpose

CreativeAssetRequest extends CreativeAsset1 — the format_id branch. That was not a choice:

CreativeAsset       base = RootModel[Union[CreativeAsset1, CreativeAsset2]]
adcp.types.CreativeAsset -> CreativeAsset1     # runtime resolves to the LEGACY branch

The public alias resolves to the legacy branch at runtime while mypy resolves it to the union, so the obvious import silently is the legacy branch. The code records this codegen defect as unreported upstream.

There is no "modern branch" to switch to: CreativeAsset2 requires format_kind and would mirror the problem. The union base is the only shape that expresses the oneOf natively, and it was rejected because a failing branch puts a codegen class name in the buyer-facing pointer:

union base error locs: ('CreativeAsset1', 'name')  ('CreativeAsset1', 'format_id')

core/error.json requires issues[].pointer to address a field in the request payload, and CreativeAsset1 names nothing a buyer sent. A callable discriminator dissolves that objection — see §3.

G11 — Creative.format is a non-spec alias with three production readers

A property returning self.format_id. The SDK parent declares no format field. It exists because the DB column is named format, so code straddling row and schema could use one name. Read by tools/creatives/_validation.py:109, _processing.py:69, and _processing.py:279/283.

G12 — A request is round-tripped through a response model to read one field back

_validation.py:99 builds a full Creative from a buyer's CreativeAssetRequest, then reads .format off it and hands the object to check_provenance_required. The request already carries format_id.

Two of that function's four checks are real and cannot live in a DTO: format existence (fetch_format_spec, an outbound call whose typed failures propagate — 429 becomes RATE_LIMITED, 5xx becomes SERVICE_UNAVAILABLE) and the provenance policy (which depends on the product's policy, absent from the creative payload). Two are redundant: the empty-name check duplicates a required field, and if not creative.format_id duplicates _exactly_one_format_identifier.

Note that fetch_format_spec is the legacy branch's resolution mechanism. In 3.1+ format identity resolves against the product's own declarations, with no dialling out.

G13 — The live adapter path supports exactly one impression tracker

Found by deleting the dead converter. _convert_creative_to_adapter_asset built tracking_urls["impression"] as a multi-URL list from the creative's assets, and its tests asserted two buyer trackers survived. The live builder calls extract_impression_tracker_url — singular, returning str | None — and wraps it in a one-element list. So the dead code was more capable than the live code, and its tests were the only record of the multi-tracker claim. Both are now deleted; this row is the record.

3. The design these measurements point to

Canonicalize internally on format_kind

Not a preference — it follows from the resolution asymmetry. v1→v2 resolves through a normative order; v2→v1 is forbidden to derive and impossible for four canonicals. So the only representation everything downstream can share is the canonical kind. format_id becomes a retained buyer assertion: stored verbatim, echoed on the legacy wire, never the identity that business logic keys on.

This removes the need for isinstance branching everywhere. The branch survives only at the edge, where an inbound legacy identity is projected to a kind.

A callable discriminator, not a flattened model

The reason the oneOf was flattened (codegen class names in the buyer's error pointer) is solvable. Pydantic's callable Discriminator selects a branch by presence, and the Tag names are chosen by us:

def which_branch(v):
    if v.get("format_id") is not None:   return "format_id"
    if v.get("format_kind") is not None: return "format_kind"

Asset = Annotated[Union[Annotated[ByFormatId,   Tag("format_id")],
                        Annotated[ByFormatKind, Tag("format_kind")]],
                  Discriminator(which_branch)]

Measured behaviour:

InputResultvs the RootModel union
format_id branch→ ByFormatIdsame
format_kind branch→ ByFormatKindsame
missing name, modern branchloc = ('format_kind', 'name')('CreativeAsset1', 'name')
neither identifierloc = (), union_tag_not_foundtwo branch-shaped errors

The extra loc segment is now a closed two-value set named after real spec fields, so the pointer builder can drop it deterministically. "Neither identifier" lands at the root, which is where a oneOf violation belongs.

One accessor, built on the helper that already exists

Downstream code should ask the request for its format identity once, not branch on which branch arrived. CreativeAssetRequest has no such accessor today; Creative has three ad-hoc ones (format, format_id_str, format_agent_url). Build on format_id_identity() (src/core/schemas/_base.py:371), which returns the (canonical agent_url, id) federation pair the pin mandates for comparison — do not write a second one beside it.

assets takes the SDK's typed slot map

Stop overriding it to dict[str, Any]. The parent's type is already the correct slot map with a key constraint and a discriminated value union. The coercion branches in listing.py exist only because the type was discarded.

Sequencing: the refusal flips with the identity

This is the one decision that needs settling before work starts, because it is lane 1 either way. Refusing format_kind is right for today's tree, where format_id is the identity. Once the identity flips, the branch needing a resolver is format_id, and the refusal flips with it. Doing both in the stated order means building a refusal and then deleting it.

OptionLane 1Cost
AFlip the identity, accept both branches, build the six-step resolver nowResolver up front, including catalog reads. Its refusal is the spec's own fail-closed, not ours.
BFlip the identity, accept only format_kind, refuse the legacy branch with FORMAT_NOT_SUPPORTED until the resolver landsOne refusal, built once, pointing the direction the design is going. Refuses spec-legal traffic explicitly.

B first, A as a later lane, is the reading that avoids throwaway work. FORMAT_NOT_SUPPORTED exists in enums/error-code.json but is not in our CODE_TABLE, so wiring it is part of the lane. Neither it nor UNSUPPORTED_FEATURE carries an x-error-metadata block in the pin, so the recovery value has to be chosen and justified rather than read off.

4. What has already been done

The legacy bare-string compatibility is removed, and it changed no production behaviour. The reachability proof:

  • Buyers: CreativeAssetRequest.format_id and PackageRequest.format_ids already refused bare strings before the removal (measured: ValidationError both). No request that used to succeed now fails.
  • Stored rows: the only converter of a bare string was upgrade_legacy_format_id, whose one reachable entry point was Creative.validate_format_id. Both of that validator's producers already supply a structured value — the buyer path (strings refused upstream) and the DB path (listing.py:284-287 builds the FormatId explicitly from the agent_url and format columns).
  • The plural helper never handled strings at all — its only branch was isinstance(fmt_id, dict) and "agent_url" in fmt_id and "id" in fmt_id.
  • products.py:547-556 does its own str/dict/model branching and was never touched.

Removed: upgrade_legacy_format_id, get_agent_url_for_format, load_format_cache, _upgrade_legacy_format_ids and its three validators, the format-alias and bare-string branches of Creative.validate_format_id, the legacy_id_map from the fixture and the refresh script, and the dead _convert_creative_to_adapter_asset (192 lines, no production callers). Net across 19 files: 1243 deletions, 60 insertions. The only added executable line in src/ reads .id instead of str(...).

Three ratchets tightened rather than grew: C901 172→170, PLR0912 123→122, PLR0915 100→99.
