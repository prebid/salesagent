pricing_option_id: from five recomputations to one stored column

Branch feature/spec-gaps-1210 · AdCP 3.1.1 (adcp==6.6.0) · 2026-09-08

1. The original problem

pricing_option_id is how a buyer selects what they are paying. It is required in all nine pricing-options/*.json schemas, and media-buy/package-request.json marks the buyer's copy "x-entity": "product_pricing_option" — it is a reference to a stored entity.

The pricing_options table had no such column. So five places in the codebase independently rebuilt the string {pricing_model}_{currency}_{fixed|auction} out of three other columns:

What that cost, concretely

Defect 1 — a row stored as "CPM" was unreachable. Nothing normalises pricing_model on the way into the table. A row holding "CPM" was announced as cpm_usd_auction (the announcer lowercases) and then looked up as CPM_usd_auction (the resolver did not). The buyer sent back exactly the id they were given, and it matched nothing.

Defect 2 — two options could share one id. Nothing prevented a product from carrying two rows that produced the same string. The reader built a dict keyed by it, so one row was silently dropped and the buyer's selection resolved to whichever row won.

Defect 3 — the id could not be chosen. A publisher had no way to name an option; the id was a function of three unrelated columns, so re-pricing an option (cpm → cpc) silently renamed the entity a buyer had already selected.

Two adjacent defects the work surfaced

Both were measured, not inferred.

  • Both shared helpers were dead against real V3 objects. synthetic_pricing_option_id() reads option.is_fixed and pricing_info_for() reads option.rate — neither field exists on the SDK's V3 pricing options (declared: [currency, fixed_price, floor_price, max_bid, …]). Both raise AttributeError on a real schema option. They happened to work only because every live call site passes an ORM row, which does have those columns.
  • The admin create form never wrote a price into the product card. products.py read first_option.get("fixed_price") — a key the form parser has never produced (the parser emits rate). The branch was dead, so a product created through the admin UI got a product_card.manifest with a pricing_model and no pricing_amount. The edit form read rate and worked. Typing the parser's output made the mismatch a hard error instead of a silent .get() miss.

2. How it was solved

A real column, and one place that assigns it

Migration d1a7c4b90e33 adds pricing_options.pricing_option_id VARCHAR(100) NOT NULL plus UNIQUE (tenant_id, product_id, pricing_option_id) — "unique … within the product", as the schema says.

The backfill reproduces the id get_products already announced, verbatim. That is the binding constraint: buyers hold these ids, so a backfill that spelled them differently would strand every id in the wild. Where a product had two rows that announced the same id, the later one gets an ordinal suffix — renaming an id that named two rows and was therefore never reliable.

lower(pricing_model) || '_' || lower(currency) || '_' ||
CASE WHEN is_fixed OR lower(pricing_model) = 'cpa' THEN 'fixed' ELSE 'auction' END

All six grammar copies are deleted. synthetic_pricing_option_id() is gone. Every reader now reads po.pricing_option_id. The grammar survives in exactly one place — PricingOption.default_option_id() — and it is a default for a new row, not a derivation on read. Once written, the column is authoritative, so a publisher can give an option any id it likes and every reader honours it.

Every writer goes through PricingOption.create(), so no row can reach the database without an id.

Collateral DRY cleanup the typing forced

parse_pricing_options_from_form() returned list[dict] — a second shape for a thing the ORM model already types. It now returns list[PricingOption]. That removed three copies of the same Decimal coercion and one hand-written seven-name column list; the edit form's copy list is now derived from the mapper, so a column added to the model is carried without anyone remembering to list it.

3b. What only the real database could show

Three of the error scenarios above originally graded states that cannot exist. The pricing_options table carries constraints no in-process fixture was meeting:

check_fixed_has_rate                is_fixed  => rate IS NOT NULL
check_auction_has_price_guidance    !is_fixed => price_guidance ? 'floor'
enforce_min_one_pricing_option      a product's last option cannot be deleted

So "a fixed option with no rate", "an auction option with no floor", and "a product with no pricing options" are rows the seller can never hold. Those scenarios passed in-process and failed only on the e2e_rest transport, which writes to a real migrated database — the in-process passes were vacuous. They are removed, with the reason recorded in the feature files. What survives are the four model-specific parameters defects that no constraint covers.

The same constraints are why PricingOptionFactory now derives rate and price_guidance from is_fixed: a flat Decimal("5.00") default was giving every auction fixture a fixed rate.

4. What behaviour actually changes

Over MCP / A2A / REST

SituationBeforeAfter
get_products, option stored with model "CPM" announced cpm_usd_auction; sending it back resolved to nothing announced cpm_usd_auction and resolves — one stored spelling
get_products, two same-shaped options on one product one silently dropped from the response unrepresentable — the database refuses the duplicate at write time
create_media_buy naming an announced id matched a recomputed string; case-sensitive mismatch failed as VALIDATION_ERROR matches the stored id
get_media_buy_delivery for such a buy option unresolvable → _package_pricing raises → the buy vanishes from its own delivery report resolves
A stored option missing what its model requires same INTERNAL_ERROR, but ungraded unchanged, now graded on all three transports

For a seller whose pricing_model values are already lowercase — the common case — nothing on the wire changes. The backfill reproduces the ids byte-for-byte. The fix removes a class of failure; it does not move anyone's ids.

In the Admin UI

  • Creating a product now writes a price into its product card. Previously pricing_amount and pricing_currency were silently omitted on the create path (dead fixed_price key). Edit already worked; the two paths now agree.
  • Re-pricing an option no longer renames it. Editing a product's pricing model or currency keeps pricing_option_id, so a buyer's stored selection stays valid. Before, the announced id silently changed under them.
  • Adding a duplicate option is now refused by the database instead of producing two rows a buyer cannot tell apart. Note: this surfaces as an IntegrityError, not a flash message — see Open items.

5. Two unit files retired

Both were commented out, not deleted, so the mapping stays reviewable.

tests/unit/test_product_conversion_pricing.py — 54 tests calling the translator directly with a hand-built option dict. That grades the translator against itself: nothing stored a row and nothing read a wire, and it could not express what a buyer gets when the stored row is malformed, because at that level there is no response. Replaced by the 21 GET-PRODUCTS scenarios above, which cover strictly more.

tests/unit/test_pricing_validation.py — 11 tests built on Mock() products whose fields were typed out by hand, so they went stale the moment the model gained a column. Three of its obligations were already graded live by existing UC-002 scenarios; three more got new scenarios. Two happy paths are the UC-002 main flow. One (test_currency_mismatch) exercised the legacy pricing_model fallback that a request carrying the required pricing_option_id cannot reach — grading it would pin a branch no conformant buyer can enter.

6. Suite state

Unit: 8 failures, all pre-existing — the same set present at the branch head before this work (12 there; 4 were test_architecture_repository_pattern rows this change cleared). Zero new failures. 7. Open items

  1. The admin form cannot set a pricing_option_id. The column supports publisher-chosen ids and every reader honours one, but the UI offers no field, so in practice every id is still the default. Adding the input is the remaining half of "the publisher owns the id".
  2. A duplicate option surfaces as an IntegrityError, not a flash message. The constraint is correct; the admin form should catch it and say "two options on a product cannot share an id".
  3. pricing_info_for() still cannot take a schema object. It reads option.rate, which V3 options do not declare. Every live caller passes an ORM row so nothing is broken today, but the signature says Any and the failure mode is an AttributeError at runtime. This is item #1 of the agreed 2 → 1 → 3 sequence, still to do. (Its sibling synthetic_pricing_option_id() is gone — the column replaced it.)
  4. Auction delivery is still broken — prebid/salesagent#2229. An auction option's rate column is NULL, so _package_pricing raises and the buy is dropped from its own delivery report. Graded as a spec-production gap by T-UC-004-package-auction-rate; not fixed here.
