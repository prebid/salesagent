Targeting: input versus state

Why test_targeting_overlay_validation fails, measured against the SDK and the pinned spec rather than patched. Branch adopt/sdk-9.0.0, adcp==9.0.0b1, spec 3.2.1.

Three sibling classes appear in one request's path and each layer refuses the previous layer's instance. The reflex is to widen the annotations until they agree. The spec says that would be wrong: the classes are different on purpose, and what is missing is a conversion the application has never had.

1. What the SDK gives

TargetingOverlay        fields=37   base=AdCPBaseModel
TargetingOverlayInput   fields=37   base=AdCPBaseModel

Two classes, the same 37 dimensions, neither a subclass of the other. The app subclasses both, adding its own internal dimensions:

Targeting       -> TargetingOverlay      -> _InternalTargetingDimensions
TargetingInput  -> TargetingOverlayInput -> _InternalTargetingDimensions

So Targeting is a TargetingOverlay and satisfies any field declaring one. TargetingInput is not, and never will be.

2. What the spec says

The two generated classes come from two schemas whose descriptions state opposite null semantics:

SchemaPropsStated purpose
core/targeting-input.json37 “Request-only targeting mutation input. Each known dimension has three states: omission inherits the product default on create…”
core/targeting.json37 “Strict non-null targeting state used during product discovery, commercial snapshots, and media-buy readback.”

That is the whole design. The input is tri-state — omission means inherit the product default, an explicit null means clear, a value means set. The state model forbids nulls, because a snapshot or a readback has to say what the targeting actually is, not what the buyer asked to change.

They are not interchangeable, and no annotation can make them so. A request shape and a state shape are different kinds of document.

3. What the app has

The declarations are already correct at both ends:

SiteDeclaresCorrect?

_base.py:2663 — request side TargetingInputyes — request
_base.py:2587 — MediaPackage Targetingyes — internal state

What is absent is anything that turns one into the other. Measured across src/:

"inherit ... product default"   0 files
"three states"                  0 files
targeting_resolution            0 files
resolve_targeting               1 file   (adapter CAPABILITIES — unrelated)

So a buyer’s TargetingInput is handed straight to a field declaring state. Pydantic validates a model-typed slot by instance, so it is refused. One site papered over the hole with a cast that asserts a falsehood:

// src/core/tools/media_buy_create.py:3349
targeting_overlay=cast(
    "Targeting | None",
    matching_package.targeting_overlay if matching_package else None,
)

The cast satisfies mypy; the runtime refuses the instance anyway. The refusal is then rewrapped as SERVICE_UNAVAILABLE — “retry with exponential backoff” — for a request no amount of retrying can fix. That is a second defect sitting on top of the first.

The failure walks forward as you widen

Widening one field moves the refusal to the next layer, which is the tell that the fix is not an annotation:

as shipped          ValidationError for MediaPackage  — expected Targeting,        got TargetingInput
widen MediaPackage  ValidationError for Package       — expected TargetingOverlay, got TargetingInput

4. The gap

One missing component, stated in the spec’s own words: a resolver that takes a buyer’s tri-state TargetingInput plus the product’s defaults and produces strict non-null Targeting state.

Input dimension is…Resolver must produce
omittedthe product default for that dimension
explicitly nullcleared — the dimension is not targeted
a valuethat value, subject to the seller’s capability check

Once that exists, every declaration above is already right and nothing widens: Targeting subclasses TargetingOverlay, so the response layer accepts it for free.

Note the conversion cannot be Targeting.model_validate(ti, from_attributes=True). That copies the input’s nulls into a model whose contract is non-null, so a “clear this dimension” instruction becomes a stored null in a snapshot. It appears to work only when the input is empty.

5. Plan

  1. Write the resolver — one function, request input + product defaults → Targeting. It is the only place the three states are interpreted, and the only place a product default is read for targeting.
  2. Call it at the one seam where a request becomes internal state (media_buy_create, the matching-package path), and delete the cast. The declarations do not change.
  3. Fix the error classification: a targeting shape the seller cannot satisfy is not SERVICE_UNAVAILABLE. Whatever the resolver refuses must carry a code the buyer can act on, and must not advise a retry.
  4. Grade it in BDD, which is where behaviour is graded: one scenario per input state — omitted inherits, explicit null clears, value sets — across the transports.

6. Scope beyond targeting

This is a shape, not a field. The creative format identity worked out the same way: the request accepts format_id or format_kind, while the state model must carry exactly one, and the seam between them is where the work lives. Expect the same input-versus-state question wherever 3.2 split a mutation input from a state document.

Not yet measured: how many of the ~22 remaining integration failures are this shape. The two CreateMediaBuyRequest accepted-shape failures were a different cause (declaration tests), and are closed.

7. What was wrong in the approach, not just the code

Three patch attempts were made and reverted before this was written:

  • widening MediaPackage.targeting_overlay to a union — moved the refusal one layer on;
  • model_validate(..., from_attributes=True) — would have copied “clear me” nulls into a strict non-null model, and the probe that appeared to validate it used an empty instance, so it could not have failed;
  • repointing the creative models at canonical_creative — would have removed the legacy format_id arm the 3.x compatibility window requires.

Each was a plausible local fix found by following the error message. None was reached by asking what the SDK provides, what the spec mandates, and what the app is missing — which took four measurements and produced a different answer.
