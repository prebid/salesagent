# Known-failing storyboard-conformance checks.
#
# RE-SEEDED FROM ONE MEASURED RUN: test-results/innet_180926_2349, an in-network run of this
# tree, scoring passed=49 failed=16 skipped=235 storyboards_executed=72 on BOTH protocols
# with zero disparity between them. Every id below is a nodeid that run produced; none was
# derived by hand from a check name, because the failure messages print check ids
# slash-separated while the parametrized ids are ``::``-separated and the media_buy track
# carries an extra path segment -- converting between them by hand is the arithmetic this
# header has forbidden since the first seeding.
#
# 18 ROWS PER PROTOCOL AGAINST A ``failed`` COUNTER READING 16. The summary's ``failed`` is
# the runner's own tally; ``summary["failures"]`` is the per-check array the test module turns
# into parametrized items, and it carries 18 records per protocol. The ledger keys on those
# records, so 18 is the number of rows. The previous seeding had the same shape -- 23 rows
# against ``failed=21`` -- so this is the runner's counter, not a miscount here.
#
# WHAT THE RE-SEED DID. The previous seeding came from test-results/innet_160926_1917, which
# scored passed=30 failed=21 on both protocols and put 46 entries here. "fix(storyboard):
# derive the seeded accounts from the bundle, like the inventory" then took the score from 30
# to 49, and the ledger did not move with it. Two things happened at once and both are
# recorded here:
#
#   * 26 entries GRADUATED -- 13 per protocol, every one of them a check whose storyboard
#     could not seed its accounts before. They are gone from this file. ``ledger_fitness::
#     stale_entries`` failed on them in CI run 35407109423: an entry resolving to no
#     collected check grades nothing, and the ledger only shrinks.
#
#   * 16 checks that were previously SKIPPED now execute, and fail -- 8 per protocol, in the
#     media_buy track. They are new lines below. A storyboard whose ``get_products`` step
#     failed skipped everything downstream with ``prerequisite_failed``, so these gaps were
#     masked by the skip cascade rather than absent. They are genuine conformance gaps, not
#     regressions from the account-seeding fix: VALIDATION_ERROR where create_media_buy
#     should succeed (inventory_list_no_match, inventory_list_targeting,
#     dependency_impairment_cardinality, measurement_terms_rejected/relaxed_terms),
#     CREATIVE_NOT_FOUND on assign_creative_to_package, CREATIVE_REJECTED on a legacy inline
#     creative, NOT_CANCELLABLE on re-cancelling a cancelled buy, and a creative still
#     present in the library after cancellation.
#
# The net is 46 -> 36 entries. Of the 8 newly-surfaced checks, three already have issues
# raised from a later measurement of the same shape:
#
#   * dependency_impairment_cardinality::create_buy_two_packages -- #2267, the seller rejects
#     two packages naming one product where the pinned schema permits it.
#   * measurement_terms_rejected::create_media_buy_relaxed_terms -- #2269, the mock adapter's
#     invented 1M-impression cap refuses a conformance-sized buy. That issue records the same
#     masking this re-seed is undoing: "previously masked, because the create path died on
#     fixture faults before reaching this scenario".
#   * inventory_list_no_match::create_buy_no_match -- #1303, zero-inventory pre-validation.
#
# The other five (creative_fate_after_cancellation::list_creatives_before_cancel,
# dependency_impairment::assign_creative_to_package,
# inline_creatives_without_sync::create_buy_with_legacy_inline_creative,
# invalid_transitions::second_cancel, inventory_list_targeting::create_buy_with_lists) have no
# issue of their own yet and sit under the roadmap umbrella, #1247. Every affected storyboard
# already had a row in docs/test-obligations/storyboard-issue-map.yaml, because its
# ``get_products`` step was already ledgered, so no storyboard became untriaged here.
#
# WHAT THIS FILE COSTS, stated plainly. ``tests/storyboard/conftest.py`` xfails these ids with
# strict=False, so a regression INSIDE a ledgered check does not redden the job, and the job's
# failure count is not the gap count. The gap count lives here, in the length of this file, and
# the pass count lives in ``.storyboard-pass-floor`` -- which is the oracle for the other
# direction and is why a check that quietly degrades from PASS to SKIP now fails the job.
# A run-to-run comparison (scripts/audit/compare_runs.py) remains the way to see a ledgered
# check move.
#
# THE SYMMETRY IS THE POINT. 18 mcp entries and 18 a2a entries, and every failing check fails
# on both surfaces. The runner grades the agent once per PROTOCOL, so an mcp-only fix that
# leaves its a2a twin behind shows up here as an asymmetric pair -- which is the drift this
# split exists to expose.
#
# FORMAT. One parametrized test id per line, keyed on (protocol, track, storyboard_id,
# step_id) from the real @adcp/sdk runner's measured output. Loaded by
# tests/storyboard/conftest.py; pinned entry-for-entry by
# tests/unit/test_storyboard_ledger_state.py, so an entry added here without updating
# EXPECTED_LEDGER fails the unit suite.
#
# Runner-reported SKIPS (missing_test_controller, missing_tool, prerequisite_failed) are
# never ledgered -- they map to a native pytest.skip() in the test module. Only genuine
# check FAILURES are ledgerable.
#
# THE SDK PIN CHECK IS LEDGERED, and it is the one entry here that is not a conformance
# gap. ``test_runner_sdk_pin.py`` compares the npm runner's declared ``adcp_version`` against
# the version this repo pins, and fails: @adcp/sdk@14.0.0-rc.35 declares 3.2.0-rc.1 while the
# repo pins 3.1.1. It was already failing in the runs that scored 30/21, so it predates this
# ledger.
#
# It is expected, and the repo's pin is not what is wrong. The SDK release fixes its own
# ``adcp_version``, so the npm version and the graded spec version are one choice rather than
# two. ``--compliance-version`` is passed with the pinned version already and does not move it;
# the guard says so in its own message -- "however right the --compliance-version happens to
# be". There is no runner flag that separates the client's contract from the vectors it grades
# against, which is a defect in the grader rather than in this repo, raised upstream.
#
# 14.0.0-rc.35 is not a free choice either. The last runner line that declares 3.1 is 11.x, and
# its A2A path carries an unfixed 0.x dependency; the A2A fixes are not backported. So grading
# both protocol surfaces at all requires the 14 line, and the 14 line declares 3.2.0-rc.1.
#
# It is marked at its own source rather than listed below: this ledger's grammar keys on
# (protocol, track, storyboard_id, step_id) and refuses an entry without a protocol prefix,
# which is right -- a ledger of conformance checks should not admit something that is not one.
# Widening the grammar for one row would cost more than the row is worth.
#
# Graduating the mark means an upstream runner that either declares 3.1.1 or honours
# ``--compliance-version`` as the client contract. Until then, leaving it red would mean a
# permanently red job whose redness says nothing a reader can act on.
